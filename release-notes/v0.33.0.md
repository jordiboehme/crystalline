# There can be only one.

On Postgres, a redeploy keeps everything now: accounts, MCP sign-ins, settings and GitHub secrets live in the database, and exactly one instance owns it.

## New & Noteworthy

**A redeploy keeps your sign-ins.** A stateless pod with Postgres and no volume lost its accounts, MCP tokens and GitHub sign-ins at every redeploy, because they were still written to local files in the state folder. Every agent had to sign in again. Now everything that has to survive lives in Postgres:

- Accounts, sessions, MCP tokens, OAuth clients and grants.
- The settings and the domain registry, as one document in the database. `config.yaml` is optional and is read as a base below it. The order is: flags, then environment variables, then the document, then `config.yaml`, then the defaults.
- GitHub tokens, a saved GitHub App and sign-ins to connected Crystalline servers. They are encrypted with your own key (see below).

**Secrets are sealed with your key.** With Postgres, `CRYSTALLINE_SECRET_KEY` (or `CRYSTALLINE_SECRET_KEY_FILE`) is required. Make one with `openssl rand -base64 32`. Every secret is encrypted with XChaCha20-Poly1305 before it reaches the database, so a database dump alone shows no token. A process without the key cannot read or change a secret. A wrong key is refused, it never reads garbage. Keep the key apart from your database backups: without it the sealed secrets are gone.

**One active instance, one standby.** One Crystalline instance owns a database, or a schema in it, through a Postgres session lock. A second `crystalline serve` on the same database does not fail: it waits as a standby and takes over when the first one stops or crashes.

- The standby answers `/health` with `"role": "standby"`, so a liveness probe stays green. `/ready` answers 503 on the standby and 200 on the active instance.
- After a crash the new owner waits about 15 seconds and ends the old sessions before it serves.
- An instance that lost its lock stops writing and exits with code 4.
- `CRYSTALLINE_DATABASE_SCHEMA` puts an instance into its own schema, so several teams can use one database.
- `crystalline status` shows the role, the owner and how long a standby has waited.

**Commands run where the owner runs.** While an instance owns the database, run commands inside it: `kubectl exec <pod> -- crystalline ...` or `docker compose exec crystalline crystalline ...`. A command on another machine is refused and the message names the owner. On a free database a command takes the lock for its own run. Reports like `status` and `doctor` never take the lock.

**Logs as JSON, really all of them.** With `CRYSTALLINE_LOG_FORMAT=json`, the start-up lines of a foreground `crystalline serve` (serving on, copyright, HTTP endpoint, web UI), a fatal error, the model download line and a panic were still plain text on stderr. Datadog showed them as errors. Now every one of them is a JSON event with its real level.

## Fixes

- With `CRYSTALLINE_LOG_FORMAT=json` some start-up lines were still plain text, and a log platform showed them as errors (see above).
- On a stateless Postgres deployment every redeploy signed out every MCP client and lost the GitHub sign-ins (see above).
- When a browser or an agent went away in the middle of a sign-in, the accounts database could stay locked. Later sign-ins and the session cleanup then failed with "database is locked" until a restart. A dropped request now rolls its change back.

## Breaking changes

These apply only if you run Crystalline on Postgres. The local default (one machine, local files) is unchanged.

- Take a backup of the database before you upgrade. Once 0.33.0 has started on it, 0.32 refuses to start on that database.
- `CRYSTALLINE_SECRET_KEY` (or `CRYSTALLINE_SECRET_KEY_FILE`) is required with Postgres. Without it the instance does not start.
- Only one instance is active per database or schema. Running several active instances on one database is no longer possible. Stop every 0.32 instance before you start 0.33.0. In Kubernetes use the `Recreate` strategy, so an old pod does not hold the database while the new one waits. The first start on the upgraded database waits about 15 seconds once.
- Instances that you kept apart with a `search_path` in the URL `options` now count as one instance: the second one waits as standby. Give each one its own schema with `CRYSTALLINE_DATABASE_SCHEMA` instead.
- Accounts, sign-ins and settings start empty in Postgres. Nothing is imported from `web-auth.db`, the state folder or the keychain. Every client signs in once. The first admin comes from `CRYSTALLINE_ADMIN_NAME` with `CRYSTALLINE_ADMIN_PASSWORD_FILE`, or from the setup token the daemon prints. Link GitHub, save the GitHub App (`crystalline github app set`) and connect servers again, inside the pod. An App from the `CRYSTALLINE_GITHUB_APP_*` variables needs nothing.
- Settings you set with `crystalline config set` go into the database. A `config.yaml` you mount is read as a base and never written, except for the `database.*` keys. `config set service.http` is refused, and so is a `service.public_url` with another path than the one the environment or `config.yaml` gives: set those with `CRYSTALLINE_SERVICE_HTTP` and `CRYSTALLINE_SERVICE_PUBLIC_URL` or in `config.yaml`.
- PostgreSQL 14 or newer. Connect directly or through a pooler in session mode. A pooler in transaction mode cannot hold the lock.
- With compose, run commands with `docker compose exec`, not `docker compose run --rm`: a second container is refused while the first owns the database.
- `connect <url>` and `disconnect` on Postgres work only inside the pod.
- `crystalline connect github --personal --json` can report `share_identity` as `null` when it cannot be checked.
