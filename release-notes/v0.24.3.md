# Follow the white rabbit

An agent can now find out how a domain works and change it, a share that may not go straight to the branch finds another way in, and a search follows one source to every engram that cites it.

## New & Noteworthy

**Ask `configure` about a domain.** An agent asked to "allow direct commits" had no way to learn that the MANIFEST key is `sharing`, or which values it takes. `configure` with a `domain` now shows how that domain behaves:

- **Policies:** each MANIFEST policy with its value, the values it takes, what it means and whether you may change it.
- **Sections:** each MANIFEST section that does something (When to Use, Scope, Tag Aliases, Provisioning), and which ones are missing.
- **Rule overrides:** the overrides in `.crystalline.yaml`, each rule with its default severity, and anything in the file that does not apply.

With `set` and `unset` it changes the policies (`sharing`, `generated_indexes`) and the rule overrides (`rules.E007: off`, `token_budget`). Each value is checked before anything is written. Only the domain's owner or an instance admin may change them (without MCP sign-in: whoever may edit the MANIFEST). The skills now point agents to it, and reading a MANIFEST over MCP says where to look.

**A share finds another way in.** Your team's core members may commit straight to the branch, so the MANIFEST says `sharing: direct`. Everyone else has to go through a pull request, and until now their share was simply refused. Now the refusal offers the same changes as a proposal: `share_changes` with `as_proposal: true`, `crystalline origin share <domain> --proposal` or the new button in Fluid. After one refusal Crystalline remembers it for your GitHub login, and your later shares open a proposal on their own when the branch says no. With personal GitHub identities, other people on the same instance are not affected. Once you get direct access, the next share commits directly again. You do not need to change anything.

- `crystalline origin status` and `origin_status` say when your direct commits are refused.
- A GitHub account that cannot write to the repository at all now gets a clear message, and no proposal is attempted.
- A share that names your own open proposal on a direct domain now amends it. Before, it was refused.

**Find every engram that cites a source.** A frontmatter list such as `sources` holds anchors back to where the knowledge came from. When that source changes, an agent needs exactly the engrams that cite it. `search_engrams` now takes `$contains` and `$contains_any` in `metadata_filters`: `{"sources": {"$contains": "<anchor>"}}` matches when the list has that element. The match is exact. A key with a single value counts as a list of one. The lookup uses an index, so it stays fast on large domains: under 2 ms over 50,000 engrams. The upgrade fills the index from what is already there.

- `$contains_any` takes up to 100 distinct values.
- The index skips a custom key over 256 bytes and a value over 1 KB, so `$contains` cannot find them. `crystalline verify` and `validate_engrams` now warn about these values (rule E011).
- Postgres: the upgrade fills the index in one step and holds a lock while it does, a few seconds for 50,000 engrams. Upgrade all instances on a shared database together. Stop them all and start one new instance. It migrates the database. Then start the others. An engram that an older instance writes keeps stale index rows until it is written again or reindexed.

## Fixes

- An empty `.crystalline.yaml`, or one with only comments, was reported as a file that does not parse. It now counts as a file with no overrides.
- A `tags` filter with an empty `$in` list failed with a database error. It now matches nothing.
- On the embedded database, a `tags` filter with about 100 values in `$in` failed with "Expression tree is too large". It now works up to the new limit of 100.

## Breaking changes

- A `tags` filter with `$in` takes at most 100 distinct values. Postgres answered longer lists before, while the embedded database already failed at about 100.
