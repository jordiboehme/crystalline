# You will be upgraded.

Crystalline can now tell you about a new release and update itself. Releases are signed, subagents work quietly and dates run on a new library.

## New & Noteworthy

**Update with one command.** `crystalline update check` says if a newer release is out. `crystalline update now` updates Crystalline the way it was installed:

- Homebrew: it runs `brew upgrade` and then says if the version moved.
- .deb: it downloads and verifies the package and prints the `apt install` command. It never runs apt itself.
- tar.gz on macOS and Linux: it replaces the binary in place. It checks the new binary first (the code signature on macOS, then its version) and hands the running daemon over to the new version with the same start options. Under sudo it only replaces the binary. An agent session stays connected through the update: it waits for the new daemon instead of starting one of its own.
- Windows MSI and zip: it runs nothing. It downloads and verifies, then prints the steps and saves them as `steps.txt`.
- Docker and the Claude Desktop bundle: it says how to update them.

When a tar.gz install sits in a folder of root's, the agent tells you to run `sudo crystalline update now` in your own terminal. It does not try it for you.

Homebrew and tar.gz installs ask first (`Update to <version> now? [y/N]`), and `--yes` skips the question. Without a terminal, as in an agent's shell, `update now` only prints the plan. `update check` exits with code 10 when an update is available and nothing was done, so a script can react to it. A build that is not an official release build refuses `update now`.

**Signed releases.** Each release carries `SHA256SUMS.minisig`. `update now` checks the signature, the release tag in it and the checksum of the file before it uses a download, and refuses anything that does not match. docs/security.md shows how to check a release by hand.

**An opt-in daily check.** Turn it on with `crystalline update auto on`, or with `CRYSTALLINE_UPDATE_CHECK=true`. `crystalline update auto off` turns it off again. The check asks GitHub once a day, without a token, and sends only `crystalline/<version>` as user agent. It is off by default. It never runs in CI, in Docker, in the Claude Desktop-only bundle or with `NO_UPDATE_NOTIFIER` set. The standard Claude Desktop extension starts your installed `crystalline` and keeps its check. A release is offered once it is 24 hours old (`update.min_age_hours`, 0 to 720); `update check --ignore-age` skips that wait. `update.check` is an operator setting, so an agent cannot turn it on through `configure`. The .deb service reads `CRYSTALLINE_UPDATE_CHECK` from `/etc/default/crystalline`.

When the check is on and a newer release is ready:

- the agent hears it once at session start, with what to run for your install method. Never in a subagent and never on resume.
- a command at a terminal prints a one-line hint on stderr, once a day per version.
- `crystalline status` and `crystalline doctor` show how Crystalline was installed and if an update is ready.
- admins see a small note in Fluid's avatar menu. A Docker server never shows it.

`crystalline install` asks once if it should check daily. The answer is No unless you say yes.

**Subagents work quietly.** Crystalline's hooks now know when they run inside a subagent. A subagent gets a short note at start: it may search freely, never asks you anything and stores what it learned itself. The routing block, the recall and the reminder at session end stay silent there. The Claude Code settings file gains a `SubagentStart` entry that runs `crystalline hook stop`. Older binaries ignore it, and any uninstall removes it. The capture skill and the reminder at session end got clearer wording about what is worth keeping: facts, decisions and pitfalls that save a later session from doing the same work again.

**A runner fetches its prompt.** A runner that starts its own agent asks the server with the new ctl verb `automation_prompt`. The answer holds the prompt, the tools the agent may not use, the version and a checksum over prompt and tools, so the runner notices a change after an upgrade. `crystalline reflect prompt --json` and `crystalline evolve prompt --json` read `skills.serve` from this machine's config and environment, so they print the same prompt and checksum as the verb. A config file that does not parse is now an error there, unless you give `--skills-loaded`. `--skills-loaded true` or `false` wins over the setting, and `--config` names another config file. The n8n workflows fetch the prompt at the start of every run. They stop before they take a lease when the server forbids other tools than the workflow leaves out, and the error names the list to set. On a server with `skills.serve: false` the prompt says the skills are already loaded, and `crystalline reflect run` and `evolve run` hand the skills to their agent, so the sentence is true. (#230)

**A headless run may split an engram.** `split_engram` is allowed in a headless run now. The result is reviewed in the run's pull request like every other change.

**Dates run on jiff.** Crystalline moved from chrono to jiff for all dates and times. Every date it writes keeps its bytes. Three things change:

- A leap second `:60` is read as `:59`.
- Only years 0000 to 9999 are accepted. A date after 9999-12-30 that some time zones would put in the year 10000 is refused.
- The suffix `crystalline doctor` puts on a merged desktop folder now uses the UTC date.

## Fixes

- An agent that wrote an engram with its own frontmatter block at the top of the content got two blocks, and the keys of the second one were lost. Now those keys go into the engram's frontmatter. Explicit parameters win, keys the server sets are ignored and the answer names each key. A block that does not look like frontmatter (no known key, or a heading in it) stays text, as before.
- Engrams that 0.33.0 already stored with two blocks: `crystalline verify` (rule E012) and `validate_engrams` now find them, and `crystalline doctor --fix` merges the second block into the engram's frontmatter. Values the engram only had by default (`type: engram`, `status: stable`) give way to the ones in the block. Like an overwrite, the merge writes the frontmatter new, so YAML comments in it are not kept. In a virtual domain, write the engram again with `write_engram` and `overwrite: true`.
- No edit can put a frontmatter block at the top of the content any more. Before, only a prepend was refused. An empty block (two `---` lines) at the top of a capture is dropped, and the answer says so now.
- A share link with an expiry after the year 9999 stays valid. Very large values from a server (a token lifetime, `Retry-After`) or in `CRYSTALLINE_STALE_SECS` and `CRYSTALLINE_HEARTBEAT_SECS` are capped instead of crashing the daemon.
- A standby that took over a Postgres database could wait seconds before it served while other schemas on the same database started or upgraded. Every start waited for the migrations of every other schema, even with nothing to migrate in its own. A schema that is up to date now opens at once.
- When a command could not open the index on Postgres, it told you to check that the file is readable and to run `crystalline doctor --fix`. There is no file on Postgres. The message now names the database and says what to check: is the server running and reachable, are the user and password right and does the server have a free connection. The database's own error still comes last.
