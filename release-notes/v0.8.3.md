# Windows, unlocked

## New & Noteworthy

- **Daemon mode now works on Windows.** Windows file locks are mandatory, so the previous design (the owner record stored inside the locked `service.lock`) could neither be written by the daemon nor read by clients: every spawned daemon died silently at startup and every MCP session fell back to an embedded server after a 15 second wait. The owner record now lives in a separate `service.json`, the daemon publishes and clients attach exactly as on macOS and Linux.
- **Model downloads trust the OS certificate store on Windows and macOS.** Machines behind a TLS-intercepting proxy (common on corporate networks) previously failed the embedding model download with `UnknownIssuer` and stayed text-only forever. The downloader now validates through schannel on Windows and Security.framework on macOS. Linux keeps the bundled roots so the static binaries stay self-contained.
- **Detached daemons log to `daemon.log`.** A daemon spawned in the background writes its stderr to `daemon.log` in the state directory (capped at spawn time), so a failed startup is diagnosable from one file. `crystalline doctor` prints the path.
- **The Windows named pipe is scoped per user.** The pipe name is derived from the state directory instead of one machine-global name, so two users on one machine (or parallel test runs) no longer collide.

## Fixes

- A second concurrent instance on Windows (a second window or sandboxed session) no longer fails with `another Crystalline instance owns the index (pid 0)`; the owner and its real pid are visible again while the lock is held.
- Stale daemon records from dead processes are now detected on Windows; process liveness was previously hardcoded to alive.
- The spawned daemon on Windows no longer flashes a console window and survives the exit of whichever application launched it (job breakaway with an in-job retry).
- The MCP handshake on Windows no longer stalls 15 to 19 seconds on every start; with a working daemon the first start pays the spawn once and later sessions attach immediately.

## Breaking changes

- **A client older than 0.8.3 cannot attach to a 0.8.3 daemon** (the owner record moved out of the lock file). This only matters while old and new binaries briefly coexist on one machine: a 0.8.3 client displaces an older running daemon automatically, so upgrading the binary resolves it on the next start.
