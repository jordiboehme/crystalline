# Be excellent to each other.

Crystalline shares a node nicely now: half the memory while it indexes, no more threads than its CPU limit allows and logs a log platform can read.

## New & Noteworthy

**Indexing needs half the memory.** Every batch of 16 text pieces was padded to its longest piece and run through the model in one go. With long pieces that took more than 1 GB for a few seconds, again and again, until the backlog was done. Big updates and a first start therefore pushed a container to 2 GB and more. Now a batch is sorted by length and split into smaller passes. On 20,000 engrams the peak went from 2.2 GB to about 1.1 GB. Less padding also makes it faster: about 15 % on a Linux CPU and about 50 % on an Apple Silicon GPU.

**The embedding threads follow the CPU limit.** On Linux the model counted the physical cores of the host and ignored the container's CPU limit. On a big node with a small limit that meant many more threads than CPUs, and the container got throttled hard. Now the count is the smaller of the CPU limit and the physical cores. Set `CRYSTALLINE_EMBED_THREADS` to choose your own count. `RAYON_NUM_THREADS` still wins when it is set. The start-up log says which count is used and why.

**Logs as JSON.** Set `CRYSTALLINE_LOG_FORMAT=json` and every line is one JSON object with `timestamp`, `level`, `message` and `target` at the top level. Datadog and similar tools read `level` as the log status, so an INFO line no longer shows up as an error just because it went to stderr. The default stays plain text.

## Fixes

- Setting `CRYSTALLINE_READ_CONNECTIONS` logged "ignoring unrecognized environment variable" at every start and every command, although the variable worked. It is quiet now.

## Breaking changes

None. The embedding thread count on Linux may be lower than before when the container has a CPU limit. That is the point (see above).
