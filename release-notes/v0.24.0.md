# There is no spoon

The Claude Desktop extension carries no Crystalline of its own any more. You keep one Crystalline up to date, and Claude Desktop uses that one.

## New & Noteworthy

**One Crystalline to update.** Until now the extension brought its own copy of Crystalline. If you also installed Crystalline with Homebrew or the MSI, you had two to keep up to date. On Windows the copy inside Claude Desktop could even keep a state of its own. Now the extension is a small launcher. It finds the Crystalline you installed and hands Claude Desktop over to it.

- macOS: `brew install jordiboehme/tap/crystalline`, then the extension.
- Windows: the MSI, then the extension.
- No Crystalline yet, or an old one? Claude tells you in the chat what to install.
- One extension for macOS and Windows, on every chip.

**Claude Desktop only, on a Mac.** You use Claude Desktop and nothing else: no Claude Code, no terminal. Take `crystalline-desktop-only-v0.24.0-macos.mcpb`. It carries Crystalline inside, for Apple silicon and Intel, and works like the extension did before.

**Windows: one daemon for everybody.** Claude Desktop runs its extensions inside its own app package. Crystalline no longer runs in there. The MSI registers a task that starts the daemon when you sign in, and the extension starts it when it is not running yet. So Claude Desktop, Claude Code and the CLI share one daemon, one config and one index. The daemon stops cleanly when you sign out or shut down.

- `crystalline doctor` checks the task. `crystalline doctor --fix` registers it for you when it is missing.
- An update that is installed while the old daemon still runs: run `crystalline status` in a terminal to replace it.

**Merge what an old extension kept apart.** On Windows an older extension could keep its own Crystalline state inside Claude Desktop's package. `crystalline doctor` and `crystalline status` tell you about it. Quit Claude Desktop and run `crystalline doctor --fix --merge-desktop-state`. It adds that state's domains to yours, team domains with their sharing state included. It never overwrites and never deletes anything. When everything came over, it renames the old folder and keeps it.

**Fewer questions.** Your agent no longer asks you to confirm before it shares changes, withdraws a proposal, resolves a conflict or deletes an engram. If you want your agent to do it, it does it. Two questions stay: removing a domain and discarding unshared changes. Both now say in one line what happens and what Accept and Decline do, and the box starts checked.

## Fixes

- A daemon that was killed before it could clean up left a record that pointed at nothing. A new session then waited 15 seconds and started without the daemon, even with one running. Sessions now ask the daemon itself.
- A Homebrew or MSI Crystalline that took over a daemon the extension had started also took over its short life, and stopped five seconds after its last client.
- The nginx example for a server under a path dropped the client address in the collaboration block. It keeps it now.

## Breaking changes

- **Installed only the extension?** On Windows you need the MSI now. On macOS you need Homebrew or the Claude Desktop only bundle. Update the extension to 0.24.0 without either and Claude says "install Crystalline first". Nothing is lost: your knowledge and your state stay where they were.
- The four per-arch bundles are gone (`macos-arm64`, `macos-intel`, `windows-amd64` and `windows-arm64`). Take `crystalline-v0.24.0.mcpb`, or the Claude Desktop only bundle on a Mac.
- `share_changes`, `withdraw_proposal`, `resolve_conflict` and `delete_engram` act on the first call, also in clients that can show a form. `resolve_conflict` without a resolution is refused and names the argument.
- An engram that is open in the editor is never replaced as a whole by an agent. Before, a client that could ask you got a "yes" first. Now the agent uses `edit_engram`, or replaces it after the editor is closed.
