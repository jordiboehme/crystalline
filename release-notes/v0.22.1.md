# Hailing frequencies open

Crystalline now sets up Cursor, Kiro, Gemini CLI and Qwen Code with one command. A new skill teaches your agent provisioning, the license is now MPL 2.0 and a team on a shared database scores contradictions once instead of twice.

## New & Noteworthy

**Four more harnesses.** An agent can only learn from Crystalline if it can reach it. Until now `crystalline install` knew Claude Code, Codex and Copilot. Everybody else had to copy JSON by hand and hope the routing block arrived. Now it's one command per harness:

```sh
crystalline install cursor
crystalline install kiro
crystalline install gemini
crystalline install qwen
```

- Each install registers the MCP server, adds a session-start hook so a new chat gets the routing block and puts the skills where the harness reads them. Kiro also gets a steering file that Crystalline owns.
- `crystalline install` never edits instruction files such as CLAUDE.md, AGENTS.md, GEMINI.md or QWEN.md. It only touches the harness settings and files it creates itself.
- Your settings files keep their comments and formatting. Only our entry changes. Before a file is changed for the first time, a copy goes to the state folder (only you can read it).
- Cursor and Kiro are desktop apps and may start with a short PATH. So their install writes the full path of the `crystalline` on your PATH. Run the install again after you move or upgrade the binary. Restart Cursor after the install so it loads the hook.
- Cursor also runs your Claude Code hooks. The Claude Code routing hook stays silent inside Cursor, so the routing block arrives once.
- Skills are written once per folder. Codex, Cursor and Gemini CLI share `~/.agents/skills`, and Cursor uses `~/.claude/skills` when Claude Code is installed. A shared folder is only emptied when no installed harness still writes it.
- Provisioned skills from your domains reach the new harnesses too, once per shared folder.
- `crystalline uninstall <harness>` takes out what the install wrote and leaves the rest of your files as they were.

The setup pages in the docs list every file per harness.

**A skill for provisioning.** Provisioning works, but nothing taught an agent how to set it up. So the agent guessed, and the guesses cost the person: an MCP secret committed to a repo, a skill moved instead of copied that is gone after a `deny`, a `../` path in a team domain that breaks every teammate's pull. The new `crystalline-provisioning` skill walks an agent and a person through it together: where the tools repo lives, how the folders and names look, which skills you already have in your harness folders and how the MANIFEST gets its `## Provisioning` section through the MCP tools. The person makes every decision (the agent proposes a `git clone` or `git pull` and waits for a yes). An upgrade installs the skill next to your other Crystalline skills.

**A new license.** From 0.22.1 on, Crystalline is licensed under the Mozilla Public License 2.0. Changes to Crystalline's own files stay open and the notices stay with the code. You can now use Crystalline in a bigger project under other terms. Releases up to 0.22.0 stay under the AGPL-3.0-or-later.

**Teams on a shared database.** Two notes for an upgrade, now also in the deployment docs:

- Upgrade every instance of a shared database in one go. An older instance that keeps running after a newer one migrated the schema writes rows the newer parser would read differently, and they stay that way until the engram is edited again.
- Restart the instances one after the other, not at the same moment: the first start after an upgrade reparses the virtual domains, and an edit that lands during that reparse can be refused once.

**Faster contradiction check.** After a write, the check read every engram of the domain again, and once more every night. Now it reads only the engrams that changed. In our test with 2000 engrams a pass after a write took less than half the time.

**Build and release.** The workflows that build Crystalline got stricter. Every workflow runs with a read-only token by default, and a job that needs more asks for it. actionlint and zizmor check the workflows on every pull request. Actions stay pinned to a commit. The jobs that sign, notarize and publish run in a protected environment that only main and version tags can enter, and they get only the secrets they need. The stable build no longer restores a shared cache. Every binary is built with `cargo auditable`, so a scanner can find a vulnerable crate in a shipped binary or image later.

## Fixes

**The first command after an upgrade could fail.** With an agent still connected during an in-place upgrade, the first command could fail once and say the running daemon owns the index and did not answer. Now it waits for the new daemon and gets its answer. A command that replaces an older daemon starts the new one with the same settings the old one had (database, config file and read-only mode). The daemon of 0.22.0 did not record its settings, so after this one upgrade a command waits a few seconds for your agent to start the new daemon and otherwise answers on its own.

**A hung model download blocked the contradiction check.** A download that never sent data (for example behind a proxy that accepts and never answers) held the check until a restart. Now a download that gets no data for two minutes fails, `crystalline status` shows why and it is tried again later. The embedding model download has the same guard.

**Team domains with Windows line endings.** When the GitHub repo of a team domain held files with CRLF line endings, a few checks still compared them byte by byte. A rename that only changed the case showed the file as changed, a renamed file was not shown as a rename, a pull reported an untouched file as merged and every untouched file was read twice per check. All of them compare the text with plain line endings now.

**A split without a checksum was refused on a shared database.** `split_engram` without `expected_checksum` was refused when another instance wrote the same engram at that moment. Now it retries on the newest text, like an edit does, and is refused only when the lines it moves were changed.

**A stale refusal on Postgres.** On a shared Postgres database, an edit could be refused as stale even though nobody else had changed the engram. Now it goes through, as it does on the local database.

**Pending pairs showed 0 while scoring.** During a check after a write, `crystalline status` showed no pairs waiting. Now it shows how many are left.

**A sync without the daemon skipped virtual domains.** `crystalline sync` with no daemon running left the stored engrams of a virtual domain in their old reading after a parser change. Now it reparses them too.

**Shared database, contradiction check:**

- Two instances scored the same virtual domain, so the work and the model's memory were spent twice. Now one instance scores a virtual domain at a time, and the other one does not load the model for it.
- An instance with the check turned off deleted the scores of virtual domains that another instance had scored. The other instance then showed nothing pending over an empty list. Now the off switch clears only the file domains the instance hosts.
- A read-only instance wrote rows when it reparsed virtual domains after a parser change. Now it leaves that to a writable instance.

**Provision status in a fixed order (#124).** `crystalline provision status` listed the domains in the order they were registered, so the undecided ones were hard to find. Now the domains are grouped (allowed, undecided, denied, no provisioning, virtual) and sorted by name in each group. The domains that declare no provisioning and the virtual ones fold into one summary line each, and `--all` lists them one by one. The JSON output always lists them all. The list of domains awaiting a decision and `crystalline doctor` use the same order.

**Private domain names could show up where they should not.** A few answers named or counted domains the caller has no access to:

- A refusal for an unknown domain in `provision` or in the collaboration tools listed domain names, private ones included. Now it names only the domains you can see.
- The note after a write that suggests sharing your changes could count and name private team domains you are not a member of. Now it leaves them out.
- The routing block an HTTP session gets at the handshake counted every registered domain. Now it counts only the domains that are not private.

## Breaking changes

None.

- The index schema is unchanged, so 0.22.0 still opens it.
- Behaviour change you may notice: `provision status` prints a different order and folds the quiet domains.
- Teams on a shared Postgres database: the instances now take short per-domain locks in the database. They break behind a pooler in transaction mode (such as PgBouncer in transaction mode). Point `CRYSTALLINE_DATABASE_URL` at Postgres directly or at a pooler in session mode.
- Run `crystalline uninstall <harness>` for Cursor, Kiro, Gemini CLI or Qwen Code before you downgrade below 0.22.1.
