# Let it go

A patch for Windows. The daemon no longer keeps the folder of the program that started it in use.

## Fixes

**The Claude desktop app on Windows could not update.** The update stopped with "Another program is currently using this file" on a path under `WindowsApps\Claude_<version>`, and the app didn't open again until Crystalline was stopped. The daemon started by `crystalline mcp` kept the working folder of the program that started it, for its whole life. On Windows a folder that is some process's working folder can't be renamed or deleted. So a daemon started from inside the app's folder blocked the update.

A daemon started by a client (Claude Code, Codex, the Claude Desktop extension or any other) now works in Crystalline's state folder, on every platform. A relative `--db`, `--config` or `CRYSTALLINE_CONFIG` given to the client is made absolute first, so it still points to the same file.

If the dialog is on screen right now: run `crystalline ctl shutdown`, then let the update finish. After the upgrade, the next client replaces the old daemon with a new one that no longer holds the folder.

## New & Noteworthy

**You can now see where the daemon runs.** On Windows a daemon can also inherit the job or the package identity of the program that started it. Both can keep that program's files in use, and until now nobody could tell.

- `crystalline doctor` shows the daemon's working folder, and on Windows its job and package identity. It warns when the daemon may keep its starter's files in use. The warning doesn't count as a problem, so doctor's exit code doesn't change.
- `crystalline status` has one new line, `Runs in:`.
- `ctl status --json`, `status --json` and `doctor --json` gain a `runs_in` object. Nothing was removed or renamed.
- Crystalline has always asked Windows to start the daemon outside the job of its client. When Windows refuses, the daemon still starts inside the job, as before. Now it logs a warning in the client's log and in `daemon.log` instead of saying nothing.

## Breaking changes

None. One behaviour change worth knowing: a relative path you wrote by hand in `config.yaml` (a domain or database path) or in a `CRYSTALLINE_*` variable now resolves against the state folder in a daemon started by a client. Before, it resolved against the folder the first client happened to start in. `crystalline domain add` always writes absolute paths, so this only affects paths written by hand. A `crystalline serve` you start yourself is unchanged: it keeps the folder you started it in.
