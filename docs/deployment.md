# Deploy Crystalline

Crystalline runs the same way in every scenario: a daemon in the middle keeps one search index in sync with knowledge, and one or more agents connect to it, whether that connection is a local stdio pipe or a network HTTP endpoint. A browser is one more client of that same endpoint, since the daemon serves the web UI itself. The scenarios below are variations on that one architecture.

See [Get started](../README.md#get-started) in the README to install the binary and wire up an agent; this guide covers where the daemon, its knowledge and its index live in each shape.

## Personal workstation

The default shape: install the binary, point one or more agents at `crystalline mcp` over stdio, and the first connection spawns a background daemon that loads the embedding model once and watches every registered domain. Knowledge lives in ordinary local folders, read-write, so capturing what an agent learns as it works is the entire point. See [Get started](../README.md#get-started) in the README for the stdio setup.

That daemon serves the web UI too, however it started: a hand-typed `crystalline serve` and the one an agent's stdio connection spawns behave the same, and both open the HTTP endpoint at `http://localhost:7411` unless it is turned off. So there is nothing to deploy to browse what your agents have learned - open that address, and the first visit to an instance with no accounts yet asks you to create your admin account right there in the browser (see [Web UI from the daemon](#web-ui-from-the-daemon)). `crystalline config set service.http false` closes the endpoint for every daemon that user starts, since the config file is per user rather than per machine, and `CRYSTALLINE_SERVICE_HTTP=false` closes it for the one process it is set on.

```mermaid
flowchart LR
    A1[Agent] -->|stdio| D[Daemon]
    A2[Agent] -->|stdio| D
    B[Browser] -->|HTTP :7411| D
    D --> K[Knowledge files]
    D --> I[Index]
```

### Daemon lifecycle

It does not matter who or where starts the daemon. The first `crystalline mcp` connection spawns it as a fully detached process (its own session, no controlling terminal, stdio closed) that serves the user's state directory and outlives every client that connects to it; later connections and plain CLI verbs attach to the same daemon over its local socket. Stopping it is one command, `crystalline ctl shutdown`, and the next connection simply spawns a fresh one. The one exception is the Claude Desktop only extension on macOS: its daemon runs from inside Claude Desktop's own extension folder, so it is not detached from Desktop and exits on its own five seconds after its last client disconnects (a browser tab on the web UI does not count as a client). Desktop's next session starts a fresh one; a Claude Code session attached to the same daemon keeps it alive for as long as it is connected. The standard extension starts the installed binary, whose daemon is the normal detached one.

A daemon can also end up in a third state: alive and holding the index lock, but answering nothing on its socket. Nobody can attach to it and nobody can take the index from it, so it would block every client until the process died on its own. The next client that connects ends that state instead of waiting it out. It probes the socket for two seconds, and only when nothing answers and the service record names a process that is both alive and identifiably a Crystalline binary does it ask that process to stop, force it if it will not, clean up the record and start a fresh daemon. Anything less than certain about who holds the lock is refused rather than signalled, with an error naming the lock file. `crystalline status` reports the same state read-only as `unresponsive`, and `crystalline doctor --fix` performs the replacement on demand.

Upgrades need no manual restart: attaching is version aware, so the first client built from a newer binary (after a `brew upgrade`, say) asks the older daemon to shut down gracefully and a new daemon starts on the current version. The takeover is one-way - an older client attaches to a newer daemon rather than displacing it back. Agent sessions ride through the swap, because the stdio bridge reconnects when its daemon goes away, replays the MCP handshake and answers any request the restart orphaned with a retryable error instead of silence.

Unregistering a domain stops it being served the moment it happens, whatever became of its index rows: nothing answers for a domain nobody registered, so the knowledge you deliberately removed cannot outrank what you kept. What is left after that is only disk, and the daemon tidies it in the background rather than leaving it there forever. Once an hour it checks every domain its index knows against the current configuration and stamps each one still registered, so it always has evidence of when a domain was last seen; a domain that has gone seven days without being registered has its engram rows collected, and its domain row goes with them so the name is free again. Seven days give a `config.yaml` typo or a machine left off for a week room to recover before anything is dropped, and since nothing is served from those rows regardless, the only thing the wait costs is disk. A domain the sweep cannot be sure about is left alone rather than guessed at: a virtual domain's engrams are its only copy and are never swept away unattended (end one on purpose with `crystalline domain remove <domain> --purge`, which asks first), a domain another instance still holds the host lock of stays that instance's to keep, and a read-only instance collects nothing at all. `crystalline doctor` reports what the sweep would collect and how long each candidate has gone unregistered, and `crystalline doctor --fix` collects them right away, grace period ignored, and also drops the empty domain rows older versions left behind after a removal (an explicit `domain remove` drops its own row at once) - the immediate path for someone who just removed a domain on purpose and does not want to wait the week out.

### Install markers

Each package writes a one-line `install-source` file that tells `crystalline update` how this binary was installed. The marker is read relative to the binary's real path, so a copy of the binary somewhere else does not inherit it. The .deb ships `/usr/lib/crystalline/install-source` with `deb`. The Homebrew formula writes `install-source` with `homebrew` into the formula's `libexec` folder. The MSI installs `install-source` with `msi` beside `crystalline.exe` in `bin\`, in the default folder or a custom one. The container image ships `/usr/local/lib/crystalline/install-source` with `docker`, owned by root and read-only. The tar.gz and zip archives carry no marker, and the Claude Desktop only bundle is known by `CRYSTALLINE_CHANNEL=mcpb`. Only a binary the release workflow built for a tagged release is an official build. Any other build (a `cargo build`, a dry run of the workflow, a distribution package) never replaces itself with `crystalline update now`.

## Updating

Two commands update Crystalline, and they work the same in every shape:

- `crystalline update check` asks GitHub now for the newest stable release. It prints both versions, when the release was published, how this binary was installed, what `update now` would do and the link to the release notes. It asks whether or not the daily check is on. Exit code 0 means up to date, or the newer release is still younger than the release-age gate (the output says when it is offered). 10 means an update is available. 1 means the check failed. `--json` prints the same plan as JSON.
- `crystalline update now` prints the same plan and then does what the install method allows. Exit code 0 means done, or nothing to do. 10 means an update is available but nothing was done. 1 means refused (the reason is printed) or failed.

Only a stable release newer than the running binary is offered: never a pre-release, never a downgrade. A release is offered once it is 24 hours old (`update.min_age_hours`, 0 to 720, or `CRYSTALLINE_UPDATE_MIN_AGE_HOURS`), so a release that is pulled again soon after it came out reaches nobody. `--ignore-age` on either command skips the wait. When GitHub's API does not answer (its rate limit), the age counts from the first time this machine saw the release.

`update now` reads the [install marker](#install-markers) of the binary you run and refuses before it downloads anything when it should not act: on a build that is not official ("not an official release build"), inside an app package such as Claude Desktop's ("run it in a normal terminal"), when the marker and the binary's path disagree (both are named), in a Docker install, in the Claude Desktop-only bundle and when the method cannot be told.

Homebrew and tar.gz installs change installed files, so `update now` asks first (`Update to <version> now? [y/N]`), and `--yes` skips the question. Without `--yes` and without a terminal, as in an agent's shell, it prints the plan, ends with "Nothing was changed. Run crystalline update now --yes to update." and exits with 10. The .deb, MSI and zip are only downloaded and verified, which changes nothing installed, so `update now` does that without a question and then prints the command or the steps that install it. You run those yourself.

Every download is verified before it is used, and a failed check stops the update: the sha256 digest GitHub lists for the file (when the API answered), the file's line in `SHA256SUMS`, and the minisign signature over `SHA256SUMS`, whose signed comment must name the release being installed. On macOS the new binary must also carry Crystalline's code signature, and on a tar.gz install it must print the release's version before it is put in place. A line such as "Verified: the sha256 digest GitHub lists, the minisign signature over SHA256SUMS for v0.34.0, the line in SHA256SUMS." says which checks ran. `update now` refuses a release without a valid signature, so it cannot install anything older than 0.34.0, the first signed release. How to check a download by hand: [Verify a release](security.md#verify-a-release).

Downloads go to `~/.cache/crystalline/updates/<tag>/` on macOS and Linux (`XDG_CACHE_HOME` moves it) and to `%LOCALAPPDATA%\crystalline\updates\<tag>\` on Windows. The folder of the release you install stays until a newer one was downloaded and verified. A lock file in `updates/` keeps two runs apart.

### Homebrew

`crystalline update now` runs `brew upgrade jordiboehme/tap/crystalline` after you said yes, then reads the version Homebrew installed. It says "upgraded to <version>", or fails with "brew did not upgrade (tap not refreshed?)" when `brew upgrade` ended without a new version: run `brew update` and try again. By hand, run the same `brew upgrade` command. The next `crystalline` command or agent session hands the daemon over to the new version ([Daemon lifecycle](#daemon-lifecycle)).

### .deb

`crystalline update now` downloads and verifies the package and prints how to install it, with the full path of the download folder, for example:

```
Install it with:
  cd /home/ada/.cache/crystalline/updates/v0.34.0
  sudo apt install ./crystalline_0.34.0_amd64.deb
```

It never runs apt. As root the line has no `sudo`. Run as `sudo crystalline update now`, it downloads into a new folder of root's and prints `sudo apt install` with the full path of the package. Upgrading the package restarts the systemd service only if it is running. The service reads its settings from `/etc/default/crystalline`, so its daily check is turned on there, not with `update auto on` ([Linux server with systemd](#linux-server-with-systemd)).

### tar.gz on macOS and Linux

`crystalline update now` downloads and verifies the archive, takes only the `crystalline` binary out of it, checks it (the code signature on macOS, then its version) and puts it in place of the binary you ran. Then the new binary hands the running daemon over to the new version with the same start options (database, config, read-only mode, HTTP address, allowed hosts). An agent session that is connected at that moment waits for the new daemon instead of starting one of its own, and its connection carries on with it. Then the new binary refreshes the installed hooks and skills for user scope and for the project of the current folder. Other projects refresh when a session starts in them. When the daemon read a `CRYSTALLINE_*` variable that this shell does not have, it is left running on the old version and the output says why; run `crystalline status` from a shell that has the variable.

When you cannot write to the binary's folder, `update now` refuses before it downloads anything and names the folder. For a folder of root's (such as `/usr/local/bin` on Linux) it suggests `sudo crystalline update now`. Under `sudo` it downloads into a new folder of root's and replaces only the binary. The daemon is not touched, and the output says to run `crystalline status` as yourself, which hands the daemon over. By hand: take `crystalline` from the newest release's tar.gz and move it over the old binary.

### Windows MSI and zip

On Windows `crystalline update now` runs nothing. It downloads and verifies the .msi or the zip into the download folder (for the zip it also takes `crystalline.exe` out of it), prints the steps with exact paths for Windows PowerShell 5.1 and PowerShell 7, and saves them as `steps.txt` in the same folder, whose path it prints. Every agent session that uses Crystalline holds `crystalline.exe` open, so the steps start with closing them. An agent can run `update now` and show you the steps, and you run them when your sessions are closed.

For the MSI the steps are:

1. Close every agent session that uses Crystalline. When a daemon runs, stop it with `crystalline ctl shutdown`, or the installer may ask for a reboot.
2. Run the installer and wait for it, with the folder of your current install as `APPLICATIONFOLDER`, so a custom folder is kept. `update now` prints the full line, for example `$p = Start-Process msiexec.exe -Wait -PassThru -ArgumentList '/i', '"<download folder>\crystalline-v0.34.0-windows-amd64.msi"', '/passive', '/norestart', 'APPLICATIONFOLDER="C:\Program Files\Crystalline"'; $p.ExitCode`. In the default folder a double click on the .msi works too. Windows asks for administrator rights. The MSI has no Authenticode signature yet, so the prompt names an unknown publisher. The signed `SHA256SUMS` that `update now` checked is what tells you the file is the release.
3. Read the exit code: 0 means installed, 3010 means installed and active after a reboot (reboot first), 1602 means cancelled (for example a no at the administrator prompt; nothing changed), 1618 means another installation is running (wait and run step 2 again). Any other number means it did not install.
4. Start the daemon again as it was started, then run `crystalline status`. The steps say how: the task `\Crystalline\Daemon` (`schtasks.exe /Run /TN '\Crystalline\Daemon'`), the same `crystalline serve` command with the variables it had then, or nothing, because the next agent session starts it.

For the zip the steps do not stop the daemon:

1. Close every agent session that uses Crystalline.
2. Copy the new `crystalline.exe` from the download folder beside the old one, as `crystalline.new.exe`.
3. Rename the old `crystalline.exe` to `crystalline.old.exe` (Windows allows that for an exe in use).
4. Rename `crystalline.new.exe` to `crystalline.exe`. If this fails, the steps say how to put the old one back.
5. Run `crystalline --version`. It must print the new version.
6. Run `crystalline status`. It hands the daemon over to the new version with its start options.

Run the steps one at a time and stop at the first error. The copy comes first, so a step that fails never leaves the folder without its exe. The next `update now` and `crystalline doctor` remove a `crystalline.old.exe` that is no longer in use.

### Docker

The image has its update check off, and `update now` refuses ("a Docker install; pull the new image"). Pull the new image and recreate the container, for example `docker compose pull && docker compose up -d`. See [Run in a container](#run-in-a-container).

### Claude Desktop extension

The standard extension starts the `crystalline` you installed, so update that one with the method above. Claude Desktop then offers the new extension in an update dialog ([Claude Desktop setup](setup/claude-desktop.md#updating)). The Claude Desktop-only bundle carries its own Crystalline: its update check is off and `update now` refuses. Download the newer `crystalline-claude-desktop-only-v<version>-macos.mcpb` from the releases page and open it, so it installs over the old one.

### A binary you built yourself

A binary from `cargo build`, `cargo install` or a distribution package is not an official build, so `update now` refuses and never replaces it. Build the new version the same way. `update check` still tells you whether a newer release exists.

### The daily update check

The daily check is off by default. Turn it on with `crystalline update auto on` (it prints "Update check on. Turn it off with: crystalline update auto off") and off with `crystalline update auto off`. Both set `update.check`, the same as `crystalline config set update.check true`; the variable is `CRYSTALLINE_UPDATE_CHECK`. The key is an operator setting, so an agent cannot switch it with the `configure` tool. `crystalline install` in a terminal asks once per machine:

```
Check once a day for a newer Crystalline? Nothing is installed without you. [y/N]
```

Yes turns the check on. No, Enter or Ctrl-C leave it off and print "Daily update check: off (`crystalline update auto on` turns it on).". It never asks when `update.check` or `CRYSTALLINE_UPDATE_CHECK` is set already, with `--json`, on a build `update now` does not act on, when the check is kept off (see below) or when a session start refreshes an install. An install without a terminal prints only that second line, once per machine.

Once a day (after a failed check, after four hours) Crystalline asks GitHub for the newest release, with no token and the User-Agent `crystalline/<version>`. GitHub sees your address and the version, nothing else; the details are in [Outbound connections](security.md#outbound-connections). The check never makes the daemon's start or its requests wait. The check only looks: it installs nothing. With the check off the daemon makes no request; `update check` and `update now` still ask when you run them.

The check stays off, whatever `update.check` says, when `NO_UPDATE_NOTIFIER` or `CI` is set to a value in the daemon's environment, in a Docker install and in the Claude Desktop-only bundle. A systemd service reads its settings from `/etc/default/crystalline`: add `CRYSTALLINE_UPDATE_CHECK=true` there and restart the service. `crystalline update auto on` says so on a machine with the .deb and its unit.

When a check finds a newer release that passed the age gate, it shows in these places:

- `crystalline status` and `crystalline doctor` show how this binary was installed, whether it is an official build and what the last check found, for example "update check on; Crystalline 0.35.0 is available (this is 0.34.0); run: crystalline update now". With the check off they say "update check off" and why.
- After most commands at a terminal, one line on stderr, at most once a day per version: "Crystalline 0.35.0 is available (this is 0.34.0). Update with: crystalline update now". It never shows with `--json`, when stderr is not a terminal, or after `status`, `doctor`, `update`, `install` and the commands that programs and hooks run.
- At the start of an agent session, the routing block that the session-start hook from `crystalline install` delivers carries one short block, at most once a day per version. Never in a subagent, never on a resumed, cleared or compacted session, and only for an install `update now` acts on:

  ```
  Crystalline 0.35.0 is available (this is 0.34.0, homebrew). Notes: https://github.com/jordiboehme/crystalline/releases/tag/v0.35.0
  Tell the user once. If they want it: run crystalline update now --yes. No user here: do nothing.
  ```

  The last line names what to run for the install method: `update now --yes` for Homebrew and tar.gz, `update now` and the apt command it prints for the .deb, `update now` and the steps it prints for the MSI and the zip. The block reads only the cached result: no network, no daemon call, no wait.
- In Fluid, an admin sees a small note in the avatar menu ([Web UI from the daemon](#web-ui-from-the-daemon)). Nobody else sees it.

```mermaid
flowchart LR
    D[Daemon, check on] -->|once a day, no token| G[GitHub releases API]
    D --> C[update-check.json]
    C --> S[status and doctor]
    C --> H[stderr hint]
    C --> B[Session-start block]
    D -->|admins only| F[Fluid note]
    P[Person or agent] -->|crystalline update now| V[Download, verify, act per method]
```

## Claude Desktop extension

The standard extension (macOS and Windows) carries no Crystalline. `crystalline install claude-desktop` builds it on your machine, saves it as `crystalline.mcpb` in Crystalline's state folder and opens it in Claude Desktop. The release does not carry it. The command pins the path of the first crystalline on `PATH` (or its own, when `PATH` has none) in `CRYSTALLINE_BINARY`. The extension is a small Node launcher that Claude Desktop runs with its own Node. It tries the pinned binary first and falls back to a search (Homebrew's two folders, then `PATH` on macOS; `Program Files`, then `PATH` on Windows). It checks that it is 0.24.0 or newer and relays stdio to `crystalline mcp`, which lands on the same daemon as the personal workstation shape. So a Desktop user keeps one Crystalline up to date, the same one Claude Code and the CLI use. After an upgrade, the first `crystalline mcp` the older extension starts builds the extension again at its own version and opens it, so Claude Desktop shows an update dialog. It does this once per version and only when `crystalline install claude-desktop` ran once (its record in the state folder), with a lock so that only one offer runs at a time. On Windows the bridge inside Claude Desktop's package writes nothing: it sends `desktop_offer` to the daemon outside the package, which offers it when it runs the same version, and the bridge does not wait for the answer. Declined, or no dialog: run `crystalline install claude-desktop`. Without a usable binary the launcher answers by itself: one `status` tool, and instructions that tell the model (and through it the user) what to install. Someone who uses only Claude Desktop on a Mac, and neither Claude Code nor the `crystalline` command, can take `crystalline-claude-desktop-only-v<version>-macos.mcpb` instead. It carries a universal binary and keeps the 0.18.2 behaviour: its daemon stays attached to Desktop and exits five seconds after Desktop quits. Both bundles take no configuration and start with no domains. The daemon opens the web UI at `http://localhost:7411` by default, so the extension is also how a Desktop user gets the browser half (`service.http: false`, or `CRYSTALLINE_SERVICE_HTTP=false`, turns it off). The agent creates a domain whenever it needs somewhere to capture knowledge, with the `add_domain` tool - a folder of markdown files under `Documents/Crystalline` (the default domains root, overridable with `domains_root` or `CRYSTALLINE_DOMAINS_ROOT`), a database-backed virtual domain or a GitHub team domain. Onboarding is automatic, and the same command saves the `crystalline-intelligence` skill as a zip in Downloads, which adds capture and collaboration best practices as an uploadable skill (see [Skills](learning-loop.md#skills)).

**On Windows the process inside Desktop is only a bridge.** Claude Desktop is an MSIX app, and a process it starts can run inside its package, where new files under `AppData` are written to a hidden copy that only the app sees and the process ends when the app ends. So `crystalline mcp` inside the package never hosts a daemon, never takes one over and never runs the knowledge stack itself, and it writes nothing under `AppData`. The same holds since 0.30.0 for every `crystalline` command that runs inside Claude Desktop, such as one from Claude Code's shell or a Claude Code hook there: it sends its writes to the daemon (`domain add`, `config set` and every data command among them) or refuses, and it never opens an index of its own, not even for a read. Without a daemon such a command runs the task like the bridge does, and when no daemon comes up it says why and names a terminal outside Claude Desktop. `crystalline serve` does not run inside the package at all, and the terminal setup steps (`connect`, `disconnect`, `install`, `uninstall`, `daemon-task register`, `doctor --fix`, `doctor --discard-rename`, `users`, `kept drop`, `model download`) refuse there and name the terminal. Only the per-session hook files under `hooks\` are still written there; the daemon's own `hooks\maintenance.json` is not, and the Stop hook sends its stamps to the daemon instead. The reason: Windows keeps every new file such a process creates under `AppData` in the package's private copy, and our saves always create a new file, so a write from inside would build a second state the daemon never sees. The bridge finds the daemon by its pipe first (never by `service.json` alone), resolves the state folder from the known folder rather than an `APPDATA` the package may have changed, and when no daemon answers runs the Windows task `\Crystalline\Daemon` and waits up to 15 seconds. The MSI registers that task for the Users group: it starts `crystalline serve --daemon --from-task` at every sign-in, outside any package, with no time limit. A daemon the task starts reads the system environment, not your shell's. So a variable such as `CRYSTALLINE_CONFIG` or `CRYSTALLINE_SERVICE_HTTP` that you set only in a terminal does not reach it. Outside Claude Desktop the task stands in for a daemon only when no such variable is set; otherwise the client starts the daemon itself. When the running daemon serves another config file or HTTP address than your shell would, `crystalline status` and `crystalline doctor` name the variable. On Windows the line reads "The daemon serves <its value>, not <this shell's value> from <VARIABLE>: a daemon the sign-in task started reads the system environment. Set <VARIABLE> as a user environment variable, or stop the daemon (`crystalline ctl shutdown`) and start it from this shell." On macOS and Linux there is no sign-in task, so the line reads "The daemon serves <its value>, not <this shell's value> from <VARIABLE>: the daemon was started without this shell's environment. Stop it (`crystalline ctl shutdown`) and start it from this shell, or set <VARIABLE> where it starts." The daemon stops cleanly on sign-out and on shutdown. When Crystalline is removed, the MSI ends every running Crystalline task, the machine task and each per-user task, with `schtasks /End`. From 0.24.2 on that includes the removal of the old version during an update. The update from 0.24.1 has no such step and relies on Restart Manager. That stops a daemon hard, without its clean shutdown, and it reaches only a daemon a task started. A daemon started another way in another user's session is left to Windows' Restart Manager, which may ask for a restart. After the upgrade, Claude Desktop's next request starts the task again, and so does the next sign-in. `crystalline doctor` checks the task. When it is missing, `crystalline doctor --fix` registers one for the current user, but only for the crystalline the MSI installed in its default folder, `Program Files\Crystalline\bin`. For a copy anywhere else it reports the task and registers none. Install the MSI, or run it again, to get the task. The task `crystalline doctor --fix` registers for the current user is named `\Crystalline Daemon for <name> (<SID>)`, so two accounts with the same user name never share one. A task with the name 0.24.0 gave it, `\Crystalline Daemon for <name>`, still works. `crystalline doctor` points it out, and `crystalline doctor --fix` and `crystalline daemon-task register` move it to the new name. When the machine task `\Crystalline\Daemon` works, `--fix` only removes the old task, because every bridge finds the machine task first. A task under the old name that belongs to another account is left alone. When the machine-wide task is broken, `--fix` asks for an administrator instead of fixing it. For details, run `crystalline doctor`. A daemon older than the installed binary is used as it is. Run `crystalline status` in a terminal outside Claude Desktop to replace it.

```mermaid
flowchart LR
    I[crystalline install claude-desktop] -->|builds and opens| CD[Claude Desktop]
    CD -->|runs with its Node| S[Launcher shim.js]
    S -->|stdio| M[crystalline mcp, pinned or found]
    M -->|pipe first| D[Daemon outside the package]
    M -.->|Windows, no daemon| T[Task Crystalline Daemon]
    T -->|at sign-in or on demand| D
    M -.->|newer than the extension, once per version| U[Update offer: build and open]
    D -.->|desktop_offer, Windows package| U
    U -->|update dialog| CD
    A[Agent] -->|add_domain| D
    D --> K[Domains under Documents/Crystalline]
    B[Browser] -->|HTTP :7411| D
```

**A second state inside Claude Desktop's package.** Up to 0.23.1 the extension carried its own binary, and before 0.30.0 every `crystalline` command that ran inside Claude Desktop (Claude Code's shell and hooks there) wrote its state itself. On Windows either could leave a second state inside Claude Desktop's package. Its symptom: searches find no domains, or fewer, while the routing block at session start lists them. `crystalline doctor` and `crystalline status` report it and name the domains it registers that the daemon does not serve, and the bridge tells the agent about it at the start of a session. A folder there that is only another name for the real state folder (the same `config.yaml`) is not reported, and one that shares any state file with it is never merged. `crystalline doctor --fix --merge-desktop-state`, run with Claude Desktop closed, merges it: the union of both domain lists and the database-backed domains that exist only there. It also takes over the `github` settings, such as `github.enabled`, that only Claude Desktop's config had, and names each one. A setting this machine already has is never changed. It never overwrites or deletes anything, and it renames the folder to `crystalline.merged-<date>` only when everything was merged.

## Team server

For a team, run the GHCR image (see [Run in a container](#run-in-a-container)) via `examples/docker/compose.yaml`: the image's `CRYSTALLINE_SERVICE_HTTP=0.0.0.0:7411` default has the daemon listening on the network already, and every agent on the network reaches it over streamable HTTP instead of stdio. Knowledge is bind-mounted from the host so it stays exactly the same markdown files, a `/data` volume holds the disposable index, and the slim `latest` image downloads the model into that same volume once (pick `with-model` instead to skip the download). The compose file sets `CRYSTALLINE_AUTH_MCP=true`, so each agent signs in with a personal MCP token (see [An account per agent](#an-account-per-agent)); without it, anyone who reaches the port is served with no sign-in. Agents that reach the daemon by a hostname rather than `localhost` need that host in `CRYSTALLINE_SERVICE_ALLOWED_HOSTS` (the daemon validates the `Host` header against DNS rebinding, which is not access control; see [Configure through environment variables](#configure-through-environment-variables)). The MCP transport caps a request body at 15 MiB, room for a 10 MiB file an agent uploads as base64 (13,981,016 bytes) plus the JSON-RPC envelope; the JSON API applies 10 MiB to everything but its two archive-upload routes, so a text write between 10 and 15 MiB is served by MCP and refused by the browser route, and a body past 15 MiB is refused with `413 Payload Too Large` before any tool runs; an operator meets this through a proxy first, which is why anything in front of the port needs its own body limit raised to match (see [Team server with Fluid](#team-server-with-fluid)). See [Run in a container](#run-in-a-container) for the compose file and image tags.

```mermaid
flowchart LR
    A1[Agent] -->|HTTP :7411| D[Daemon]
    A2[Agent] -->|HTTP :7411| D
    D -->|bind mount| K[Knowledge files]
    D -->|volume| I[Index]
```

### An account per agent

An agent that runs on another machine does not need a password, because it never signs in to the web UI. Give it its own account with no password and one personal MCP token, in one step:

```bash
crystalline users add agent-build --role editor --mcp-token build
```

The command creates the account `agent-build` and prints the token once. Add `--json` to get `name`, `role`, `id`, `token` and `label` as one object for a script. `--mcp-token` and `--password-stdin` cannot be used together, and a name that already exists is refused: a token for an existing account is `crystalline users mcp-token <name>`. The account is created with the role you give (viewer if you give none), so an agent that writes needs `--role editor`. Password sign-in never works for it, and `crystalline users list` shows it as "active, no password". You can still list, rotate and revoke its tokens with `crystalline users mcp-token`, change its role with `users role`, set what it may write with `users writes` and turn it off with `users disable`.

An account can also carry a write list: the domains it may write to. Every other domain is read-only for that account, while it still reads every domain it can see. An entry is a domain name (`agents-bot`) or a name prefix ending in `*` (`agents-*`). Without a list nothing changes. A list only lowers rights: a domain on the list still needs the role and, for a private domain, the membership. A read-only domain stays read-only for everybody.

A worked example: every agent gets its own domain, reads all company knowledge and writes only its own domain.

```bash
crystalline domain init /srv/knowledge/agents-bot --name agents-bot
crystalline domain add agents-bot /srv/knowledge/agents-bot
crystalline users add bot --mcp-token bot --role editor --writes agents-bot
```

`crystalline users writes bot agents-bot,agents-shared` replaces the list, `crystalline users writes bot` prints it, and `crystalline users writes bot --clear` removes it. `crystalline users list` shows each account's list. An entry that names no registered domain is accepted with a warning, since the domain may be created later. A domain rename updates the entries that name the domain exactly; an entry with `*` stays as it is.

What the agent sees: its routing block marks every other domain "(read-only)", and a domain row in `list_domains` carries `read_only: true` for it. A write to any other domain, `eng` for example, is refused with "'eng' is not on the write list of 'bot'; an instance admin changes it with crystalline users writes".

On the agent's machine, set the server and the token and nothing else:

```bash
export CRYSTALLINE_REMOTE_URL=https://crystalline.example.com
export CRYSTALLINE_REMOTE_TOKEN=cmt_...
```

See [A local Crystalline with domains from shared servers](#a-local-crystalline-with-domains-from-shared-servers) for what that offers the agent.

## Web UI from the daemon

The daemon serves Fluid itself, and it does so by default. The browser UI is built into the binary and the HTTP endpoint opens at `127.0.0.1:7411` unless something turns it off, so one process on one port answers both the agents that speak MCP and the people who want to read what those agents learned: point a browser at `http://localhost:7411` and the app is there, with no second container, no static bundle to deploy and no version to keep in step. `service.http: <host:port>` (or `CRYSTALLINE_SERVICE_HTTP`) moves the endpoint somewhere else and `service.http: false` closes it - that is the machine's answer, read by every daemon on it however it was started. `serve --http <host:port>` and `serve --http off` are the one-invocation override: a daemon whose flag disagrees with the configured value says so out loud at startup (see [Linux server with systemd](#linux-server-with-systemd)). It is the same UI the compose variant below runs - domains down the side, an engram with its frontmatter, observations, relations, backlinks and neighborhood graph, faceted search and Cmd+K to jump anywhere - served straight from the daemon that holds the index.

Agents hand people links into it. Every read, write, edit and move an agent makes over MCP comes back with `web_url`, the engram's page, and a list result comes back with one `web_url_template` to fill in; a URL may end in `#` and a heading's slug to open the page scrolled to that section, and the link symbol beside every heading copies exactly that URL. The link is the same for everybody on a shared instance and carries no token: on a default install it opens the login screen first and lands on the page after sign-in, and with `auth.anonymous` on it opens directly. Where the daemon cannot work out the address people reach it at - behind a proxy that rewrites the `Host`, inside a container, or with the UI served by a separate Fluid deployment - `service.public_url` names it (see [Configure through environment variables](#configure-through-environment-variables)), path included when the UI is served under one (see [Under a path](#under-a-path)).

```mermaid
flowchart LR
    B[Browser] -->|HTTP :7411| D[Daemon]
    A[Agent] -->|MCP over HTTP :7411| D
    D --> K[Knowledge files]
    D --> I[Index]
```

The web UI and the JSON API are both on by default wherever the HTTP endpoint is on, so there is nothing to enable. Two settings turn them off: `service.ui: false` (or `CRYSTALLINE_SERVICE_UI=false`) serves the API and MCP without the UI, which is the shape a separate Fluid deployment fronts, and `service.api: false` leaves MCP and `GET /health` alone on the port and takes the UI down with it, since a UI without its API is a shell that can only render a login error. Both are read once when the HTTP surface starts, like `service.read_only`, so changing one needs a daemon restart, and the line the daemon prints on start names which of the two is off.

Accounts work exactly as in [Team server with Fluid](#team-server-with-fluid), because it is the same API behind the same UI: nothing is readable until an account exists. The browser is where that first account is normally made. A daemon that has no accounts yet greets the first visit with a create-first-admin form instead of a login form: fill in a name and a password, and you are that instance's admin and signed in already. There is no second chance for a passer-by, because once any account exists the endpoint behind that form is gone for good and answers `410 Gone` to everyone, forever. `crystalline users add ada --role admin` does the same job from a terminal (it prompts for a password, or `--password-stdin` reads it from a pipe) and stays the scripted and recovery path; it writes the accounts database directly, so a running daemon picks the new account up on its next lookup with nothing to restart. One platform is the exception: on Windows the accounts database cannot be shared between two processes (the database engine has no cross-process coordination there yet), so `crystalline users` has to wait until the daemon is stopped, and the browser is the way to manage accounts while it serves. The static shell is served to anyone who connects, exactly as nginx serves it in the compose variant; every byte of knowledge still comes through the JSON API, which answers `401` to a request that carries no identity.

Who may fill that form in is decided by the connection itself, never by anything a request can claim. A caller on the machine that serves the instance is trusted on the strength of its loopback peer address and is asked for nothing more. A bind anyone else can reach cannot be, so a `serve` that binds anything but loopback (`0.0.0.0`, a LAN address, the container default) mints a one-time setup token for that process and prints it as it starts, on the same startup banner as the rest of its startup lines, for as long as the instance has no account yet. Read it wherever that banner goes: the terminal for a `serve` you typed, `docker logs` for a container and `journalctl -u crystalline` under systemd (both of those run `serve` in the foreground and collect what it prints), or the daemon log for a daemon running in the background. To choose the token yourself, set `CRYSTALLINE_SETUP_TOKEN` (or `CRYSTALLINE_SETUP_TOKEN_FILE` for a Docker secret) to at least 32 characters; the daemon then prints only which variable it uses. The form asks for the token only when the server says it is required, so a loopback user never sees the field, and a remote one pastes in the printed value. The token belongs to that one serve process: restart the daemon and the next one prints a fresh token, unless you set one with `CRYSTALLINE_SETUP_TOKEN`. That lasts until the first admin exists. After that the form is gone for good, so there is nothing left for a token to open and a restart prints none.

The same rule has a caveat worth knowing before a proxy goes in front. A request carrying `X-Forwarded-For`, `Forwarded` or the other forwarding headers is never counted as local, even when the proxy that sent it runs on this very machine, since a loopback peer with proxy headers is a reverse proxy relaying somebody remote. So the wizard behind a proxy asks for a token, and a daemon bound to loopback has none to give. Create the first admin before you put a proxy in front of the daemon, or bind a network address so that `serve` prints a token to paste.

The `Host` allow-list guards the JSON API as well as the MCP endpoint, so the name people open the UI at needs an entry in it, just like the name agents use. `http://localhost:7411` works with nothing configured. To open `http://server.lan:7411`, put `server.lan` in `CRYSTALLINE_SERVICE_ALLOWED_HOSTS` (see [Configure through environment variables](#configure-through-environment-variables)); the host of `service.public_url` is allowed without an entry. Without it the page loads, but every API call is answered `403` with a detail that names the setting. The check stops a web page that points its own name at your machine (DNS rebinding) from using the API, for example to create the first admin on an instance that has no account yet. The GitHub App's webhook is not checked, because each delivery carries a signature a web page cannot make.

Serve it over TLS anywhere but localhost. The session cookie is marked `Secure` for any browser `Host` that is not loopback, so a browser on a plain `http://team.lan` is handed a cookie it refuses to store and signing in never sticks. Put a TLS terminator in front of the daemon; it has to forward the `Host` header verbatim, leave `Origin` alone, pass WebSocket upgrades through for `/api/v1/collab/` or the editor runs solo-only, and accept a request body at least as large as the daemon does - an nginx terminator here carries the same 1 MiB default as the compose config and needs the same `client_max_body_size` raised to match, 10 MiB for the API in general, 15 MiB for the MCP endpoint and the remote tool route (`/api/v1/ctl`), which both carry a file an agent uploads as base64, 64 MiB for the two archive paths (`/api/v1/domains/*/archive/preview` and `.../import`), which carry a whole domain rather than one document, and 25 MiB for the GitHub App's webhook (`/api/v1/github/webhook`), the most GitHub sends in one delivery. [Team server with Fluid](#team-server-with-fluid) spells out the full proxy requirements, and they are the same here.

The web UI keeps one stream open per browser, `GET /api/v1/events`, a server-sent event stream that tells the page what changed so it refetches in place. All tabs of a browser share that one stream, so any number of tabs work over plain HTTP/1.1, where a browser allows only six connections per host; an HTTP/2 proxy (Caddy, or nginx with `http2` on a TLS listener) lifts that per-host limit altogether. A reverse proxy in front of the daemon must not buffer the stream, or the page hears nothing until the buffer fills. The daemon sends `X-Accel-Buffering: no` on the response, which a default nginx honors in proxy mode; add `proxy_buffering off;` to the `location /api/` block all the same, for a configuration that strips upstream headers. Caddy flushes `text/event-stream` responses as they arrive; `flush_interval -1` inside `reverse_proxy { ... }` is the same safeguard there. The stream starts with a comment (`: open`) that is sent with the headers, so a proxy or a dev server that holds the headers back until the first body bytes still opens it at once. It then carries a comment every fifteen seconds, so a read timeout of a minute or more never cuts it (the bundled template's `proxy_read_timeout 120s` is fine).

Read-only and anonymous serving need no extra parts either. `--read-only` refuses every write inside the API while the UI, which is GETs, is served in full and renders itself read-only from its own capability probe; `auth.anonymous: true` answers identityless requests at viewer level. The two together are the published archive anyone who can reach the port may browse without signing in at all, with no nginx anywhere in it (see [Read-only deployments](#read-only-deployments)).

With `update.check` on, an admin sees a small chip in the avatar menu when the server found a newer stable release, for example "0.35.0 available". It opens a note with both versions, the release notes and the command to run on the server, `crystalline update now`. Editors, viewers, anonymous readers and agent tokens never see it. The update check runs on the server, never in the browser, and the note is read with the same probe the page already makes. Fluid does not update anything itself.

A binary built without the bundle says so rather than pretending: the startup line reads `web UI not built into this binary`, and a navigation gets a `503` page naming `pnpm --dir fluid build` while the JSON API and MCP carry on unaffected. That is the state of a clone built without node, or of a `--no-default-features` build; every release binary carries the bundle, and so does the container image, which repackages the same binary. One combination is unsupported on such a build: OAuth for MCP clients needs the consent page, which lives in the bundle, so set `auth.oauth: false` there. It is otherwise derived on wherever `auth.mcp` is on and `service.ui` has not been turned off, and a start in that state prints a warning naming the key - nothing is granted, but a client that tries to connect is sent to a consent page that is not there.

## Team server with Fluid

The scale-out variant. The daemon serves the UI itself now ([Web UI from the daemon](#web-ui-from-the-daemon)), so reach for this shape when the front door deserves a tier of its own: nginx replicas that scale independently of the daemon, gzip on the wire, one obvious place to terminate TLS, and an upgrade decoupling where the UI image can move ahead of the daemon (which is why Fluid tells a browser when the two versions have drifted apart). It is the team server with a browser tier in front of it. `deploy/fluid/docker-compose.yml` runs two containers on one network: the same Crystalline daemon as above, and Fluid, the web UI, as an nginx image (`ghcr.io/jordiboehme/crystalline-fluid`) that serves a static bundle on port 80 and forwards `/api/` to the daemon. Agents keep reading and writing over MCP, each signing in with its own token (the compose file sets `CRYSTALLINE_AUTH_MCP=true`, see [An account per agent](#an-account-per-agent)); people get the same knowledge as pages they can browse, search, link to and read side by side with what an agent was taught. Crystalline stores what was learned; Fluid is where you think with it.

```mermaid
flowchart LR
    B[Browser] -->|HTTP :80| F[Fluid, nginx]
    F --> S[Static bundle]
    F -->|/api to crystalline:7411| D[Daemon]
    A[Agent] -->|MCP over HTTP| D
    D -->|bind mount| K[Knowledge files]
    D -->|volume| I[Index]
```

Fluid forwards the browser's `Host` to the daemon, and the daemon answers the JSON API only for a `Host` on its allow-list (see [Web UI from the daemon](#web-ui-from-the-daemon)). `http://localhost` works as it is. Any other name people open Fluid at, a LAN name or a public host name, goes into `CRYSTALLINE_SERVICE_ALLOWED_HOSTS` on the crystalline service, or into `CRYSTALLINE_SERVICE_PUBLIC_URL`, whose host is always allowed. The image also refuses to be framed by another site: every app route, the OAuth consent page included, carries `Content-Security-Policy: frame-ancestors 'none'` and `X-Frame-Options: DENY`, as the daemon's own UI does.

The bundled nginx config carries its own dedicated location for the collab WebSocket, `/api/v1/collab/`, with the Upgrade and Connection headers the plain `/api/` block does not send. Anyone who replaces the Fluid image's nginx config with their own has to carry that block over, or the upgrade never reaches the daemon and the editor runs solo-only with nothing on screen to explain why. The config also raises `client_max_body_size` to 10 MiB to match the daemon's own limit, and a replacement config that leaves nginx's 1 MiB default in place turns every save and every archive import of a larger engram into a proxy refusal. The archive routes get a second, larger directive of their own, in a regex location matching `^/api/v1/domains/[^/]+/archive`: a domain export is re-imported as one zip with its `assets/` attachments inside it, so those two paths accept 64 MiB where everything else keeps 10 MiB, exactly as the daemon does. A replacement config that carries the server-level directive over but not that location refuses an archive the same deployment produced, which reads on screen like a Fluid bug rather than a proxy one. The remote tool route gets an exact location too, `= /api/v1/ctl` with 15 MiB: a file an agent on a connected machine uploads travels as base64 in that body (13,981,016 bytes for a 10 MiB file), and the daemon takes 15 MiB on that route. A replacement config without it refuses a full-size upload with a proxy error the agent cannot read. That location also waits 180 s for the daemon, longer than the 120 s a connected machine waits for a forwarded call: a shorter proxy timeout cuts off a slow upload. The GitHub App's webhook gets an exact location of its own too, `= /api/v1/github/webhook` with 25 MiB, the most GitHub sends in one delivery and what the daemon takes on that route. A replacement config without it refuses a large delivery, and the access change it carried then waits for the five minute cache. The same template turns proxy buffering off in its `/api/` location, for the change stream the web UI keeps open (see [Web UI from the daemon](#web-ui-from-the-daemon)); a replacement config that leaves buffering on gives a page that never follows a change.

Nothing is readable until an account exists: the JSON API answers `401` to a request that carries no identity. Creating the first admin is the one bootstrap step, and there are three ways to take it. From the host, `users add` writes the accounts database directly (never through the daemon), so a running instance picks the new account up on its next lookup with nothing to restart:

```sh
docker compose -f deploy/fluid/docker-compose.yml up -d

printf '%s' 'the-password' | docker compose -f deploy/fluid/docker-compose.yml \
  exec -T crystalline crystalline users add ada --role admin --password-stdin
```

Or mount the password as a file and pass `--password-file /run/secrets/<name>` instead of `--password-stdin`; one trailing line break is dropped.

Or let the daemon create it at its first start, from the environment. Set `CRYSTALLINE_ADMIN_NAME` and `CRYSTALLINE_ADMIN_PASSWORD_FILE` on the crystalline service, and mount the password as a Docker secret:

```yaml
services:
  crystalline:
    environment:
      CRYSTALLINE_ADMIN_NAME: ada
      CRYSTALLINE_ADMIN_PASSWORD_FILE: /run/secrets/crystalline_admin_password
      CRYSTALLINE_GITHUB_TOKEN_FILE: /run/secrets/crystalline_github_token
      CRYSTALLINE_AUTH_OIDC_CLIENT_SECRET_FILE: /run/secrets/crystalline_oidc_secret
    secrets:
      - crystalline_admin_password
      - crystalline_github_token
      - crystalline_oidc_secret

secrets:
  crystalline_admin_password:
    file: ./admin-password.txt
  crystalline_github_token:
    file: ./github-token.txt
  crystalline_oidc_secret:
    file: ./oidc-client-secret.txt
```

The admin is created at a start only while no account exists. A later start never changes it, and it never brings back an admin you deleted. Once it exists the browser form asks for nothing, because the instance has an account, and the daemon prints no setup token. The plain `CRYSTALLINE_ADMIN_PASSWORD` works too, but it shows up in `docker inspect`, so use the file form. A file loses one trailing line break and nothing else. If the name or the password is missing, or the file cannot be read, or the password is empty, the first start stops with a message that names the variable. It also stops when a variable and its file form are both set, and when the store refuses the name (for example a name with a space in it); the message names the variable and the reason. When an account exists already, the variables are ignored, and a password variable that is still set logs one warning per start so you can remove it.

The GitHub token and the OIDC client secret lines are only needed when you use team domains or single sign-on; leave out what you do not use.

Or take it in the browser instead: open Fluid and an instance with no accounts renders the create-first-admin form ([Web UI from the daemon](#web-ui-from-the-daemon)). The daemon binds `0.0.0.0` inside its container, so that form asks for the one-time setup token the daemon printed when it started, and `docker compose -f deploy/fluid/docker-compose.yml logs crystalline` is where to read it (a restarted daemon prints a new one, until the admin exists and none is printed again). Every route mints the same admin, and each one closes the form for good.

Restart the daemon after upgrading the binary, before editing accounts, so both sides open the accounts database the same way. A container upgrade recreates the container and has this covered already; a native install upgraded underneath a daemon that keeps running does not.

`-T` because `--password-stdin` reads a pipe and compose would otherwise allocate a terminal there is nothing to read from. Everyone else is `--role viewer` or `--role editor`. Two other identity modes need no accounts at all: `CRYSTALLINE_AUTH_ANONYMOUS=true` serves an identityless request at viewer level, which together with `--read-only` is a published archive anyone who can reach it may browse, and `CRYSTALLINE_AUTH_TRUSTED_HEADER=remote-user` takes the already-authenticated user from a header an SSO proxy sets, creating that account at viewer role the first time it is seen. The trusted header is only safe when the proxy sets it itself and strips whatever a client sent, which means that proxy has to sit in front of Fluid rather than behind it: nginx forwards client headers untouched. A proxy that speaks the standard forward-auth quartet has `CRYSTALLINE_AUTH_PROXY_HEADERS=true` instead, on the same terms and with the same warning: see [Proxy forward auth](#proxy-forward-auth). Provisioning is capped by `auth.max_users`, default 100; existing accounts always resolve, and `crystalline users` is never capped.

Those three modes are about the people using Fluid. The agents connecting over HTTP MCP are governed separately, by `auth.mcp`, which is its own scenario with its own token-issuance story and its own consequences for what an authenticated agent may see: see [Authenticated agents](#authenticated-agents).

An admin can also manage domains from Fluid itself: create local, virtual or GitHub team domains, connect GitHub under Administration > GitHub connection in the avatar menu, and download or import a domain as a zip archive. Download archive and Import archive on the domain page are the plain backup and restore story - the zip holds the domain's markdown files (MANIFEST included) and imports through the normal write path, so the index stays in sync.

Serve it over TLS anywhere but localhost. The session cookie is marked `Secure` for any browser `Host` that is not loopback, and for any request a proxy in front reports as `https`, so a browser on a plain `http://team.lan` is handed a cookie it refuses to store and signing in never sticks. Put a TLS terminator in front of the Fluid container and the same deployment works unchanged: Fluid passes an existing `X-Forwarded-Proto` through rather than overwriting it with its own hop.

Any proxy in front of the daemon's HTTP endpoint needs WebSocket upgrade pass-through for `/api/v1/collab/` as well as plain HTTP forwarding: nginx needs `proxy_set_header Upgrade $http_upgrade; proxy_set_header Connection "upgrade";` (the bundled `nginx.conf.template` carries the full block). The Origin header must reach the daemon unmodified, and the Host header must stay the browser-facing host rather than being rewritten to an internal name - the server's same-host Origin check compares the two, and a proxy that breaks either the upgrade or that comparison gets a `403 Forbidden` whose detail names Origin, not the proxy, which is the tell for diagnosing it. Forward the Host header verbatim: in nginx that is `proxy_set_header Host $http_host;` and not `$host`, which drops the port, so a deployment published on any port but the default answers every join with that 403 while the Origin the browser sent carries `:8080`.

Fluid holds no state of its own, so it scales to as many replicas as a deployment wants. Two variables configure the image: `CRYSTALLINE_UPSTREAM`, the daemon's `host:port`, `crystalline:7411` by default, and `CRYSTALLINE_BASE_PATH`, empty by default, which serves the app under a path such as `/crystalline` (see [Under a path](#under-a-path)); the daemon behind it then needs `service.public_url` with the same path. nginx resolves the upstream once, when it loads its configuration, which is why the compose file gates Fluid on the daemon's healthcheck and why a daemon that moves to a new address needs the Fluid container restarted rather than only itself. Reading is what the UI is for: the sidebar lists what this instance knows about, an engram page carries its frontmatter, observations, relations, backlinks and an interactive neighborhood graph, and Cmd+K (Ctrl+K where there is no Cmd key) opens a command palette that jumps to any domain, or to any engram by title, from anywhere in the app.

## Linux server with systemd

The team server shape without a container: the `.deb` ships a systemd unit,
installed disabled, so installing the package never starts anything. Put any
overrides in `/etc/default/crystalline` (bind address, read-only mode, team
domains - the same variables as [Configure through environment
variables](#configure-through-environment-variables)) and turn the service on.
The unit's own `ExecStart` carries no bind address of its own, and it stays
that way in any unit file an operator writes: an agent's `crystalline mcp`
connection can start a daemon of its own on this same machine, and a daemon
that did not read the same configuration would bind loopback while the LAN
endpoint the unit exists for quietly disappears. Exposure belongs to
configuration, not to a flag on one process's command line.

```sh
sudo systemctl enable --now crystalline
```

The unit runs `crystalline serve` in the foreground under a dynamic service
user: the index and socket live in `/var/lib/crystalline`, the model cache in
`/var/cache/crystalline` and the config in `/etc/crystalline/config.yaml`.
HTTP is on at `127.0.0.1:7411` by default, so the unit serves MCP, the JSON
API and the web UI there as installed, and `CRYSTALLINE_SERVICE_HTTP=false`
in `/etc/default/crystalline` closes the endpoint (the file is read after the
unit's own defaults, so a line there wins). Set
`CRYSTALLINE_SERVICE_HTTP=0.0.0.0:7411` there instead to let agents on the
network learn from it, and probe `GET /health` from a load balancer or uptime
monitor without an MCP handshake. That network bind is also the one that makes `serve` print a
one-time setup token for the browser's create-first-admin form ([Web UI from
the daemon](#web-ui-from-the-daemon)), for as long as the instance has no
account; the service user has no terminal, so read it back with
`journalctl -u crystalline`. The sandbox makes the
filesystem read-only outside those directories, so grant each knowledge
folder a write allowance with a drop-in: `sudo systemctl edit crystalline`,
then `ReadWritePaths=/srv/knowledge` under `[Service]`. Check on the daemon
with `systemctl status crystalline` and `journalctl -u crystalline` rather
than `crystalline ctl` (the daemon's socket lives under the service user, out
of reach of a login shell). A tarball install gets the same unit from the
repository at `crates/cli/debian/crystalline.service`, copied to
`/etc/systemd/system/` with ExecStart adjusted to where the binary landed (a
standalone binary is often `/usr/local/bin/crystalline`). Upgrading the
package restarts the service only if it is running; a disabled unit stays
untouched. The shipped unit also carries `RestartPreventExitStatus=3` beside
its `Restart=on-failure`: exit code 3 means another Crystalline instance
already owns the index, which a restart cannot fix, so the unit stays
`failed` there instead of flapping between active and failed where
monitoring cannot see it. Carry that line into a hand-written unit too.

The service runs as its own user and reads its settings from
`/etc/default/crystalline`, not from the config of the person who installed
it, so `crystalline update auto on` in a login shell does not reach it. To
let the service check once a day for a newer release, add
`CRYSTALLINE_UPDATE_CHECK=true` to `/etc/default/crystalline` and run
`sudo systemctl restart crystalline`; `crystalline update auto on` says so
on a machine with the .deb and its unit.

```mermaid
flowchart LR
    M[Uptime monitor] -->|GET /health| D[Daemon under systemd]
    A1[Agent] -->|HTTP :7411| D
```

## Published read-only domains

When a team curates knowledge as a reviewed git repository instead of writing into the container directly, `examples/docker/compose.git-sync.yaml` adds a sidecar that pulls the repository into a shared volume every 60 seconds and mounts it read-only into Crystalline. The compose file also sets `CRYSTALLINE_AUTH_MCP=true`, because read-only stops writes and not reads: each agent signs in with its own token (see [An account per agent](#an-account-per-agent)). The daemon runs with `--read-only`, so the write-gated tools disappear from the MCP tool list (they are named under [Read-only deployments](#read-only-deployments), with the three more that leave the list beside them) and agents can only search and read, while sync, the file watcher and embedding keep following every pull. A team domain connected to a GitHub origin (see [Team knowledge on GitHub](#team-knowledge-on-github)) gets the same effect natively, no sidecar container needed: `update_domain` and `origin_status` stay visible even in read-only mode once `github.enabled` is on (with it off no collaboration tool is listed at all), so a read-only instance keeps a team domain current on its own background poll schedule. A third option needs no mounted config and no sidecar at all: an immutable image started with `CRYSTALLINE_SERVICE_READ_ONLY=true`, `CRYSTALLINE_GITHUB_ENABLED=true`, one or more `CRYSTALLINE_DOMAIN_<NAME>` and `CRYSTALLINE_DOMAIN_<NAME>_ORIGIN` pairs and `CRYSTALLINE_GITHUB_TOKEN` for a headless sign-in bootstraps each team domain itself on first start and keeps it current on the same background poll schedule, with nothing left to mount or edit ever again. See [Read-only deployments](#read-only-deployments) and [Configure through environment variables](#configure-through-environment-variables) for the full behavior and variable list.

```mermaid
flowchart LR
    G[Git repository] -->|pull every 60s| S[Sidecar]
    S --> K[Knowledge files]
    K -->|read only| D[Daemon]
    D -->|HTTP, read and search only| A[Agent]
```

## Air-gapped or egress-restricted

When a host has no outbound network access, or the first-start model download delay is unwanted for any other reason, use the `with-model` image, or set `CRYSTALLINE_MODELS_DIR` on any install to point at a model directory fetched ahead of time, so nothing in the runtime path ever needs the network. This is orthogonal to read access: combine it with either the read-write [team server](#team-server) shape or the read-only git-sync shape, since air-gapping is about the model rather than about who can write. See [Run in a container](#run-in-a-container) for the image variants and `CRYSTALLINE_MODELS_DIR`. The model is fetched at a fixed commit (for the default model `835ad14087e140460703cf0fae09f97d469d65c2`), and `crystalline model download` of the same release writes exactly that snapshot. A directory that holds only another complete snapshot of the same model (a copy fetched earlier, or by another tool) still works: the daemon starts on it with no network call, logs a warning with both commits, and `crystalline doctor` shows the same warning. Such a daemon is the one exception to "never needs the network": once per start it tries to fetch the pinned commit in the background, never blocking the start, and without network access that attempt fails with one log line. Once the pinned commit is there, the next start switches to it when its weights and tokenizer are the same; if they differ, it stays on the older snapshot, because the index would have to be embedded again. After the switch, a writable instance removes the older snapshot from the default model cache only; a `CRYSTALLINE_MODELS_DIR` is your folder and is never cleaned.

The contradiction check is another exception. With `evolve.contradictions` set to anything but `off`, the daemon downloads an NLI checkpoint on its first pass, and no image bundles one. To keep such a host offline, set the same profile once on a machine with network access, let its daemon download the checkpoint into its `CRYSTALLINE_MODELS_DIR`, and copy that directory to the offline host. The checkpoint is fetched at a fixed commit too (`b5113eb38ab63efdd7f280f8c144ea8b13f978ce`), and only that commit is used: unlike the embedding model there is no start on another snapshot, so a copy of any other commit makes the daemon try a download.

```mermaid
flowchart LR
    M[Model] -->|baked into image| D[Daemon]
    D -->|HTTP, no egress| A[Agent]
```

## Embedding model hardware

On a Mac with Apple Silicon the local embedding model runs on the GPU through Metal. Every other platform runs it on the CPU: Linux, Windows, containers and Intel Macs. Intel Macs are left out because the GPU kernels the model needs use matrix instructions only Apple Silicon GPUs have. Nothing needs to be set up for Metal. Crystalline (the daemon, or a CLI command that embeds on its own) opens the GPU, loads the model there and embeds one test text. If any of that fails, it logs one warning with the reason and runs on the CPU, so a Mac without a usable GPU (a virtual machine, for example) works as before. Set `CRYSTALLINE_ACCELERATION=off` to keep the model on the CPU.

The GPU takes the embedding work off the CPU, which matters for a daemon that shares the machine with other work. The results are the same to the last float digits on both devices (in a measurement on real engrams, the cosine between the CPU and the GPU vector of a chunk was never below 0.9999998), so an index embedded partly on the CPU and partly on the GPU needs no re-embedding. The GPU costs some more memory while the model is loaded. The very first start after an install compiles the GPU programs, which can take about 15 seconds once; macOS keeps them, so later starts are fast.

The NLI model of the contradiction check (`evolve.contradictions`) makes the same choice when it loads: Metal when the model loads there and scores one test pair, the CPU otherwise, with the same warning and the same `CRYSTALLINE_ACCELERATION=off` switch. Each model makes this choice on its own, so one can run on the GPU while the other runs on the CPU. Its scores are the same on both devices too (on the parity pairs the contradiction probability differed by less than 0.00001 between GPU and CPU, far away from the threshold of 0.95), so pairs scored on one device need no new scoring on the other. With both models loaded on the GPU the daemon uses more memory than with the embedding model alone.

`crystalline status` shows the device the loaded model runs on now, for example `device: metal`, `device: cpu (fallback: <reason>)`, `device: cpu (metal failed at runtime: <error>)` or `device: cpu (off by CRYSTALLINE_ACCELERATION)`. The contradictions line shows the same for the NLI model while it is loaded; the daemon drops that model after ten idle minutes, and then the line shows no device. `crystalline doctor` shows the same device as `status` under the embeddings block and under the contradictions row when a running daemon answers and has the model loaded. Without that, it shows the device a model load would pick on this machine; it does not load a model for this, so a failure that shows only when a model runs is not part of that answer.

The GPU can also fail later, after the model has loaded and passed its test. Then that model switches to the CPU on its own: Crystalline logs one warning with the model and the error, loads the model again on the CPU and runs the failed request again there. A search whose query was being embedded still answers, and an NLI batch is still scored, so no pairs are parked. The model stays on the CPU until the process ends, also when the daemon loads it again (the NLI model after ten idle minutes, for example), and `crystalline status` shows `device: cpu (metal failed at runtime: <error>)`. Only the model that failed moves; the other one keeps its device unless it fails too. Nothing needs to be set and nothing needs a restart. A restart tries the GPU again; set `CRYSTALLINE_ACCELERATION=off` if it keeps failing on your machine.

```mermaid
flowchart LR
    S[Daemon start] --> Q{Apple Silicon and not off?}
    Q -->|yes| G[Metal: load and test]
    Q -->|no| C[CPU]
    G -->|ok| M[Model on GPU]
    G -->|any error| C
```

## Run on PostgreSQL

Crystalline can keep its durable state in a PostgreSQL database with pgvector instead of in local files. This suits a stateless container or pod that has no volume: a redeploy then keeps every account, session and token, the settings and the domain registry, and the sealed GitHub tokens, App and server sign-ins, so nobody has to sign in or link GitHub again. Use `examples/docker/compose.postgres.yaml` as a start: an immutable image with `CRYSTALLINE_DATABASE_BACKEND=postgres`, `CRYSTALLINE_DATABASE_URL` and `CRYSTALLINE_SECRET_KEY` set, no mounted config.yaml needed. Like the other compose files it sets `CRYSTALLINE_AUTH_MCP=true`, so each agent signs in with its own token (see [An account per agent](#an-account-per-agent)). PostgreSQL 14 or newer is needed.

**One active instance per database.** Exactly one Crystalline instance is active on a database, or on a schema inside it. The active instance holds a session advisory lock in the database. A second `crystalline serve` on the same database does not fail. It waits as a standby, with no time limit, and logs one line about it every minute. Several active instances on one database are not supported. Earlier versions allowed it; if you ran that way, stop every old instance before you start the new version.

**The standby.** A standby answers `GET /health` with 200 and `"role": "standby"`, so a liveness probe stays green. `GET /ready` answers 503, and every other route answers 503 with `Retry-After: 5`. The active instance answers `/health` with `"role": "active"` and `/ready` with 200. `crystalline status` shows the role, the owner and how long the standby has waited.

**Takeover.** The standby tries the lock every two seconds. It takes over at once when the active instance stops gracefully. After a crash the lock comes free at once, and the new owner waits a grace of about 15 seconds before it serves. When the node of the active instance vanished without closing its connections, the server ends the dead session after up to 15 seconds more, and then the same grace follows. The first start on a database that has no owner row yet (an upgrade from 0.32, or an empty schema) waits the same grace once. Before the grace, the new owner ends the sessions of its predecessor in the database. For that it must use the same database role as the predecessor, or have the `pg_signal_backend` role. A predecessor that runs as a superuser can only be ended by an instance that uses the same role or is a superuser itself. When the grant is missing, the start stops with a message that names it.

**Fencing.** The active instance checks every few seconds that it still holds the lock. When it has lost it, for example after a network break, it stops writing and exits with code 4. That is the fenced exit. Under systemd, `Restart=on-failure` starts it again, and it comes back as a standby. Exit code 3 means that the daemon found its state folder held by another process, and the shipped unit does not restart on it, so it does not flap. The compose policy `restart: unless-stopped` restarts on exit 3 too, so a container whose state folder is held tries again after each restart. A second `serve` instance on the same database never exits 3: it waits as a standby. A transaction-mode connection pooler cannot hold a session lock, so with one the owner fences itself and restarts in a loop. Connect directly, or through a pooler in session mode.

**Accounts live in the database.** Accounts, sessions, MCP tokens, OAuth clients and grants are stored in Postgres. `web-auth.db` is not used there. A file that an earlier run left behind is not read; the start logs one warning about it. Nothing is imported from it: the accounts start empty, every client signs in once, and the first admin comes from `CRYSTALLINE_ADMIN_NAME` with `CRYSTALLINE_ADMIN_PASSWORD_FILE`, or from the setup token the daemon prints (see [Team server with Fluid](#team-server-with-fluid)).

**Secrets are sealed in the database.** The GitHub tokens of the instance and of each person, a saved GitHub App and the sign-ins to connected Crystalline servers are stored in the table `instance_secret`, one row each. Each row is encrypted with XChaCha20-Poly1305 under a 32 byte key that you supply in `CRYSTALLINE_SECRET_KEY`, or in a file named by `CRYSTALLINE_SECRET_KEY_FILE`. Make a key with `openssl rand -base64 32` (64 hex characters work too) and keep it safe and apart from the database backups: without it the sealed secrets cannot be read. A lost key means deleting the old rows (`DELETE FROM instance_secret`, or `DELETE FROM team_a.instance_secret` with `database.schema` set to `team_a`), because a start stops while rows of another key remain, then saving the App and linking GitHub again. There is no key rotation yet. The key is required on Postgres. A `serve` without it does not start, and the message names the variable. The keychain and the state folder are never used for secrets there, so nothing falls back to a local file. Each row records the id of the key that sealed it (the first 16 hex characters of its SHA-256). When the database holds rows sealed with another key, the start stops and names both ids, and the rows are kept as they are. Run commands that change a secret inside the active instance (`kubectl exec <pod> -- crystalline ...`), where the key is set. There `connect github`, `connect <url>`, `disconnect <name>` and `github app set` and `remove` seal or delete the secret themselves on a connection of their own, then tell the daemon, which reads it again from the database. The secret never goes over the control socket. `users add`, `users disable` and `users remove` ask the daemon to delete the token. A key that does not match the sealed rows is refused before anything is written, and both key ids are named. Only the daemon that owns the database is asked: a daemon of the same machine that serves another database (a Turso one, or another schema) is passed by. Without such a daemon, a command needs the key too. It takes the database for its run when no instance owns it, and it is refused before it writes anything while another instance owns it or when the key is missing. Server sign-ins are the exception: `connect <url>` and `disconnect <name>` are made in the pod only, where the daemon keeps `sources.json` and the vault together, and they are refused elsewhere with the `kubectl exec` example. An `origin` command without a daemon checks for the key before its first write as well. Token files, an App file and server sign-in files that an earlier run left in the state folder are not read, and the start warns about them: people link GitHub again once. Turso ignores the key, with one warning at the start.

**Settings and domains live in the database.** The settings and the domain registry are one document in the table `instance_config`. Only the active instance writes it. `config.yaml` is optional. When it exists, it is a read-only base under the document. The order is: flags, then environment variables, then the document, then `config.yaml`, then the defaults. Settings merge key by key: a key in the document overrides the same key in `config.yaml`, and keys the document does not hold come from `config.yaml`. Domains merge by name, and a document entry replaces the whole entry of the same name from `config.yaml`. A redeploy with an empty disk keeps all of it. Nothing is imported: a setting or a domain you saved in `config.yaml` stays visible as the base, and a change saved there later is not copied into the document. A running instance reads `config.yaml` once, at its start, so a change saved there applies at the next start.

These rules follow from that:

- A domain that `config.yaml` registers cannot be removed, purged or renamed on Postgres. Edit `config.yaml` for that. Its settings can still be changed, and the change goes into the document.
- The `database` block is never stored in the document. `crystalline config set database.url` and the other `database.*` keys write `config.yaml` and need no owner. That is how you point a laptop away from a database that another instance owns.
- The bind address, the base path and the label of the owner row come from the environment or `config.yaml`. The instance reads them before it takes over, and so before it reads the document. `crystalline config set service.http` is refused, and so is a `service.public_url` whose path differs from the path that the environment or `config.yaml` gives (for example `https://kb.example/crystalline` when they give none): a different path saved in the document would apply to only part of the server. Set them with `CRYSTALLINE_SERVICE_HTTP` and `CRYSTALLINE_SERVICE_PUBLIC_URL` or in `config.yaml`. A `service.public_url` with the same path can be saved in the document; the label of the owner row still comes from the environment or `config.yaml`. `service.allowed_hosts` and `service.read_only` do apply from the document, because the instance reads them after the takeover.
- `service.read_only` makes the instance refuse knowledge writes. It does not lock the settings: `crystalline config set`, `config unset` and `provision allow` or `deny` still work from the command line, so `crystalline config unset service.read_only` takes a saved value out again. The change applies at the next start.
- Every other `config set` and `config unset` needs the owner. Run the command inside the active instance (`exec`), or on a free database, where the command claims the database for its run. A save that ended with an unknown result ("the save may have been stored") is read again before it is reported.
- `crystalline config show`, `status`, `domain list`, `doctor` and `provision status` read the document without taking the lock, so they work while another instance owns the database.
- A secret you set with `crystalline config set`, for example an OIDC client secret, is stored in the document as plain text, as `config.yaml` does today. Use the environment variables to keep secrets out of the database.
- One database has one registry. Two machines cannot register the same domain name for different folders.
- A document the instance cannot read stops the start, and the commands that need it are refused. This happens when the stored body was changed by hand, or after a downgrade to a version that reads a setting with another type. To recover, keep a copy of the body (`SELECT body FROM instance_config`), then empty it with `UPDATE instance_config SET body = '{}' WHERE id = 1` or remove the row with `DELETE FROM instance_config`. With `database.schema` set, name the table in that schema, for example `team_a.instance_config`. The instance then starts on `config.yaml` and the defaults. The settings and domains of the old document are gone until you set them again.

**Schemas.** `CRYSTALLINE_DATABASE_SCHEMA` (`database.schema`) names the schema an instance uses. One instance owns one schema. Teams that must not share an owner use one schema each, or one database each. Set the schema with this variable and not with `options` in the URL. When both name a schema, this variable wins: every connection sets its search path to it right after it connects, over a `search_path` from the URL `options` or a role default. Those two only take effect when the variable is unset, and the owner lock does not see them, so two instances that differ only there count as one instance: one owns the database and the other waits. To share knowledge between instances, use a team domain on GitHub (see [Team knowledge on GitHub](#team-knowledge-on-github)) or connect to another server (see [A local Crystalline with domains from shared servers](#a-local-crystalline-with-domains-from-shared-servers)).

**Connections.** An active instance opens up to eleven connections: up to four in the write pool, up to four for reads, one for the accounts, one that holds the lock and one for the configuration document and the sealed secrets, plus one short probe at start. A command in the pod that seals a secret beside the daemon opens one more short connection of its own while it writes. A standby uses one. Size `max_connections` of the server for the instances that can be active or standby at the same time.

**Commands.** While an instance owns the database, run commands inside that instance. In Kubernetes use `kubectl exec <pod> -- crystalline ...`, with compose use `docker compose exec crystalline crystalline ...`. A command on another machine that would open the database is refused, and the message names the owner. The same holds for a daemon that a client starts on its own and for `crystalline mcp --embedded`: they refuse and never wait. On a free database a command takes the lock for as long as it runs and gives it back when it ends. `crystalline users` and `crystalline members` may write the accounts beside the owner. Reports such as `crystalline status` never take the lock or open the store on Postgres. They read the owner row and say who owns it.

**Diagnostics.** The start logs one "durable state" line with the database, the schema, where the accounts live, when the configuration document was last saved, which `config.yaml` is read as the base, the id of the secret key with the number of sealed secrets, and where the GitHub App comes from (`env`, `vault` or `none`). It never names a sealed secret. An earlier info line, written when the vault is installed, names the same key id and row count. When `config.yaml` registers domains, another info line names them. Credential files that an earlier run left in the state folder (`origins/github-token*.json`, `origins/github-app.json`, `origins/github-app.present` and the `credential.json` of each connected server under `remote/`) get one warning: they are not read while Postgres is configured. Only their names are looked at. `crystalline status` and `crystalline doctor` show an "ownership and durable state" block. It says whether a secret key is set for the command and how many sealed secrets the database holds, never a key id or a row name, and a missing key fails neither. It also says where the GitHub App comes from. A command without the vault only knows an App from the environment, so otherwise it says "not checked (a saved App would be sealed in the database)". App variables that do not make a usable App are reported as an error of the environment. The block repeats the warning about leftover credential files. `crystalline doctor --fix` is refused while another machine owns the database.

**File domains.** The files of a domain stay on the disk of the instance that serves them. The index in Postgres is built from those files, so keep the knowledge folder on a volume or restore it from its Git remote, and a lost index is rebuilt with `crystalline reindex --full`. The engrams of a virtual domain live only in the database, so back it up or export it with `crystalline domain export`.

```mermaid
flowchart LR
    A[Agents and browsers] --> LB[Service or load balancer]
    LB -->|/ready 200| ACT[Active instance]
    LB -.->|/ready 503| SB[Standby instance]
    ACT -->|holds the session lock| PG[(PostgreSQL + pgvector)]
    SB -.->|tries the lock every 2 s| PG
    PG --- ST[Accounts, sessions, tokens, settings, sealed secrets, index]
```

## Team knowledge on GitHub

For a team that keeps a domain in a GitHub repository instead of a shared filesystem or database, each repository (optionally a subfolder of one) becomes a team domain, with an origin recording which repository, subfolder and branch it tracks. Members connect once with a short code confirmed in a browser they are already signed into: no git, no SSH keys and no token to paste for someone who only knows the GitHub web UI. Crystalline shares new knowledge as a proposal the team reviews and merges on GitHub itself, or commits it straight to the branch on a domain whose MANIFEST says `sharing: direct`, and brings each team domain up to date automatically in the background once its proposals merge; a genuine disagreement between local and team knowledge surfaces as a conflict, settled locally. A fleet of worker or agent hosts can join the same team domain with no interactive connect step at all: three environment variables - `CRYSTALLINE_DOMAIN_<NAME>`, `CRYSTALLINE_DOMAIN_<NAME>_ORIGIN` and `CRYSTALLINE_GITHUB_TOKEN` - register the domain, attach its origin and supply this machine's GitHub identity, so a new node bootstraps the domain itself and starts polling for updates on first start. See [Share knowledge with a team](teams.md#share-knowledge-with-a-team) for the full verb set and the one-time connect flow, and [Configure through environment variables](#configure-through-environment-variables) for the fleet variant.

A team server can also reach GitHub through a GitHub App of its own, and then who may use each team domain follows the repository on GitHub. See [Team server with a GitHub App](#team-server-with-a-github-app).

## Team server with a GitHub App

A team server can reach GitHub through a GitHub App of its own instead of one person's sign-in. The App reads, pulls and shares every team domain with a short-lived installation token for its repository. Who may use each team domain then follows the repository on GitHub: a person links their GitHub account once, and their role on the repository decides what they may do with the domain here. [Access that follows GitHub](teams.md#access-that-follows-github) describes the rules; this section is about setting it up.

```mermaid
flowchart LR
    P[Person in Fluid] -->|signs in, links GitHub once| S[Team server]
    A[Agent over MCP] --> S
    S -->|installation token: pull, share| R[(GitHub repository)]
    S -->|who may read and write| R
    R -.->|signed webhook: access changed| S
    S --> K[Team domain files and Reflection]
```

**Set it up.**

1. Set `service.public_url` to the address people and GitHub use to reach the server, and turn on collaboration with `crystalline config set github.enabled true`.
2. As an admin, open Administration > GitHub connection in Fluid (the avatar menu) and press Create GitHub App, optionally with the organization that should own it (empty is your own account). Crystalline hands GitHub a manifest with the name `Crystalline <host>`, the callback URL, the four permissions below and, when GitHub can reach `service.public_url`, the webhook. You confirm on GitHub, GitHub sends you back, and Crystalline stores the App. A `service.public_url` on a loopback or private address, on a host name without a dot (such as `kb`), or on a host name under `.local`, `.lan`, `.internal`, `.home.arpa` or `.localhost`, gets an App without a webhook; access changes then take up to five minutes.
3. Press Install on repositories and choose the repositories of your team domains. Install it only where it is needed: see [the installation token's reach](security.md#a-github-app-and-its-tokens).
4. In the App's settings on GitHub, enable Device Flow, so people can link GitHub from a terminal as well. A manifest cannot switch it on.
5. Connect each team domain and say who may read it: `shared` (everyone signed in) or `private` (only people with access to the repository on GitHub). Fluid's connect dialog, `crystalline domain add <name> --origin <owner>/<repo> --readers shared|private` and MCP `add_domain` with `readers` all ask; nothing is defaulted.
6. Each person links their GitHub account from their profile in Fluid (see below).

The Create button is only there while no App is configured. To create a new App, remove the old one first with `crystalline github app remove`. Creating needs `service.public_url`, an admin session and a writable instance. The state handed to GitHub works once, for the browser session that asked, within an hour.

**Save an App from the CLI.** For a server without a browser, save an App you created on GitHub with `crystalline github app set --app-id <id> --client-id <id> --private-key-file <path>`, plus `--client-secret-file <path>` and `--webhook-secret-file <path>` when the App has those secrets. The private key and the secrets are read from files and never from the command line. `set` asks GitHub first whether it accepts the key and refuses an App that GitHub knows under another id. When the keychain cannot be read, `crystalline github app remove` still deletes the file copy and the marker (see [Where credentials and tokens are kept](#where-credentials-and-tokens-are-kept)), so origin operations run again, and says when an App saved in the keychain may remain; run it again once the keychain is unlocked. This is also the way out of a stale marker, for example after the keychain item was deleted by hand. Without a marker an unreadable keychain changes nothing: `origin status` and `doctor` read as on an instance without an App. `crystalline github app status` shows the App (its source, id, client id and slug, which secrets are set, the accounts it is installed on), `crystalline github app remove` deletes it, and a running daemon picks up either change at once. The `configure` tool reports the same App read only.

**Check it.** `crystalline doctor` checks the App: the key parses, GitHub accepts the signed token, the App has the four permissions it needs, the installations can be listed, this machine's clock is within a minute of GitHub's, and a webhook secret is set when `service.public_url` is. A missing permission is named, with the hint to change it in the App's settings on GitHub. GitHub then asks the owner of each installation to accept the new permissions, and the change only works there after that. When a daemon runs, doctor also names each closed domain, the time since GitHub last answered, and a `github.agent_identity` that names an instance admin.

**Linking a person's GitHub account.** With a GitHub App, each signed-in person can link their own GitHub account from their profile in Fluid, viewers included. This uses the App's web flow, so it needs two things: `service.public_url`, and the App's client secret (`--client-secret-file` on `crystalline github app set`, or `CRYSTALLINE_GITHUB_APP_CLIENT_SECRET`; an App created from Fluid has it). In the GitHub App's settings, add `<service.public_url>/api/v1/github/link/callback` as a callback URL, spelled exactly like `service.public_url`. Without `service.public_url` or without the client secret, starting a link answers 409 and names what is missing. The link is bound to the browser session that started it: GitHub sends the browser back to the callback, the session cookie comes with it, and a callback from any other session is refused: nothing is exchanged, and the browser lands on the profile with a sentence that says to connect again. A browser that lost its session on the way lands on the sign-in page and comes back to the profile. The state is good for one callback and ten minutes. A person can also start from an agent session: MCP `configure` with `connect: "github"` answers a single-use link (`<service.public_url>/api/v1/github/link/go?n=...`) that the agent relays, and the person opens it in a browser signed in as the same account, which goes on into the same flow. The link works once within ten minutes, a browser without a session is sent to the sign-in page and back (its single sign-on button comes back too), and a link opened by another account is refused, so a forwarded link never links someone else's GitHub account. Links are kept in the server's memory: a link opened after a restart is not valid any more, and the person asks the agent for a new one. Unlinking revokes the person's token at GitHub; when GitHub cannot be reached the link is still removed here and the answer says to revoke the token in the GitHub settings. An admin can unlink any account with `DELETE /api/v1/users/{name}/github-link`, for example to free a GitHub account that was linked to the wrong Crystalline account.

### Use an existing GitHub App

For infrastructure as code, supply the App through the environment instead of creating it in Fluid: `CRYSTALLINE_GITHUB_APP_ID`, `CRYSTALLINE_GITHUB_APP_CLIENT_ID` and `CRYSTALLINE_GITHUB_APP_PRIVATE_KEY` (all three required together), plus `CRYSTALLINE_GITHUB_APP_CLIENT_SECRET` for linking in the browser and `CRYSTALLINE_GITHUB_APP_WEBHOOK_SECRET` for the webhook. The private key and the two secrets have `_FILE` forms (`CRYSTALLINE_GITHUB_APP_PRIVATE_KEY_FILE` and so on), which suit a Docker or Kubernetes secret mounted as a file. See [Configure through environment variables](#configure-through-environment-variables) for each variable.

The variables win over an App saved in the keychain or on disk. While they are set, `crystalline github app set` and `remove` refuse, and Fluid shows the App without the Create button. Nothing from them is written to `config.yaml` or to the state folder.

Check the App's settings on GitHub once:

- Callback URL: `<service.public_url>/api/v1/github/link/callback`, spelled exactly like `service.public_url`.
- Device Flow: enabled, for linking from a terminal.
- Webhook: active, URL `<service.public_url>/api/v1/github/webhook`, with the same secret as `CRYSTALLINE_GITHUB_APP_WEBHOOK_SECRET`.
- Repository permissions: Contents read and write, Pull requests read and write, Metadata read.
- Organization permissions: Members read.
- Events: Member, Membership, Organization, Repository and Team. GitHub sends installation events to every App without a subscription.
- Setup URL (optional): `<service.public_url>/api/v1/github/app/setup`, which brings you back to the GitHub connection page in Fluid after an install.
- Request user authorization (OAuth) during installation: off. Crystalline links people through its own flow.

`crystalline doctor` warns when one of the four permissions is missing.

### Where credentials and tokens are kept

- **The App** (its id, client id, private key and secrets), when created in Fluid or saved with `github app set`: in the OS keychain, as the item `github-app` (or `github-app:<host>` for an Enterprise Server). A keychain save also writes `github-app.present` into the origin state folder (`origins/` in the state folder). It holds only the host, so a keychain that later cannot be read refuses origin operations instead of falling back to the instance sign-in. Without a working keychain (a container, a server without a desktop session) the App goes to `origins/github-app.json`, readable by this user only (mode `0600`).
- **An App from the environment** stays in the environment. It is never written anywhere.
- **Installation tokens** are never stored. They live in the daemon's memory, are renewed five minutes before they expire, and are gone on a restart.
- **People's tokens** (the user token of each GitHub link and its refresh token) live in the token store, like the instance's own GitHub token: in the keychain, or without one in `origins/github-token-personal-<name>.json`, readable by this user only.
- **The link records** (which account is linked to which GitHub id and login) live with the accounts: in `web-auth.db` in the state folder, or in the database on [PostgreSQL](#run-on-postgresql).
- **On PostgreSQL** the App, the instance token, the people's tokens and the sign-ins to connected Crystalline servers are not kept in the keychain or the state folder. Each is one row of the table `instance_secret`, sealed with the key in `CRYSTALLINE_SECRET_KEY` (see [Run on PostgreSQL](#run-on-postgresql)). No `github-app.present` marker and no token file is written there, and a file that an earlier run left behind is not read. The start, `status` and `doctor` name such files in a warning, so you can move them away. An App or a token from the environment still wins over a sealed row.

See [What Crystalline writes](security.md#what-crystalline-writes) for the state folder of each platform.

**Keep the origin state folder.** `origins/` holds, for each domain connected through the App, the ids of its repository and of the owner (see [Access that follows GitHub](teams.md#access-that-follows-github)), and without a keychain also the App and the people's tokens. In a container it is under the `/data` volume (`/data/state/crystalline/origins`). Keep that volume across restarts and upgrades. Without a keychain, a lost folder means the App is saved again and every person links GitHub again. And a domain whose repository was transferred on GitHub in the meantime is not noticed, because its recorded ids are gone. On PostgreSQL the App and the tokens are in the database, so a lost folder costs only the recorded ids.

### Webhooks

With a webhook, a change of who may read a repository takes effect within seconds. Without one, the five minute cache decides. GitHub delivers the events to `POST /api/v1/github/webhook`, signed with the App's webhook secret. The route needs no sign-in, so an authenticating proxy in front of the server must let that one path through: see [Proxy forward auth](#proxy-forward-auth). [Security](security.md#a-github-app-and-its-tokens) says how a delivery is checked.

### GitHub Enterprise Server

Set `github.api_url` to `https://<host>/api/v3`. Every App call goes there, and the browser steps (creating the App, installing it, linking people, the device flow) go to `https://<host>`. Notes:

- Support for an Enterprise Server was tested against a simulated server, not against a real one. Please report what you find.
- Creating the App from Fluid needs Enterprise Server 3.0 or later; with an older server the error names its version. Then create the App on the server by hand and save it with `crystalline github app set` or the environment.
- An App saved for github.com is not used against an Enterprise Server address, and the other way round.
- Commits name a linked person by `<id>+<login>@users.noreply.<host>`. GitHub documents this address form for github.com only, so it may not link to the profile on your server.
- An older server that does not say whether a repository is internal makes Crystalline read an internal repository as private.

## Reflection on a team server

A domain shared through GitHub keeps its [Reflection](reflection.md), its documents for people, on one home instance: the team server whose `service.public_url` is the domain's `reflection_home`. That key is filled in when Reflection is switched on at the team server, so switch it on there and not on a laptop. Switching it off turns `reflections/` into ordinary engram content, which "share changes" then offers, so do not share changes while it is off. To move the home, switch it off and on again at the new home in one go and share the MANIFEST change at once; the old home stops when it pulls that change (see [One home, one backup](reflection.md#one-home-one-backup)). Every other instance that holds the domain answers `this domain's Reflection lives at <url>`, and people and agents work on the Reflection at the home.

On PostgreSQL only the active instance serves a Reflection (see [Run on PostgreSQL](#run-on-postgresql)). A standby serves nothing until it takes over. After a takeover the new owner serves the Reflection from its own disk, so it needs the domain folder (see [One home, one backup](reflection.md#one-home-one-backup)).

The home backs the whole `reflections/` folder up to the branch `crystalline/reflections` of the domain's repository. The branch never carries an engram, and sharing engram changes never carries a file under `reflections/`. A runner can work the Reflection's queue on its own, against the home: see [Loop runners](#loop-runners), and [Restore from the backup](reflection.md#restore-from-the-backup) for the way back.

```mermaid
flowchart LR
    people[People, through their agents, the files or the JSON API] -->|edit, comment| home[Team server: the home instance]
    agents[Agents over MCP] -->|reflect, write_reflection, discuss| home
    cron[Scheduled agent run] -->|reflect| home
    home -->|share changes: engrams| main[(GitHub: tracked branch)]
    home -->|backup: reflections/| backup[(GitHub: crystalline/reflections)]
    laptop[A laptop subscribed to the domain] -.->|points to the home| home
```

## Loop runners

The reflect loop and the evolve loop can run without a person starting an agent. Crystalline never starts a program: a runner outside it asks whether work is due, takes a lease, runs a headless agent, shares what the agent changed as a pull request and records the run. With nothing due it ends at once. The full guide is [Run the loops on their own](automation.md).

A runner is one of these:

- `crystalline reflect run` or `crystalline evolve run` from cron, a systemd timer or a CI schedule. It needs Claude Code on the same machine.
- `crystalline reflect watch` as a long-running process: a systemd unit, a login item or one replica in a cluster. It checks the status every minute and runs when something is due.
- A Kubernetes CronJob or a GitHub Actions job in remote mode: `CRYSTALLINE_REMOTE_URL` and `CRYSTALLINE_REMOTE_TOKEN` point it at the team server, with the `cmt_` token of an agent account. [`examples/kubernetes/`](../examples/kubernetes/) has the runner image and the manifests, [`examples/github/`](../examples/github/) the workflow.
- An n8n workflow that calls the same steps through the ctl route and runs its own AI Agent with the MCP Client Tool ([`examples/n8n/`](../examples/n8n/)).

The reflect loop runs against the domain's Reflection home. The evolve loop on a team domain runs against its evolve home, the instance whose `service.public_url` is the MANIFEST's `evolve_home`; the first scheduled evolve run at an instance with an address fills it in (see [One evolve runner per team domain](teams.md#one-evolve-runner-per-team-domain)). On PostgreSQL only the active instance runs it (see [Run on PostgreSQL](#run-on-postgresql)); a standby runs nothing until it takes over. An evolve runner can also be an instance of its own that joins the team domain from its GitHub origin with `CRYSTALLINE_DOMAIN_<NAME>`, `CRYSTALLINE_DOMAIN_<NAME>_ORIGIN` and `CRYSTALLINE_GITHUB_TOKEN`, runs and ends; give it a fixed `CRYSTALLINE_SERVICE_PUBLIC_URL`, so it can be the evolve home. A runner that reaches the server by a name people do not use needs that name in the server's `CRYSTALLINE_SERVICE_ALLOWED_HOSTS`.

A domain can also ask its instance to send a signed webhook when work becomes due (`reflect_trigger: webhook`, `evolve_trigger: webhook`), so a runner such as n8n starts without polling. The webhook URL and its secret are instance settings: `automation.webhook.url` and `automation.webhook.secret`.

```mermaid
flowchart LR
    S[Scheduler: CronJob, GitHub Actions, n8n, cron] -->|start| R[Runner]
    W[watch process] --> R
    R -->|status, lease, share, record: ctl route| D[Team server]
    D -.->|signed webhook when work is due| S
    R -->|starts| A[Headless agent]
    A -->|MCP over HTTP with the token| D
    D -->|the run's changes as a pull request| G[(GitHub)]
```

## Run in a container

Crystalline publishes a multi-arch OCI image (`linux/amd64` and `linux/arm64`) to GHCR on every release, for Linux server deployments. macOS and Windows have no OCI container runtime worth targeting here, so those platforms run the native binary (see [Get started](../README.md#get-started) in the README); the container covers the Linux server case.

Two image variants ship under the same name, tag-selected:

| Tag | Size | Embedding model | Best for |
|---|---|---|---|
| `latest` (or a pinned `vX.Y.Z`) | ~15 MB | Downloads in the background on first daemon start (needs egress to huggingface.co once) | The common case: a host with normal internet access, where a short model download on first start is fine |
| `with-model` (or a pinned `vX.Y.Z-with-model`) | ~235 MB | Baked into the image, no download | Air-gapped or otherwise offline hosts, or anywhere semantic search must work from the very first `search` call with no warm-up delay |

Pick `with-model` whenever the host has no outbound network access or the first-start download delay is unwanted; pick the slim `latest` otherwise, since it is the smaller image to pull and update.

A Raspberry Pi 5 is a fine `arm64` host for either variant: the daemon holds about 390 MB of model weights once loaded, an 8 GB board carries the idle daemon and a bulk re-embed of a corpus in the ten-thousand-engram class with room to spare, and a 4 GB board carries the idle daemon comfortably and that same bulk embed with little else running, so the 8 GB board is the one to pick for a corpus that size; a laptop or a desktop notices none of this.

```sh
docker pull ghcr.io/jordiboehme/crystalline:latest
# or: docker pull ghcr.io/jordiboehme/crystalline:with-model

docker run -d \
  --name crystalline \
  -p 7411:7411 \
  -v "$(pwd)/knowledge:/knowledge" \
  -v crystalline-data:/data \
  ghcr.io/jordiboehme/crystalline:latest
```

That one published port carries the browser too: the image serves the web UI built in, so `open http://localhost:7411` lands on Fluid while agents keep speaking MCP to the same address (see [Web UI from the daemon](#web-ui-from-the-daemon) for accounts, TLS and the two toggles). A fresh container has no accounts, so that first visit renders the create-first-admin form. The container binds `0.0.0.0`, which is not loopback, so the form asks for the one-time setup token the daemon prints as it starts: `docker logs crystalline` is where to read it, and a restarted container prints a new one until that first admin exists. To choose the token yourself, set `CRYSTALLINE_SETUP_TOKEN` (or `CRYSTALLINE_SETUP_TOKEN_FILE` for a Docker secret) to at least 32 characters; the daemon then prints only which variable it uses. To skip the form, set `CRYSTALLINE_ADMIN_NAME` and `CRYSTALLINE_ADMIN_PASSWORD_FILE` and the container creates the admin at its first start (see [Team server with Fluid](#team-server-with-fluid)).

What persists where:

- `./knowledge` (bind mount) holds the engrams of every file domain, one subfolder per domain - the durable state for file-backed knowledge, exactly the same markdown-plus-frontmatter files the native binary reads.
- `crystalline-data` (named volume, mounted at `/data`) holds the search index and the embedding model cache. For file domains those two are fully rebuildable: losing them costs a `crystalline reindex --full` (a lost volume leaves no index to destroy, so the ordinary rebuild does the whole job; the `--wipe` recovery path is for a database that is still there and will not open) and a model re-download (skipped entirely on `with-model`, since its model lives outside `/data` and is never affected by the volume), never knowledge. Four things on this volume are not rebuildable, though. If you run virtual domains, their engrams are the source of truth and live here, so back this volume up or `crystalline domain export` them to the bind mount to keep a file copy, or download the domain as a zip from Fluid's domain page (admin). `web-auth.db` holds the JSON API's accounts and sessions, which are data rather than derived state: losing it means creating every user again with `crystalline users add`. On [PostgreSQL](#run-on-postgresql) the accounts live in the database instead and this file is not used. And for a domain in [review mode](teams.md#review-mode), every actor's private drafts are journaled under the daemon's state directory on this same volume rather than in the bind-mounted folder - they are unshared knowledge that exists nowhere else, so losing this volume loses them too, not merely an index to rebuild. With a [GitHub App](#team-server-with-a-github-app), the origin state under `/data/state/crystalline/origins` holds the App, the people's GitHub tokens (a container has no keychain) and the recorded ids of each connected repository: losing it means saving the App and linking every person again. On [PostgreSQL](#run-on-postgresql) the App and the tokens are sealed in the database instead.

Local domains created from Fluid land under the server's domains root, which defaults to `~/Documents/Crystalline` in the daemon's home; in a container set `CRYSTALLINE_DOMAINS_ROOT` to a persistent path (a bind mount, or a folder under the `/data` volume such as `/data/domains`) so UI-created domains survive the container.

The maintenance pending state lives in the daemon's state directory, so a containerized daemon paired with a host-side Stop hook never arms the pending ask: the two processes see different state directories, and the domains one records a human writing to are not the ones the other reads before it nudges. The hook still asks on its weekly arm, from its own clock on the host.

The per-prompt recall hook has the same split: it looks for the daemon's socket in the host's state directory, finds none beside a containerized daemon and stays silent.

The image runs as the non-root user `65532:65532` and ships `/data` owned by it, so an empty named volume mounted there is writable from the first start: Docker copies the image directory's ownership into the volume when it initializes it. A bind mount never inherits that - the host directory keeps its own ownership - so a host folder mounted at `/data` instead of a named volume has to be made writable by that uid first, or the daemon cannot create its state directory and the container restarts in a loop:

```sh
mkdir -p ./crystalline-data
sudo chown 65532:65532 ./crystalline-data
```

The same applies to the bind-mounted knowledge folder whenever the daemon writes into it (an agent's `write_engram`, or the generated `index.md` files), which includes the case where `docker run` creates a missing bind-mount source itself: Docker creates it root-owned. A named volume put in that folder's place is no different, because the ownership Docker copies into a fresh volume is the mount point's in the image and the image ships no `/knowledge`: it comes up root-owned exactly like a bind-mount source Docker created, so give it to the daemon's uid once - `docker run --rm -v crystalline-knowledge:/knowledge alpine chown -R 65532:65532 /knowledge`, from an image that has a shell, since Crystalline's is distroless - before `domain init` writes anything into it. A knowledge folder mounted read-only, as in `compose.git-sync.yaml`, needs nothing.

The `with-model` variant sets `CRYSTALLINE_MODELS_DIR` (also settable directly, on any install, to relocate the model cache anywhere else) to a path outside `/data` so the baked model is never shadowed by the `/data` volume mount. The bundled model is [ibm-granite/granite-embedding-97m-multilingual-r2](https://huggingface.co/ibm-granite/granite-embedding-97m-multilingual-r2), Apache-2.0 licensed. The image bundles no NLI checkpoint: a profile other than `off` for `evolve.contradictions` downloads one into `CRYSTALLINE_MODELS_DIR` on the first pass, so that directory must be writable then, or hold the checkpoint already (see [Air-gapped or egress-restricted](#air-gapped-or-egress-restricted)).

A daemon prunes the model directories its configured embedding model does not use right after that model loads, but only among the models Crystalline itself can download; a directory for anything else in `CRYSTALLINE_MODELS_DIR` is never touched. The models Crystalline can download include the NLI checkpoints of the contradiction check: the daemon keeps the one the `evolve.contradictions` profile uses and removes the others, all of them while the setting is `off`, even when another Hugging Face tool put them there. So a shared cache is safe to point Crystalline at, with two exceptions. Another tool's copy of one of those NLI checkpoints is removed. And two daemons sharing one host's `CRYSTALLINE_MODELS_DIR` but configured with different `embeddings.model` values would each delete the other's weights and re-download them on every start, because both models are ones Crystalline knows; give such hosts separate `CRYSTALLINE_MODELS_DIR` values. A read-only instance never prunes, and neither does one configured for a remote embedding provider.

Both variants ship a built-in Docker `HEALTHCHECK` that probes `GET /health` with no shell involved (the image is distroless), so `docker ps` reports health directly and a Compose service can gate on `condition: service_healthy`. External monitors (a Kubernetes `httpGet` probe, an uptime checker such as Gatus, a load balancer) can probe the same `/health` endpoint directly rather than going through Docker's own health state. `/health` answers with a `role` field: `active` for a normal instance, `standby` for an instance that waits for a PostgreSQL database another instance owns (see [Run on PostgreSQL](#run-on-postgresql)). A standby is alive, so `/health` stays 200 for it. `GET /ready` answers 200 once the instance serves requests and 503 for a standby, so use `/ready` to decide where traffic goes.

On Kubernetes, run one replica with the `Recreate` strategy. A `RollingUpdate` starts the new pod before it stops the old one, and the new pod then waits as a standby that is never ready, so the rollout never finishes. Probe `/health` for liveness and `/ready` for readiness:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: crystalline
spec:
  replicas: 1
  strategy:
    type: Recreate
  selector:
    matchLabels:
      app: crystalline
  template:
    metadata:
      labels:
        app: crystalline
    spec:
      containers:
        - name: crystalline
          image: ghcr.io/jordiboehme/crystalline:latest
          ports:
            - containerPort: 7411
          env:
            - name: CRYSTALLINE_SERVICE_HTTP
              value: "0.0.0.0:7411"
            - name: CRYSTALLINE_AUTH_MCP
              value: "true"
            - name: CRYSTALLINE_DATABASE_BACKEND
              value: postgres
            - name: CRYSTALLINE_DATABASE_URL
              valueFrom:
                secretKeyRef:
                  name: crystalline-db
                  key: url
            - name: CRYSTALLINE_SECRET_KEY
              valueFrom:
                secretKeyRef:
                  name: crystalline-db
                  key: secret-key
          livenessProbe:
            httpGet:
              path: /health
              port: 7411
          readinessProbe:
            httpGet:
              path: /ready
              port: 7411
```

The secret `crystalline-db` holds the database URL and the secret key, for example `kubectl create secret generic crystalline-db --from-literal=url=postgres://... --from-literal=secret-key="$(openssl rand -base64 32)"`. Run commands in the pod, for example `kubectl exec deploy/crystalline -- crystalline users add agent-build --role editor --mcp-token build`.

Sample Compose files ship under [`examples/docker/`](../examples/docker/), and the one deployment that is meant to be run rather than read from under [`deploy/`](../deploy/):

- **`compose.yaml`** - the single-container setup above, plus a commented one-shot `domain init` / `domain add` recipe for bootstrapping a fresh domain (`domain add` indexes it immediately, routed to the running daemon over the shared `/data` volume).
- **`compose.git-sync.yaml`** - a scale-deployment variant that adds a sidecar keeping the knowledge folder synced from a git remote every 60 seconds, mounted read-only into Crystalline. This is the pattern for a team that manages engrams as a reviewed git repository rather than writing into the container directly.
- **`compose.postgres.yaml`** - the [Run on PostgreSQL](#run-on-postgresql) setup: a Postgres service with pgvector plus one Crystalline instance pointed at it via environment variables, and a commented standby that waits for the first one and takes over when it stops. Reach for it when a container has no volume and must keep its accounts and sessions over a redeploy.
- **`deploy/fluid/docker-compose.yml`** - the [Team server with Fluid](#team-server-with-fluid) setup: the daemon plus the browser UI on port 80, with the first-admin bootstrap in a comment. It can build the Fluid image locally (`docker compose build fluid`) as well as pull it.

All four set `CRYSTALLINE_AUTH_MCP=true`, so every agent that connects over HTTP signs in with a personal MCP token (see [Authenticated agents](#authenticated-agents)). Give an agent its own account and token with `docker compose -f <file> exec crystalline crystalline users add agent-build --role editor --mcp-token build`; the token is printed once. Without the setting, anyone who can reach the published port is served with no sign-in at all. The `docker run` line above does not set it, so add `-e CRYSTALLINE_AUTH_MCP=true` there for any host other people can reach. A daemon that binds an address other machines can reach while `auth.mcp` is off logs a warning at every start that says so.

### Configure through environment variables

An immutable image with no `config.yaml` to mount or edit configures purely through the environment: every settings key maps mechanically to `CRYSTALLINE_` plus the key uppercased with dots replaced by underscores (`github.enabled` becomes `CRYSTALLINE_GITHUB_ENABLED`), plus a handful of variables covering what has no settings-registry key of its own:

| Variable | Maps to | Notes |
|---|---|---|
| `CRYSTALLINE_SERVICE_READ_ONLY` | `service.read_only` | `serve --read-only` still forces it on |
| `CRYSTALLINE_SERVICE_HTTP` | `service.http` | the HTTP endpoint carrying MCP, the JSON API and the web UI: on at `127.0.0.1:7411` by default, `false` turns it off, `true` spells the default out, or give it a `host:port` to bind instead. `serve --http` wins over it, `serve --http off` closes it - but only for that one invocation, and a `serve` whose flag disagrees with this value says so at startup |
| `CRYSTALLINE_SERVICE_UI` | `service.ui` | `true` (default) serves the embedded Fluid web UI on the HTTP endpoint; `false` serves the JSON API and MCP only, the shape a separate Fluid deployment fronts. Read once when the HTTP surface starts, like `service.read_only` |
| `CRYSTALLINE_SERVICE_API` | `service.api` | `true` (default) serves the JSON API under `/api/v1`; `false` leaves MCP and `GET /health` alone on the port and disables the web UI with it, since a UI without its API is a shell that can only render a login error. Read once when the HTTP surface starts, like `service.read_only` |
| `CRYSTALLINE_SERVICE_ALLOWED_HOSTS` | `service.allowed_hosts` | comma-separated `Host` allow-list for the MCP endpoint and the JSON API (the GitHub App's webhook excepted); loopback and the host of `service.public_url` are always allowed and a single `*` allows any Host; `serve --allowed-host` wins over it. A browser `Origin` on an MCP request has to name one of the same hosts, over `http` or `https`; a request without `Origin` is not affected. **With `auth.oauth` in effect this key does a second job**: a derived origin - what both well-known documents publish and what an authorization records as a grant's audience - is named only for a `Host` on this list, and a request arriving at any other is answered `403` rather than handed a document naming it. An `auth.oidc.redirect_uri` override is exempt, being the operator's own answer to what this instance is called. See [MCP clients over OAuth](#mcp-clients-over-oauth) |
| `CRYSTALLINE_SERVICE_PUBLIC_URL` | `service.public_url` | the address people open the Fluid web UI at, for example `https://knowledge.example.com`: an absolute `http` or `https` url with no query or fragment, used verbatim as the base of every `web_url` the tools hand back and as the OAuth resource identifier. A path such as `https://example.com/crystalline` serves the whole server under it (see [Under a path](#under-a-path)): each segment uses lower-case letters, digits, `.`, `_` and `-`, a trailing slash is dropped, and a first segment the server answers at itself (`api`, `assets`, `health`, `.well-known`, a page of the web UI) is refused. Unset (default) derives the address per caller - from the request's `Host` and forwarded scheme for an HTTP client, from the bound port as loopback for a local one - and a caller it cannot be derived for gets a `web_url_note` instead of a link, saying the operator sets the address with the crystalline CLI. An instance served over plain `http` on a non-loopback address still derives an `https` address it does not serve, so set this key there. Set it where a proxy rewrites the `Host`, in a container whose outside port is not its inside port, or where a separate Fluid deployment fronts an API-only daemon. `0.0.0.0` and `::` are refused: a bind wildcard is not an address. Setting the key through `crystalline config set` refuses a value that cannot work, so the mistake is caught while somebody is reading; a value that cannot work arriving through this variable or hand-edited into `config.yaml` is ignored instead, with one startup warning naming the key, the value and the reason, and the address falls back to being derived per caller. Read once when the HTTP surface starts, like `service.read_only` |

| `CRYSTALLINE_SETUP_TOKEN` | the first-run setup token | sets the one-time token the create-first-admin form asks for on a bind that is not loopback, instead of the one `serve` mints. At least 32 characters, or `serve` refuses to start. Never printed or logged; `serve` prints only which variable it came from. It stops working once the first admin exists |
| `CRYSTALLINE_SETUP_TOKEN_FILE` | a path to a file holding that token | the file form of the variable above |
| `CRYSTALLINE_MODELS_DIR` | the model cache path | pre-existing, unchanged |
| `CRYSTALLINE_ACCELERATION` | n/a (environment only) | `off` keeps the local embedding model and the contradiction check's NLI model on the CPU on an Apple Silicon Mac, where they otherwise run on the GPU through Metal. Any other value, and no value, leaves the GPU on. Has no effect on other platforms, which always use the CPU. Read when the model loads. A model that fails on the GPU after it loaded moves to the CPU on its own, without this switch. See [Embedding model hardware](#embedding-model-hardware) |
| `CRYSTALLINE_CHANNEL` | install channel marker | `desktop` when the launcher of the Claude Desktop extension that `crystalline install claude-desktop` builds starts the installed binary, `mcpb` from the Claude Desktop only bundle; it changes what the degraded status server tells the user to update, and with `desktop` it also lets the bridge check the launcher version (`CRYSTALLINE_LAUNCHER_VERSION`). Not meant to be set by hand |
| `CRYSTALLINE_BINARY` | n/a (set by the extension) | the crystalline the extension runs first, written by `crystalline install claude-desktop`; the launcher drops it before it starts `crystalline mcp`. Not meant to be set by hand |
| `CRYSTALLINE_LAUNCHER_VERSION` | Claude Desktop launcher version | set by the Claude Desktop extension's launcher to its own version; the bridge uses it to tell the agent when the extension is too old. Not meant to be set by hand |
| `RUST_LOG` | n/a (not a Crystalline setting) | the log filter, in the tracing `EnvFilter` syntax: a level (`debug`) or per-crate directives (`crystalline_engine=debug,warn`); the daemon's own crates are `crystalline_service`, `crystalline_engine`, `crystalline_rest` and `crystalline_identity`. Unset means `info` for `serve`, with the model download crates (`xet`) at `warn`, and `warn` for `crystalline mcp` and every other command. Logs always go to stderr, never to stdout, and a lifecycle hook (`crystalline hook ...`) logs only when this is set. How long the periodic jobs (the reflect count, embed and evolve ticks, and the origin poll of each domain), each GitHub access lookup (repository, outcome) and each `automation_status` and `automation_overview` call took is logged under the target `crystalline_engine::timing`: at `info` when it took 1 second or more, at `debug` always, so `RUST_LOG=info,xet=warn,crystalline_engine::timing=debug` shows every pass |

These eleven variables have a file form: `CRYSTALLINE_AUTH_OIDC_CLIENT_SECRET_FILE`, `CRYSTALLINE_AUTOMATION_WEBHOOK_SECRET_FILE`, `CRYSTALLINE_GITHUB_TOKEN_FILE`, `CRYSTALLINE_GITHUB_APP_CLIENT_SECRET_FILE`, `CRYSTALLINE_GITHUB_APP_PRIVATE_KEY_FILE`, `CRYSTALLINE_GITHUB_APP_WEBHOOK_SECRET_FILE`, `CRYSTALLINE_REMOTE_TOKEN_FILE`, `CRYSTALLINE_SETUP_TOKEN_FILE`, `CRYSTALLINE_ADMIN_NAME_FILE`, `CRYSTALLINE_ADMIN_PASSWORD_FILE` and `CRYSTALLINE_SECRET_KEY_FILE`. `CRYSTALLINE_DATABASE_URL` has none, so a database password still sits in that variable or in `config.yaml`. Point a file form at a Docker secret (`/run/secrets/<name>`) so the value never shows up in `docker inspect`. The rules are the same for all of them: an empty value counts as unset, the file loses one trailing line break and nothing else, and the start stops with a message naming the variable when both forms are set, the file cannot be read or the file holds nothing after that line break. The secret key is the one exception: a key never holds a space, so its file loses all surrounding whitespace.

`<NAME>` in a domain variable is lowercased with underscores turned into hyphens for the domain name itself (`CRYSTALLINE_DOMAIN_TEAM_KNOWLEDGE` becomes the domain `team-knowledge`). The three suffixes are read before the name is, so a `<NAME>` ending in `_ORIGIN`, `_REVIEW` or `_READERS` names no domain: `CRYSTALLINE_DOMAIN_CODE_REVIEW` is review mode for a domain called `code`, never a domain called `code-review`, and a domain that wants one of those words at the end of its name is registered in `config.yaml` instead. A suffix variable naming a domain no `CRYSTALLINE_DOMAIN_<NAME>` defines refuses at startup naming both variables, so a node never comes up believing it attached an origin or turned review on somewhere it did not. Precedence, highest first: a command-line flag, then an environment variable, then `config.yaml`, then the built-in default; an environment value is never written back to the config file.

Review mode adds nothing else to this surface: no new transport, no new `serve` flag and no separate image variant. It is exactly the `CRYSTALLINE_DOMAIN_<NAME>_REVIEW` row above (or the equivalent `review: overlay` key in `config.yaml`) plus the `crystalline domain review` CLI verb and its REST counterpart, both already gated by the same roles as every other domain-admin action. See [Review mode](teams.md#review-mode) for what it does to reads, writes and sharing.

## Private domains

Every domain starts shared: every account on the instance may read it, following the roles [Team server with Fluid](#team-server-with-fluid) describes. A domain may instead be made private - visible to its owner, the accounts invited into it and instance admins, and to nobody else. A private domain a caller cannot see answers exactly as a domain nobody registered: absent from the domain list, absent from search, "not registered" when named directly. There is no way to tell "private" apart from "does not exist" from the outside, which is the point.

**Membership levels**, from least to most: viewer (read and search, nothing more), editor (everything a viewer may do, plus writing and editing its engrams), manager (everything an editor may do, plus inviting, removing and re-leveling members, including other managers). The owner sits above all three: only the owner of a private domain, or an instance admin, changes its visibility, transfers it or removes it, so a manager may fill a domain with people but cannot re-share it, hand it to someone else or delete it. A shared domain has no owner, so only an instance admin removes one; privatizing an existing shared domain is admin-only too, even for the account about to own it.

**Instance admins always see and administer every domain**, private ones included - the same rule a GitHub organization owner already knows about its repositories. And whoever holds the machine administers every domain too, invited or not: the CLI runs on the host that already holds the domain's files and the accounts database beside them, so a permission check there would protect nothing that is not already open to whoever is sitting at that terminal. Private domains protect an account from other accounts, never from whoever operates the machine.

Manage membership from Fluid's Members card on the domain, or from the CLI:

- **`crystalline domain members <domain> list`** - who owns the domain and who is invited, with each member's level.
- **`crystalline domain members <domain> add <user> [--level viewer|editor|manager]`** - invite an account, or move one to a different level. Defaults to viewer.
- **`crystalline domain members <domain> remove <user>`** - end a membership. The owner holds no membership row of its own; hand the domain to someone else with `domain transfer` instead.
- **`crystalline domain members <domain> reflection add <user> --level reader|contributor`** and **`... reflection remove <user>`** - give an account the Reflection of this one domain, or take it away, on a shared or a private domain. See [Who may do what](reflection.md#who-may-do-what).
- **`crystalline domain visibility <domain> private --owner <account>`** - close a shared domain, naming who owns it from here.
- **`crystalline domain visibility <domain> default`** - share it with every account again; this forgets who was invited.
- **`crystalline domain transfer <domain> <new-owner>`** - hand a private domain to a different account. The old owner keeps nothing; invite them back if they should stay.
- **`crystalline domain add <name> <path> --private --owner <account>`** - register a domain already private, owned by the account named, in one step.

Every one of these writes the accounts database directly from the host, the same way `crystalline users` does, so each works whether or not a daemon is running.

### Invite links

An invite link brings a person in without anyone typing their login name first. It is shown once, to copy and hand over yourself; Crystalline never mails it. The token sits in the part of the address after `#`, so it never reaches an access log or a `Referer` header.

**Who makes one.** An instance admin makes links for any instance role below admin (`none`, `viewer` or `editor`; `viewer` when none is given), with or without a private domain to join and a level there, and may mark a link as a local-account link (it may create an account with a password where single sign-on or a proxy would otherwise be the only way in). With `auth.invites.managers` on (off by default), the owner or a manager of a private domain may make links too, only to that domain: such a link gives instance role `none` and a level there not above their own. No link reaches a shared domain or one whose access follows GitHub.

**What holds.** A link lives 7 days unless its maker picks 1 to 30 days, and it is single use and revocable. An admin holds at most 50 pending links at once, an owner or manager 10. Every pending link counts against `auth.max_users` like an account, so a link is refused once the accounts and the pending links reach the cap. A link is built from `service.public_url` and keeps its path, `https://kb.example.com/crystalline/invite#cin_...`; without `public_url` the server answers the path alone and Fluid completes it with the address the browser is on.

**Taking a link.** Opening a link shows a page that names who made it, the domain and the level, and asks the person to accept; nothing is redeemed by opening it, so a link preview in a chat cannot use it up. The page reads the token from the address and asks `POST /api/v1/invites/confirm` with the token in the body, which answers what the link gives and which sign-in this instance offers: `local` (a login name and a password made here), `oidc` (see [Enterprise SSO](#enterprise-sso)) or `proxy` (see [Proxy forward auth](#proxy-forward-auth)), plus whether a local account may be made. A local account with a password is made only where `local` is the offer or an admin made the link a local-account link, so an invite never walks around the identity provider. Accepting is `POST /api/v1/invites/redeem`: with a login name and a password it makes the account, at the link's role, and signs it in; a person who is signed in already redeems for their own account. Redeeming is one transaction: the link is marked used only while it is unused, unrevoked and unexpired, the account is made or found, and the membership is written. An existing account keeps its own role and gets the membership only, raised and never lowered, and no account is ever found by its address. What the link gives is checked again at that moment: its maker is still an enabled account, still an admin where the link needs one (any role but `none`, a local-account link, a link without a domain), still the owner or a manager of the domain at the link's level, `auth.invites.managers` is still on for a link an owner or a manager made, and the domain is still private and not governed by GitHub. A new account counts against `auth.max_users` here too. The confirm route answers one sentence, "This invite link is not valid any more.", for a link that is unknown, used, revoked, expired or no longer allowed, so it cannot be used to find out which; the redeem route says which once the token matched a link. Both routes count wrong tokens per address on the login throttle (`auth.login.*`); behind a reverse proxy every person shares the proxy's address there. A read-only instance answers confirm and refuses redeem. Every redemption is logged at INFO with the account, the link, whether the account was made, the domain and the level.

**The routes.** `POST /api/v1/invites` makes a link and answers its token and address once. `GET /api/v1/invites` lists links without their tokens, filtered with `state=pending|used|revoked|expired`: every link for an admin, the caller's own for anyone else. `DELETE /api/v1/invites/{id}` revokes an unused link: an admin any, its maker their own. A read-only instance refuses both changes and still serves the list. Every link made and revoked is logged at INFO with who did it.

## Authenticated agents

`auth.mcp` (or `CRYSTALLINE_AUTH_MCP=true`) decides whether an HTTP MCP connection has to authenticate, separately from the three modes above that govern people in a browser. Off (the default) is the legacy open tier: any client that can reach the port is served, with no account behind the connection. On, every one of them presents a personal MCP token exactly like a human user, as `Authorization: Bearer cmt_...`, and a request without a valid one is answered `401` before the transport sees it, so the session never opens. The `WWW-Authenticate` challenge in that `401` is a bare `Bearer` while this instance serves no OAuth, and carries `resource_metadata="<origin>/.well-known/oauth-protected-resource"` where it does - which an unset `auth.oauth` makes the default on any instance that serves the UI, so the recipe in [MCP clients over OAuth](#mcp-clients-over-oauth) is the shape most shared instances answer with. One case reads like the first even where OAuth is on: a request whose `Host` is not on `service.allowed_hosts` gets the bare `Bearer`, since the address it named is not one this instance will publish as a resource - and the transport refuses that same request `403` a moment later anyway. Every rejected credential gets the identical answer, so nothing about the response says which token exists or why it failed. Local stdio clients are unaffected either way, since those are the machine's owner; turn this on for any instance reachable beyond a trusted network. A daemon that binds a non-loopback address with `auth.mcp` off says so in a warning at every start, and the compose files under `examples/docker/` and `deploy/` turn it on. A hosted client that speaks OAuth needs no token pasted at all: see [MCP clients over OAuth](#mcp-clients-over-oauth).

**Issuing a token.** A signed-in user issues one for themselves in Fluid, under profile > Agent access. From the host that holds the accounts database, an admin issues one for any account instead: `crystalline users mcp-token <name>` (`--label <text>` names what it is for; `--list` shows the tokens an account already holds without ever printing one back, `--rotate <id>` replaces one keeping its label, `--revoke <id>` stops one at once). Either way the token is shown exactly once, at issuance - only its hash is stored, so a lost one is revoked and replaced rather than looked up. Both routes stay open on a read-only instance, which is the one place this API serves a write under `service.read_only`: a token is account state rather than knowledge, and an agent there cannot connect at all without one.

**Registering a harness against it.** However a harness spells a custom header for a remote MCP server, name `Authorization` carrying the printed token:

```json
{
  "mcpServers": {
    "crystalline": {
      "type": "http",
      "url": "https://team.example.com/",
      "headers": {
        "Authorization": "Bearer cmt_xxxxxxxxxxxxxxxxxxxxxxxxxxxx"
      }
    }
  }
}
```

That is the shape most remote-server-capable MCP clients use for a custom header; consult the harness's own docs for its exact spelling. Each request carries the header, not just the handshake: a session belongs to the account that opened it, and another account naming it - even with a valid token of its own - is answered `403` without being told whose session it is.

**What an authenticated agent may see.** It acts as its account: it reads the domains that account may read, its writes are refused where that account is only a viewer - of the instance, or of a private domain it was invited into as one - and a private domain it is not a member of is answered exactly as a domain nobody registered: absent from `list_domains`, absent from search, "not registered" when named (see [Private domains](#private-domains)). With `auth.mcp` off there is no account to be, so every agent on the open tier is the anonymous tier: it reads and writes what is shared and sees no private domain at all. On an instance where nobody has made a domain private, both tiers behave exactly as they always did. Every write an authenticated agent makes carries who it acted as in the engram's own provenance, unless `identity.actor` is set: `generated.by` records `<client>-for-<account>` - the MCP client's own name and the account it authenticated as, joined by the word `for` (a client calling itself `claude-code/2.0`, authenticated as `ada`, lands `claude-code/2.0-for-ada`) - so a later reader can tell which person's session made a given write. `identity.actor`, where configured, overrides this and every other actor string with its own fixed value (see the `CRYSTALLINE_IDENTITY_ACTOR` row above).

**Write-result nudges.** Every write, edit, move, delete or split answers with a short trailer of its own once in a while: a `---` rule followed by at most one line starting `[crystalline] `, asking the agent to propose sharing unshared work, to run maintenance or to work a Reflection's queue with `reflect` - the same standing practice a Stop hook teaches, reaching here the one kind of session a hook can never nudge at its end. It is throttled per authenticated identity, at most once every four hours per nudge kind, so two agents working as different accounts are nudged on their own independent clocks; with `auth.mcp` off there is no identity to key it by and the whole instance shares one cooldown instead. A client parsing the receipt text as structured data should cut at the `---` rule rather than trying to parse the trailer itself, since that rule is the one boundary this server guarantees never appears inside the written content.

**What an authenticated agent may change about the instance itself.** Registering a domain (`add_domain`), changing settings (`configure` with `set`, `unset` or a connect, never an operator setting, which is refused for every caller) and deciding what a domain installs into this machine's harnesses (`provision` with `allow`, `deny` or `apply`) are instance-state changes, and with `auth.mcp` on they need the instance admin role, exactly as the same actions do over the JSON API. An agent authenticated as a viewer or an editor is refused with a message naming the role and the way to ask for the change; reading the settings back with a bare `configure`, or the decisions back with `provision` `status`, is a read and stays open to everyone (a bare `configure` shows only the settings an agent may change; the network, the database and sign-in are operator settings that only `crystalline config` shows and changes; `provision` `status` names only domains the caller may see). `configure` with a `domain` is about that domain rather than the instance: it lists the domain's MANIFEST policy keys (`sharing` and `generated_indexes`), its sections and its `.crystalline.yaml` rule overrides (`rules.<ID>` set to `off`, `error`, `warning` or `info`, plus `token_budget`), and with `set` and `unset` it changes the policy keys and the rule overrides. The domain's owner or an instance admin may change them; with `auth.mcp` off, the open tier may change them wherever it may edit the MANIFEST with `edit_engram`, which excludes a domain in review mode. A domain in review mode takes a policy change as a draft and refuses a rule override, since `.crystalline.yaml` is not an engram. A virtual domain has no `.crystalline.yaml`. Comments in `.crystalline.yaml` are not kept when `configure` writes it. `token_budget` must be a positive whole number, and 0 is refused. Two rules read it: verify's `Q002` and the evolve sweep's `V105`. `rules.Q002: off` turns `Q002` off. A mounted domain, one served by a connected server, is refused rather than forwarded. The change is made on that server. A read-only instance is the exception for `configure`: it is not listed there and refuses every call, a bare one included, since an agent there can act on none of the settings and a public instance would otherwise show its paths and sign-in setup to anonymous readers (see [Read-only deployments](#read-only-deployments)); the operator reads them with `crystalline config show`. Unregistering a domain (`remove_domain`) follows the private-domain rule instead of the admin one, since it is narrower: an instance admin, or the owner of a private domain, and a domain the agent cannot see is answered as one nobody registered. With `auth.mcp` off there is nobody to hold a role, so the open tier keeps exactly the powers it had - `add_domain` and `configure` are served as before - with one exception: `remove_domain` is new and refuses the open tier outright, because ending a domain is not something nobody in particular does. A local stdio session is the machine owner throughout and is never gated here at all.

**One removal is destructive, and every surface refuses it until it is confirmed.** A file or team domain's files are never deleted by a removal, so unregistering one loses nothing: the folder stays and registering it again re-adopts it (a team domain is reconnected with its repository rather than with its folder, which is what keeps its origin). A virtual domain's engrams live in the database and go with it, so the engine refuses that removal unless the request says the loss was intended - `purge: true` on the `remove_domain` tool, `?purge=true` on `DELETE /api/v1/domains/{domain}` (answered `409` without it), and `--purge` on `crystalline domain remove`. Fluid sends it after its own confirmation. The rule is the engine's rather than any one client's, because this route serves a private domain's owner now and not only an admin.

```mermaid
flowchart LR
    A[Agent] -->|Authorization: Bearer cmt_...| G{MCP gate}
    G -->|no token, or an invalid one| R[401 and a Bearer challenge]
    G -->|valid token| S[Session bound to the account]
    S --> D[Daemon: reads and writes as that account]
```

## MCP clients over OAuth

`auth.oauth` turns Crystalline into an OAuth 2.1 authorization server for its own MCP endpoint, so a hosted client - Claude.ai's remote connector first of all - reaches this instance without a person pasting a token into it. The client discovers that the endpoint is protected, registers itself, sends the person to sign in and consent, and from then on holds a credential the MCP gate checks exactly like a personal MCP token from [Authenticated agents](#authenticated-agents). The identity provider is whatever this instance already signs people in with - local accounts, [Enterprise SSO](#enterprise-sso), or [Proxy forward auth](#proxy-forward-auth) - since the consent page is an ordinary signed-in Fluid page: whoever can sign in there can consent.

`auth.oauth` is tri-state, unset by default. Unset, it follows `auth.mcp`: a shared instance where every agent has to authenticate and the UI is served gets OAuth for free, no second switch to flip - see [A shared instance in three steps](#a-shared-instance-in-three-steps) below. Set it `false` (or `CRYSTALLINE_AUTH_OAUTH=false`) to keep issuing personal MCP tokens only, whatever `auth.mcp` says. Set it `true` to insist: it then needs `auth.mcp` on, since the tokens it issues are checked at that gate; `service.api`, since its endpoints live under `/api/v1`; and `service.ui`, since consent happens on a Fluid route - with the UI off, `/authorize` falls to the MCP transport and nobody can ever consent - and the daemon refuses to start against any of the three missing, naming which one. A followed value never trips those refusals, since it only ever turns on where all three already hold. Wherever `auth.oauth` ends up off, the two well-known documents below answer `404`.

**Discovery.** Two documents, mounted at the origin root beside `/health` rather than under `/api/v1`, since the specification places them there: `GET /.well-known/oauth-protected-resource` names this endpoint as a protected resource (its `resource` and the one entry in `authorization_servers`, both the instance's own origin), and `GET /.well-known/oauth-authorization-server` names the three OAuth endpoints below plus what this server supports (authorization code and refresh token grants, PKCE `S256` only, public clients only). A client that shows up with no credential is refused the way [Authenticated agents](#authenticated-agents) already describes, with one addition: the `401`'s `WWW-Authenticate` header carries `resource_metadata` pointing at the protected-resource document, and the teaching text in the body says a client that speaks OAuth can connect without a token at all. Under a path (see [Under a path](#under-a-path)) the two documents are also served at their RFC 9728 and RFC 8414 addresses, `/.well-known/oauth-protected-resource/<path>` and `/.well-known/oauth-authorization-server/<path>` at the host root, which the proxy has to forward, and `resource_metadata` names the first.

**The origin.** Both documents, the challenge above, and every access token's audience all name the same address: this instance's base, its origin (scheme, host, optional port) plus the path of `service.public_url` when it has one (see [Under a path](#under-a-path)). Derived per request from the incoming `Host` by default (an origin with no path, since only `service.public_url` can name a path), the same rule the [Enterprise SSO](#enterprise-sso) callback address uses - and overridden the same way, by `auth.oidc.redirect_uri` when that key is set, since it is the one place an operator behind a Host-rewriting proxy has already named the public address (see that key's row in [the environment table](#configure-through-environment-variables)). A deployment that rewrites `Host` and has not set that key mints tokens for an address nobody outside the machine can reach. Separately, the public host itself has to be on `service.allowed_hosts` (see [Configure through environment variables](#configure-through-environment-variables)): the MCP transport validates the `Host` header and answers `403 Forbidden` for a name it was not told to trust, and a derived origin holds to the same list - the two well-known documents and the authorize leg refuse an unlisted `Host` with their own `403` rather than publishing it, so no client is handed a resource identifier the transport then refuses, and no grant records one. With the list unset (the default) the origin rule narrows nothing, while the transport and the JSON API keep their own default of loopback plus the host of `service.public_url`; a single `*` turns all of them off. A configured `auth.oidc.redirect_uri` is exempt, since it is the operator's answer rather than the request's - but a proxy that forwards the public hostname still needs that hostname listed, because the transport checks it either way. `service.public_url`, when set, is that base (its path included) and outranks the origin of `auth.oidc.redirect_uri`; the redirect uri keeps its own job as the callback address.

**The endpoints**, all under `/api/v1` and public by path - no session or MCP token is needed to reach any of them, since none of them exist yet for a client that has not registered:

| Route | What it is for |
| --- | --- |
| `POST /api/v1/oauth/register` | Dynamic client registration (RFC 7591): a client posts its redirect URIs and gets back a `client_id` (`coc_` plus hex), no secret - only public clients exist here |
| `GET /api/v1/oauth/authorize` | Starts an authorization: validates the client, redirect URI and PKCE challenge, then redirects the browser to the Fluid consent screen |
| `GET /api/v1/oauth/authorizations/{id}` and `POST /api/v1/oauth/authorizations/{id}` | The consent screen's own read and decision, guarded like any other Fluid page - the account making the decision has to be signed in |
| `POST /api/v1/oauth/token` | Turns an authorization code into a token pair, or a refresh token into a fresh one |
| `POST /api/v1/oauth/revoke` | Ends a grant by its access or refresh token (RFC 7009); `crystalline disconnect` calls it. Answers `200` whether or not the token was live |

**Registration is open, and bounded rather than gated.** Anything may call `POST /api/v1/oauth/register`, the way any browser may load a login page: at most 30 registrations per 10 minutes per process, a 64 KiB request body, and at most 1000 stored registrations at once. A registration nobody ever brings to consent is pruned an hour after it was made, so an anonymous caller filling the table costs an operator nothing to wait out; one that has completed at least one consent is pruned only after 30 days with no further use. `client_name` is optional and shown on the consent screen (default "an MCP client" when a client sends none); `client_uri` and `redirect_uris` are the rest of what a client controls about how it is described.

**Starting an authorization is bounded the same way, per registration.** `GET /api/v1/oauth/authorize` carries no credential - it cannot, since there is no account yet at the moment a client sends its person here - so the bound is the `client_id` every request must name, which came from a registration and is therefore already inside the limits above. One registration may have at most 4 authorizations waiting for a decision at once, and past that its next request is answered `temporarily_unavailable` until one of its own is decided, expires, or is 30 seconds old and gives way to the newcomer. A flood therefore fills its own four slots and refuses itself, rather than filling the instance-wide pending map and refusing everyone else's consent. Behind that sits a global cap of 1000 pending authorizations, which the per-registration bound keeps an anonymous caller from reaching, and a ten-minute expiry on any request nobody decides. None of this replaces a rate limit at the proxy: if this instance is on the public internet, give `/api/v1/oauth/` and `/api/v1/auth/login` a limit there like any other unauthenticated endpoint. The login route carries its own per-name delay (see `CRYSTALLINE_AUTH_LOGIN_MAX_DELAY`), which bounds guessing against one account but not one attempt each against many, and a failed sign-in is logged so a tool like fail2ban can read it.

**What the consent screen shows.** The signed-in account's name, the client's name and (when it set one) its own URL, the host its redirect address points at - with a warning when that host is this machine itself rather than a service on the web, which is what a loopback redirect during local development looks like - and how long the request has left before it expires. There is exactly one decision to make: Allow or Deny, for the whole account, until revoked; there are no scopes narrower than that to choose among. The page carries `Content-Security-Policy: frame-ancestors 'none'` and `X-Frame-Options: DENY` like every other Fluid route, from the daemon and from the nginx Fluid image alike, worth naming here because this is the one page in the product where a single click hands a client everything an account can do, exactly the target clickjacking goes after.

**Tokens, lifetimes and rotation.** A successful exchange returns an access token (`coa_` plus hex, one hour) and a refresh token (`cor_` plus hex, thirty days from issue). Every refresh rotates both: the predecessor stops working immediately, and the new refresh token's thirty days start again from that moment - so a client that refreshes regularly never has to send anyone through consent again. A refresh token presented again less than 60 seconds after it was rotated gets a fresh pair of its own, at most twice per rotation, and the pair from the first refresh keeps working too; such a pair is then a session like any other: several sessions of one client that share one stored credential often refresh with the same token at the same moment, and a client that lost an answer retries with the token it still holds. Any later use of a rotated refresh token is treated as a stolen or replayed credential, not an ordinary invalid one: it revokes the whole grant, so the client has to be re-authorized from `/oauth/authorize` like the first time. The same is true inside the 60 seconds for a third presentation of one token, when the token it was rotated into (or a pair minted from it) has itself been rotated already, or when another client presents it. Rotated tokens are remembered for thirty days, however often the grant rotates. The server logs both cases at INFO with the seconds since the rotation (`a refresh token reused inside the grace window got its own pair` and `a replayed refresh token revoked an oauth grant`), never with token material. PKCE with `S256` is mandatory on every authorization; the code it produces is single use and lives 60 seconds, long enough to reach the token endpoint and no longer.

**Connect a hosted client - Claude.ai's connector, as the worked example.** In Claude.ai's connector settings, add a custom connector and paste this instance's origin with no trailing slash (the metadata's `resource` has to equal the address the person typed exactly, and a client that adds a path or a slash where the person didn't will not match it). The connector registers itself against `/oauth/register` on the spot; there is nothing to create by hand first. It then opens this instance's sign-in - whichever of local accounts, single sign-on or a forward-auth proxy this instance is configured with - and lands on the consent screen described above. Allow, and Claude.ai holds a token pair and connects over MCP as that account from then on, refreshing on its own. The connection shows up afterward on the account's own profile, under the Connected clients card next to Agent access - client name, redirect host, when it was granted, when it was last used, and a Revoke button for ending it early, the same place a personal MCP token is issued and revoked. A grant that ended in the last seven days stays listed under Recently ended with one sentence on why: an old sign-in token was used again, it was revoked there, the client signed out, or the password was reset.

**Forward-auth proxies and OAuth are unrelated, and both may run at once.** The consent screen is a browser page like any other, so a forward-auth proxy in front of this instance ([Proxy forward auth](#proxy-forward-auth)) may sign the person in for it exactly as it signs them into everything else; the MCP gate itself never reads `Remote-*` headers, whichever credential opens the session. What the proxy must not do is authenticate the machine-to-machine legs: `/api/v1/oauth/token`, `/api/v1/oauth/register` and both well-known documents are public by path and have to reach this instance unauthenticated. See [Proxy forward auth](#proxy-forward-auth) for the one footgun in getting that wrong.

**Pending authorizations and codes live in memory, not the database.** A daemon restart between the redirect to the consent screen and the code exchange loses the request; the client simply starts over from `/oauth/authorize` (or, in practice, from the person clicking connect again), since it was already going to open a browser. Issued tokens are different: they live in the accounts database beside personal MCP tokens and survive a restart untouched, so an ordinary restart never disconnects an already-authorized client.

```mermaid
flowchart LR
    C[Client] -->|1. connect, no token| G{MCP gate}
    G -->|2. 401 + resource_metadata| C
    C -->|3. GET well-known documents| M[Metadata]
    C -->|4. POST /oauth/register| S[OAuth endpoints]
    C -->|5. GET /oauth/authorize| F[Fluid: sign in, then consent]
    F -->|6. code| C
    C -->|7. POST /oauth/token| S
    S -->|8. coa_... access token| C
    C -->|9. Authorization: Bearer coa_...| G
```

### A shared instance in three steps

This is what following `auth.mcp` buys a [Team server with Fluid](#team-server-with-fluid): nobody sets `auth.oauth` at all, and hosted clients connect anyway.

1. **Create the first admin.** [Team server with Fluid](#team-server-with-fluid) covers the ways to take that bootstrap step - `users add` from the host, the admin variables in the compose file, or the create-first-admin form in Fluid.
2. **Set `auth.mcp` true**, so every agent over HTTP MCP presents a credential instead of connecting on the open tier: see [Authenticated agents](#authenticated-agents).
3. **Nothing.** `auth.oauth` is unset, so it follows: the UI is serving (the default) and every agent now has to authenticate, so OAuth is on. A hosted client such as Claude.ai connects through the sign-in and consent flow above with no token pasted anywhere; a harness that cannot speak OAuth keeps using a personal MCP token from step 2's world, issued in Fluid or with `crystalline users mcp-token`. Either way, whichever human sign-in this instance uses - local accounts, `auth.oidc` for an external provider such as Authelia or Keycloak, or `auth.proxy_headers` - is what the consent page rides on, since it is an ordinary signed-in Fluid page: nothing about OAuth itself asks which one an instance chose.

To keep tokens only on a shared instance, set `auth.oauth: false` and stop there - `auth.mcp` still governs agents, only the OAuth surface is off.

## A local Crystalline with domains from shared servers

Your own domains live on your laptop; your team's live on a shared server, and maybe a second team runs another one. Until 0.23 an agent saw one or the other: the hooks and the CLI only knew the local daemon, and a second MCP registration per server pushed every name collision onto you. `crystalline connect` adds a server as a **source**. From then on your local Crystalline offers its own domains and the domains of every connected server at the same time, through the same local daemon, the one MCP registration and the unchanged hooks.

**Connecting.** `crystalline connect https://crystalline.acme.com` checks that a Crystalline server answers there, then signs in through the server's own OAuth: it registers itself as a public client, opens your browser on the consent page and waits on a loopback port for the answer (PKCE with `S256`, a redirect to `http://127.0.0.1:<port>/callback`). A server without `auth.oauth` asks for a personal MCP token instead, issued in Fluid (profile > Agent access). On a machine without a browser, run `crystalline connect https://crystalline.acme.com --token`. Either way the token is read from stdin or a prompt, never from the command line. Plain `http` is refused unless the server is on this machine. The address keeps its path, so `crystalline connect https://example.com/crystalline` connects to a server under a path (see [Under a path](#under-a-path)), and two servers on one host under two paths are two sources. A backslash, a query or a fragment in the address is refused, and redirects are never followed. Each source gets a short name, the most specific word of its host (`acme` here); `--name` picks another. Connect as many servers as you like; `crystalline disconnect acme` removes one.

**Choosing domains.** A server can offer far more domains than you need. `crystalline connect https://crystalline.acme.com --domains alpha,beta` takes only those two, by their names on the server. The others are left out: your agent never sees them, a search never asks the server about them, and they hide none of your local copies. Connect again with `--domains` to change the list. A connect without it keeps the list as it is, so signing in again never adds domains on its own. `--all-domains` takes everything again. A listed name the server does not offer (no rights yet, or not created yet) stays on the list and `connect` says so; it shows up once the server offers it. When two servers offer the same domain, the one that lists it serves it, even when the other one served it before; the domain keeps its name on this machine and `connect` says it moved. Take a domain off the list and its name is free again, and a local copy it hid comes back. `crystalline status` shows each server's list, and `crystalline doctor` notes listed names a server does not offer. For the server from `CRYSTALLINE_REMOTE_URL`, `CRYSTALLINE_REMOTE_DOMAINS=alpha,beta` sets the list. `remote.deadline_ms` stays one setting for all servers.

A domain the server marks read-only for your account (it is locked there, your role only reads it, or it is not on your write list) is marked "(read-only)" in your routing block too. The server decides; this machine only shows it, and a write there gets the server's own answer, which names the domain by its name on the server.

**One name per domain.** Every domain has exactly one source and one name on this machine. A server's domain keeps its own name when it is free. A name, once given, never changes on its own: whoever comes later gets a suffix, `<domain>-<source name>` (`jordi-acme`), whether that is a second server, a domain that appears on a server later, or a local domain you add later. `connect` says so at once and `crystalline status` keeps showing it; `crystalline domain rename jordi-acme acme-notes --local` picks another name. Your agent only ever sees plain names, never a server qualifier.

**The same domain twice.** A team domain you cloned locally and the same domain on a server (the same repository, folder and branch) are one domain. The server wins: its copy is used and your local copy is hidden while you are connected, untouched on disk, and back on `disconnect`. `connect` warns when the hidden copy holds changes you have not shared yet. The same domain on two servers is taken from the one you connected first, unless a list of domains names it (see "Choosing domains" above).

**What it costs.** A call for one domain (read, write, edit, browse) goes only to that domain's source: one hop. A call over all domains (`search_engrams` without `domains`, `recent_activity`, `list_domains`, `evolve_engrams` or `reflect` without a domain) asks your local index and every server in parallel and waits at most `remote.deadline_ms` (3 seconds by default) for each. A server that is slower, or down, is left out of that answer and named in it. Search hits from several indexes are merged by rank (reciprocal rank fusion), because their scores cannot be compared; each server is asked for up to 100 hits per call. Live documents and draft links work on a server's domain: the server sees your agent by name in the participant strip, and a `dl_` share link holds its draft for 30 minutes after your agent's last call.

**What reaches the server.** The local daemon forwards calls to `POST /api/v1/ctl`, the control protocol over HTTPS, with the source's token and the name of the calling agent (for example `claude-code`). The route always needs a token, whatever `auth.mcp` says, runs as the token's account (the same domain rights as over MCP) and serves six commands: `status`, `tool`, `routing_bullets`, `hook_status`, `origin_status` and `origin_changes`. Every other command answers "not available over a remote connection". A `tool` call goes through the same per-tool checks an MCP call by that account does, and `configure` and `provision` are not reachable through it. A server never forwards a call it got this way to its own sources. Only your own sessions reach the servers: an HTTP client of your local daemon never borrows your sign-in.

**What stays on this machine.** The credential of each source lives in the OS keychain under `crystalline-server:<host>`, or in a file only you can read when no keychain works; the token only ever travels to its own server. Per source, `<state_dir>/remote/<host>/` keeps two small cached answers: the routing model with the domain list (`routing.json`) and the maintenance status the end-of-session nudge reads (`hook_status.json`). Nothing else of a server's knowledge is stored here. With a server down, session start prints its cached part of the routing block with one line saying it may be out of date, and its domains are missing from answers until it is back; the hidden local copy of a replaced domain is never used in its place. The local web UI shows your local domains and lists the servers' domains with a link to each server's Fluid.

**Headless machines.** `CRYSTALLINE_REMOTE_URL` and `CRYSTALLINE_REMOTE_TOKEN` (a personal MCP token) add one source without running `connect`, for CI jobs and containers. It is never written down, so its names are worked out again at each start. `CRYSTALLINE_REMOTE_TOKEN_FILE` reads the token from a file instead.

```mermaid
flowchart LR
    H[Harness] -->|stdio MCP| D[Local daemon: mount table]
    K[Hooks and CLI] -->|socket| D
    D --> L[(Local domains)]
    D -->|HTTPS, Bearer, POST /api/v1/ctl| A[Server acme]
    D -->|HTTPS, Bearer, POST /api/v1/ctl| B[Server beta]
    D -.->|server down| C[(routing.json and hook_status.json per server)]
    N[crystalline connect] -->|OAuth consent in the browser, or a pasted token| A
    N --> T[(keychain: crystalline-server:host)]
```

## Under a path

Crystalline can share a host name with other services. Put it at `https://example.com/crystalline` behind your reverse proxy and everything works under that path: Fluid, sign-in with a password or single sign-on, OAuth for hosted clients such as Claude.ai, MCP over HTTP and `crystalline connect`.

```mermaid
flowchart LR
    B[Browser or agent] -->|example.com/crystalline/...| P[Reverse proxy]
    C[crystalline connect] -->|example.com/crystalline| P
    P -->|path stripped or passed through| D[Daemon with public_url]
    P -->|two OAuth documents at the host root| D
    D --> K[Knowledge files]
```

**The rule.** Set `service.public_url` to the address with its path, for example `CRYSTALLINE_SERVICE_PUBLIC_URL=https://example.com/crystalline`. That is the only setting. The daemon cannot guess a path from a request, so without `public_url` there is no prefix, and the path is read from that one key and from nothing else (no forwarded-prefix header is looked at). Each segment of the path uses lower-case letters, digits, `.`, `_` and `-`. A trailing slash is dropped, so `https://example.com/crystalline/` and `https://example.com/crystalline` are the same address. A dot segment (`.` or `..`), a query and a fragment are refused. So is a first segment the server answers at itself: `api`, `assets`, `health`, `.well-known`, `robots.txt`, `humans.txt` and the top-level pages of the web UI (`login`, `d`, `draft`, `search`, `graph`, `authorize`, `maintenance`, `users`, `settings`, `profile` and `π`). That one is required, not cautious: the daemon accepts a request with and without its prefix, so a prefix that is also a route of its own would be stripped twice behind a stripping proxy. A path whose first segment is free (`/crystalline`, `/kb`, `/team/knowledge`) is fine. `crystalline config set` and `crystalline config unset` refuse a bad value with a sentence. A bad value in the environment variable or in a hand-edited `config.yaml` is ignored with one startup warning, and the daemon then serves at the root. The check at the end of this section shows that state.

**The proxy.** It may strip the path or pass it through, and the daemon accepts both. The daemon removes the prefix once and only as a whole segment: `/crystalline`, `/crystalline/` and `/crystalline/api/...` lose it, `/crystallinex` and `/CRYSTALLINE/...` do not, and `/crystalline/crystalline/health` becomes `/crystalline/health` and stops there. Forward the bare `/crystalline` as well, without a redirect: the daemon answers it like `/crystalline/`, and an MCP client never follows a redirect. With OAuth on (see [MCP clients over OAuth](#mcp-clients-over-oauth)), also forward the two documents at the host root. RFC 9728 and RFC 8414 insert the path after the host name, so a client asks `https://example.com/.well-known/oauth-protected-resource/crystalline` and `https://example.com/.well-known/oauth-authorization-server/crystalline`, and those two paths are not under `/crystalline`. The daemon also serves both documents inside the prefix, for a client that appends the path instead, and the `WWW-Authenticate` challenge of a refused agent names the RFC 9728 address.

nginx, passing the path through (no URI after the address; this form forwards the request as sent, which is the one the [Fluid image](#team-server-with-fluid) uses and the one to prefer):

```nginx
server {
    server_name example.com;
    client_max_body_size 10m;

    # The Host header verbatim, port included, and no buffering for the change stream.
    proxy_set_header Host $http_host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_http_version 1.1;
    proxy_buffering off;

    # A file an agent uploads travels as base64 in the body of an MCP call
    # (served at the prefix itself and below it) and of a remote tool call,
    # so those two paths take 15m where the rest keeps 10m. A connected
    # machine waits up to 120 s for an upload, so the proxy waits longer.
    location = /crystalline {
        client_max_body_size 15m;
        proxy_read_timeout 180s;
        proxy_send_timeout 180s;
        proxy_pass http://127.0.0.1:7411;
    }
    location /crystalline/ {
        client_max_body_size 15m;
        proxy_read_timeout 180s;
        proxy_send_timeout 180s;
        proxy_pass http://127.0.0.1:7411;
    }

    location /crystalline/api/v1/collab/ {
        proxy_set_header Host $http_host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_read_timeout 300s;
        proxy_pass http://127.0.0.1:7411;
    }

    location = /.well-known/oauth-protected-resource/crystalline   { proxy_pass http://127.0.0.1:7411; }
    location = /.well-known/oauth-authorization-server/crystalline { proxy_pass http://127.0.0.1:7411; }
}
```

Keep the read and send timeouts above 120 s, the time a connected machine waits for a forwarded call. A shorter proxy timeout (nginx's default is 60 s) cuts off a slow upload, and the agent then cannot know whether the file was written.

nginx, stripping the path: give each `proxy_pass` of the first two locations a trailing slash, `proxy_pass http://127.0.0.1:7411/;`. Leave the two well-known locations as they are, since they are at the host root already, and keep the collab location's `proxy_pass` without a URI. Know the cost: with a URI after the address nginx forwards a decoded and normalized path, so a permalink holding an escaped `%2F` or `%25` reaches the daemon meaning something else. The pass-through form has no such problem. The three other requirements of [Web UI from the daemon](#web-ui-from-the-daemon) stay: `Origin` untouched, the WebSocket upgrade for `/crystalline/api/v1/collab/`, and `client_max_body_size` raised (64 MiB for the archive paths, as in [Team server with Fluid](#team-server-with-fluid)). A plain `location /crystalline/` without the exact `location = /crystalline` answers the bare path with a redirect, which is why both are there.

Caddy, stripping the path:

```caddy
example.com {
    @crystalline path /crystalline /crystalline/*
    handle @crystalline {
        uri strip_prefix /crystalline
        reverse_proxy 127.0.0.1:7411
    }
    handle /.well-known/oauth-protected-resource/crystalline {
        reverse_proxy 127.0.0.1:7411
    }
    handle /.well-known/oauth-authorization-server/crystalline {
        reverse_proxy 127.0.0.1:7411
    }
}
```

Caddy, passing the path through: the same file without the `uri strip_prefix` line. Caddy keeps the `Host` header, upgrades WebSockets and flushes the event stream by itself.

The [Fluid image](#team-server-with-fluid) does this work for you when it is the front door: `CRYSTALLINE_BASE_PATH=/crystalline` serves the app under the path, forwards `/crystalline/api/` and answers the bare path, the two OAuth documents at the host root and the copies inside the path. Give the daemon behind it `service.public_url` with the same path. The proxy in front of that image still has to forward `/crystalline` and the two host root paths to it.

**The web UI.** The daemon's embedded Fluid works under the prefix with nothing to build: it serves `index.html` with `<base href="/crystalline/" />` in place of the root tag, so every asset, API call, link and WebSocket of the page goes under the path. A server at the root serves the file as built.

**Sign-in.** Every cookie the server sets, the session and the single sign-on state, is scoped to the path (`Path=/crystalline`), so two instances on one host keep separate sessions. A server at the root keeps `Path=/`. `auth.oidc.redirect_uri` may carry the same path in front of the callback: `https://example.com/crystalline/api/v1/auth/oidc/callback`, and it has to be that exact path. A redirect address whose path disagrees with `service.public_url` is refused by `config set` and `config unset`, and found at startup it leaves single sign-on off with a warning naming both values. Without `auth.oidc.redirect_uri`, the daemon builds the callback from the host the browser used, the path of `public_url` and `/api/v1/auth/oidc/callback`; register that with the provider. See [Enterprise SSO](#enterprise-sso).

**OAuth.** The resource and the issuer are both the base, `https://example.com/crystalline`, and every access token is minted for that string: a token for the bare `https://example.com` is refused here, and the other way round. There is no check in the daemon or in `crystalline doctor` that the two host root paths reach it, because from inside it cannot tell. The check below does.

**Connecting.** `crystalline connect https://example.com/crystalline` (and `CRYSTALLINE_REMOTE_URL`) keeps the path. A client looks for each OAuth document at the host root address first and then at the copy inside the path. Under a path every document and endpoint the server names has to stay inside the base, and `connect` is refused otherwise. Two paths on one host are two servers: two sources, each with its own sign-in. The keychain entry is `crystalline-server:example.com/crystalline` and the cache folder is `remote/example.com~crystalline/`, where each `/` of the path becomes `~`. A server at the root keeps the key and folder it always had, so an existing connection is untouched. See [A local Crystalline with domains from shared servers](#a-local-crystalline-with-domains-from-shared-servers).

**Check it from outside.** Run each line from a machine on the other side of the proxy, and say `Accept: text/html` where the line does, because a browser says it and curl does not.

```sh
curl -s https://example.com/crystalline/health
curl -s -H 'Accept: text/html' https://example.com/crystalline/ | grep -o '<base href="[^"]*"'
curl -s https://example.com/.well-known/oauth-protected-resource/crystalline
curl -s https://example.com/.well-known/oauth-authorization-server/crystalline
```

- Health: `{"status":"ok",...}`. Anything else means the proxy does not forward the path to the daemon. Behind the Fluid image `/crystalline/health` is not forwarded and answers the app shell, so ask `https://example.com/crystalline/api/v1/auth/providers` instead, which answers JSON.
- The shell: `<base href="/crystalline/" />`. `<base href="/" />` means the daemon has no prefix: `public_url` is unset, has no path, or was refused at startup (read the daemon's first log lines for the warning). Another path means `public_url` and the proxy disagree. No line at all means the proxy answers the page itself.
- The protected-resource document (OAuth on): `"resource"` equals `https://example.com/crystalline`. The authorization-server document: `"issuer"` equals it. A 404 on either means the proxy does not forward that host root path to the daemon, so the two root lines are missing. Another address means `public_url` is wrong, or unset while `auth.oidc.redirect_uri` names the address (see [MCP clients over OAuth](#mcp-clients-over-oauth)). With OAuth off the daemon serves no such document at all, which is a 404 too.
- The bare prefix: `curl -s -o /dev/null -w '%{http_code}\n' -H 'Accept: text/html' https://example.com/crystalline` prints `200`. A `301` or a `302` means the proxy redirects it, and an MCP client cannot follow that.

## Enterprise SSO

Setting `auth.oidc.issuer`, `auth.oidc.client_id` and `auth.oidc.client_secret` (or the three matching `CRYSTALLINE_AUTH_OIDC_*` variables) turns on a sign-in button beside the local one. It is opt-in and additive: local accounts keep working, and an instance with none of the three set behaves exactly as it did before. All seven keys are read once when the HTTP surface starts, like `service.read_only`, so a change takes effect at the next start; a block missing any of the three required keys leaves single sign-on off and says which key is missing in a startup warning rather than refusing to come up.

Three routes come with it, all public because a browser reaching them has no session yet, and all under the existing `/api/v1` mount, so a reverse proxy that already forwards `/api/` needs no new rule:

| Route | What it is for |
| --- | --- |
| `GET /api/v1/auth/providers` | Whether to draw the button, and its label. Carries no issuer, client id or secret |
| `GET /api/v1/auth/oidc/login` | Starts the sign-in: redirects to the provider with PKCE (S256), a state and a nonce |
| `GET /api/v1/auth/oidc/callback` | Where the provider sends the browser back |

**Register the callback with the provider as the redirect uri**, spelled with the scheme and host your users reach the instance at: `https://<your-host>/api/v1/auth/oidc/callback`. Crystalline derives that address from each request's own `Host` header, and the scheme by one rule: a loopback `Host` (`localhost`, `127.0.0.1`, `[::1]`) with no forwarded scheme is `http`, and everything else is `https` - which is the same rule that decides whether a session cookie gets `Secure`. So a reverse proxy that passes the public hostname through as `Host` needs nothing more; a proxy that rewrites `Host` to `127.0.0.1:7411` must also set `X-Forwarded-Proto: https` (or RFC 7239 `Forwarded: proto=https`), or the redirect uri is built with `http://` and the provider refuses it. The rule has one consequence worth stating plainly: an instance served over plain HTTP on a non-loopback address gets an `https://` redirect uri it does not serve, so single sign-on is not supported on plain-HTTP deployments off loopback. An instance reachable under more than one hostname needs every one of them registered.

**Where that derivation cannot work, name the address instead.** `auth.oidc.redirect_uri` (or `CRYSTALLINE_AUTH_OIDC_REDIRECT_URI`) is used verbatim, and the request's own `Host` is not consulted at all: it has to be an absolute `https` url ending in `/api/v1/auth/oidc/callback` (under the path of `service.public_url` when it has one) - `http` is allowed only on loopback, for a development server - and it is refused at the moment it is set, with teaching text naming the key, rather than at the provider. That is the key for a proxy that rewrites `Host` to an internal address and cannot be made to forward the public one, and for a deployment whose public entrance simply is not what the process sees. One address, so an instance reachable under several hostnames still derives per request instead.

**With `auth.oauth` on, that key also names this instance to OAuth clients.** The origin of `auth.oidc.redirect_uri` (for an instance without `service.public_url`) - its scheme, host and port, with the callback path dropped - is the OAuth resource identifier: the `resource` and `issuer` both well-known documents publish, the address in the `WWW-Authenticate` challenge a refused agent reads, and the audience every access token is minted for and checked against. Unset, the identifier is derived from each request's `Host` by the same rule the callback address uses. So a deployment behind a proxy that rewrites `Host` wants this key set even with single sign-on switched off: without it, tokens are minted for the upstream's `127.0.0.1:7411` and the published `resource` is an address nobody outside the machine can reach. A value that is not an absolute `http` or `https` url falls back to per-request derivation with a startup warning, rather than publishing something unusable. `service.public_url`, when set, is that base (its path included) and outranks the origin of `auth.oidc.redirect_uri`; the redirect uri keeps its own job as the callback address.

**A first sign-in creates the account it signs in.** The durable key is the pair of the provider's issuer and the token's `sub` claim, and nothing else: a subject nobody has seen before gets a fresh account at `auth.oidc.default_role` (`viewer` unless you set it), with a login name derived from `preferred_username`, or from the local part of the address when the provider sends no username, folded and uniquified with `-2`, `-3` and so on when the name is taken. The account carries no password, so it signs in through the provider only, and it counts against `auth.max_users` like any other. A subject that has signed in before returns to the same account whatever the provider now calls that person: only the address follows a rename, never the login name, the role or the disabled flag, and a disabled account is refused the same way it is refused everywhere else. The provider's `name` claim sets the display name once, when the account is created; a later sign-in never overwrites it, so a person can change their display name in Fluid's Profile screen (`PATCH /api/v1/me`) and keep it.

**An invite link is taken by signing on.** On an instance with single sign-on the invite page offers that sign-in only, unless an admin made the link a local-account link. Accepting sends the browser to the provider as an ordinary sign-in does; the invite's token stays on the server, in the sign-in's pending record beside the state and the nonce, and never rides in a URL. The callback then redeems it: an identity that has signed in before gets the membership on its account, and one nobody has seen gets a fresh account at the link's role (not `auth.oidc.default_role`), linked and made a member in the same transaction that uses the link. A link that can no longer be redeemed when the browser comes back (revoked, expired, its maker no longer allowed) signs nobody in, and the browser reads a page that says why; the person can still sign in the ordinary way. See [Invite links](#invite-links).

**An address never joins an existing account.** An account created locally, and an account created by an earlier sign-on, are reached by their identity link or not at all: a provider that will hand anybody an `email` claim cannot hand anybody somebody else's account, and a person who has both a local account and a provider identity gets two accounts until the two are deliberately linked.

**Linking an identity to an existing account is an explicit act, by the person or by an administrator.** There are exactly two ways, and neither of them is an address matching:

- **From the profile.** A signed-in account presses "Link" on the SSO identity card. That is a `POST /api/v1/auth/oidc/login` carrying the session's CSRF token, answering with the provider's authorization endpoint in `location` for the browser to navigate to; the sign-on then runs as usual and the callback ties the identity to the account that started it. A POST rather than a link on purpose: the session cookie is `SameSite=Lax` and would ride a cross-site top-level navigation, so a GET that started a link could be started by any other page on the internet. `GET /api/v1/auth/oidc/login` stays the ordinary sign-in, and the same GET carrying `link=true` is refused with a 400 that says where linking lives. The account that started the link has to be the account that finishes it, resolved the same way on both ends (the session cookie, or the trusted header on an instance that uses one): a callback arriving with no live account is refused with 401 (sign in again and start over), one arriving on another account's session with 409, and an identity another account already holds with a 409 that never says which account that is - an operator can move it, and a sign-on must not become a probe for who holds an identity here. The same card lists what is linked (`GET /api/v1/me/identity-links`) and gives one up (`DELETE /api/v1/me/identity-links/{issuer}`, the issuer percent-encoded as one path segment).
- **From the command line.** `crystalline users link <name> --issuer <issuer> --subject <sub>` ties a pair to an account, and `crystalline users unlink <name> --issuer <issuer>` takes it away. This is the repair for a provider that re-issues its subjects - an Entra tenant re-registration, where every `sub` changes and every account is suddenly unreachable: unlink the stale identity, then link the new subject to the same account. Both commands write the accounts database directly, so they work whether or not a daemon is running.

**An account is never left with no way in.** An account a first sign-on provisioned has no password, so its identity link is its only credential, and unlinking the last one is refused - on the profile card and on the command line alike, in one sentence that names `crystalline users passwd`. Give it a password first, or, when the repair genuinely needs the account unreachable for a moment, pass `--force` to `crystalline users unlink`: it says what it left behind, and the account stays unreachable until it is linked again or given a password.

The client secret is stored but never rendered: `crystalline config show` and `crystalline doctor` print `(set)`, and the `configure` tool does not show it at all, and a failure from the provider reaches the browser as a sentence written by Crystalline, with the provider's own words going only to the daemon's `debug` log. Set the secret through `CRYSTALLINE_AUTH_OIDC_CLIENT_SECRET` where a deployment keeps credentials out of `config.yaml` entirely. `CRYSTALLINE_AUTH_OIDC_CLIENT_SECRET_FILE` reads it from a Docker secret. An `http://` issuer anywhere but loopback is accepted with a startup warning, because the secret and every ID token then cross the network in clear text.

What an operator sees in the daemon's log at its default level: every refused sign-in is one `WARN` line naming the reason category (a state that did not match, an expired sign-in, a token whose signature, issuer, audience, expiry or nonce did not validate, a discovery or key-set fetch that failed, a userinfo answer for another subject) and the issuer, and every validated sign-in is one `INFO` line naming the issuer and the subject (the pseudonymous key, which is what makes a sign-in traceable). No refusal line carries a state, a code, a nonce, a token or the secret, and no line at any level carries a presentation claim - a name, a username or an address. The `debug` lines that render a validation failure carry the validator's own text, which for a mismatched issuer or an expired token names the value in question (`iss`, `exp`) - a refusal an operator cannot locate is not much of a refusal - and `debug` is off at the default level. A provider that keeps `preferred_username`, `name` and `email` out of the ID token (Authelia 4.38 and later without a claims policy) has the missing ones fetched from its userinfo endpoint; an unreachable userinfo costs the sign-in those fields, not the sign-in. Two more limits protect the public login route: at most 10,000 sign-ins may be in flight at once, and past that a new one is answered `503` rather than evicting somebody mid-consent, and a provider whose discovery fails is not asked again for five seconds.

```mermaid
flowchart LR
    B[Browser] -->|1. GET /auth/oidc/login| D[Daemon]
    D -->|2. 302 with PKCE, state, nonce| B
    B -->|3. authenticate| P[Identity provider]
    P -->|4. 302 back with a code| B
    B -->|5. GET /auth/oidc/callback| D
    D -->|6. code plus client secret| P
    P -->|7. ID token| D
    D -->|8. session cookie, 302 to /| B
```

**Notes for Microsoft Entra ID**, gathered in one place since a tenant's setup touches all four of the following:

- **Tenant-specific issuer.** `auth.oidc.issuer` has to be the tenant-specific `https://login.microsoftonline.com/<your-tenant-id>/v2.0`, never the `common`, `organizations` or `consumers` endpoint a portal page shows by default (its literal `{tenantid}` template breaks issuer checks and is refused with that correction, and so are the three tenant-independent aliases). See the `CRYSTALLINE_AUTH_OIDC_ISSUER` row above.
- **A certificate over a secret.** Entra can authenticate a confidential client with a certificate credential instead of a client secret, and an organization's app-registration policy may require it. Crystalline speaks `auth.oidc.client_secret` only in 0.18.0 - register a client-secret credential for the app, or hold off on certificate-only tenants until that support lands.
- **Pairwise subjects move.** An Entra `sub` is tenant- and application-specific by default (pairwise), and it can change on a tenant reconfiguration - an app re-registration, a directory merge - which strands every account that first sign-on ever provisioned. The repair is the linking commands above: `crystalline users unlink <name> --issuer <issuer>` takes the stale identity off, then `crystalline users link <name> --issuer <issuer> --subject <new-sub>` puts the new one back on the same account, with `--force` on the unlink half when the account has no other way in for the moment between them.
- **App Roles over the `groups` claim.** Crystalline reads no group or role claim in 0.18.0 - every account provisioned through single sign-on lands at `auth.oidc.default_role`, whatever the person's Entra groups or App Roles say. If claim-based role assignment is ever added, App Roles is the better source to build it on than the `groups` claim: it rides the ID token directly, where `groups` needs a Microsoft Graph lookup past 200 memberships and is easy to get wrong at tenant scale.

## Proxy forward auth

A proxy that has already authenticated the person - a forward-auth deployment, the shape [Authelia](https://www.authelia.com/) or [oauth2-proxy](https://oauth2-proxy.github.io/oauth2-proxy/) sit in front of an application as - can name them to Crystalline in the standard `Remote-*` quartet instead of anybody signing in twice. `auth.proxy_headers` (or `CRYSTALLINE_AUTH_PROXY_HEADERS=true`) turns that on, and it is off in every install that has not asked for it: with the mode off, a request carrying `Remote-User` is resolved exactly as one carrying nothing at all, so a header a client made up buys nothing.

**This is trust-the-proxy, and the trust is total.** With the mode on, whoever can set `Remote-User` on a request that reaches this instance is whoever they say they are. That is safe under exactly two conditions, and both of them are the operator's to hold:

- Crystalline is unreachable except through that proxy. A port that is also reachable directly is an open door, not a protected one.
- The proxy strips client-supplied copies of all four headers and sets them itself. A proxy that forwards what a client sent (nginx does, unless told otherwise) hands every browser the ability to name any account.

There is nothing Crystalline can check about either one, which is why the mode is opt-in and why this paragraph is where it is.

| Header | What it is used for |
| --- | --- |
| `Remote-User` | The person. The identity key, and the only header that matters for who the request is |
| `Remote-Name` | The display name, set when the account is created and never overwritten later, so a name the person changes in their profile stays |
| `Remote-Email` | The address, refreshed when it changes |
| `Remote-Groups` | Parsed and discarded. Claim mapping is not built in 0.18.0: no group decides a role, a membership or a visibility. Read as a list header, so a proxy may send one comma-separated value or one header line per group; the other three are single-valued and a second copy of one of them is refused |

**A forwarded identity gets an account of its own.** The durable key is the pair `("proxy", <the forwarded user, folded>)`, stored in the same identity-link table single sign-on uses, and a first arrival provisions a fresh account at `auth.oidc.default_role` (`viewer` unless you set it, the same key both external-authenticator modes read) counting against `auth.max_users` like any other. It is never an existing local account of the same name: a `Remote-User: ada` beside a local admin called `ada` provisions `ada-2` at viewer and leaves the admin exactly as it was. That is the same no-silent-linking rule single sign-on follows, applied to a mode that asserts nothing but a name - and it means a person who has both a proxy identity and a provider identity has two accounts until somebody links them, with `crystalline users link <name> --issuer proxy --subject <the forwarded user>`.

**An invite link gives a forwarded identity the membership only.** The proxy names the person on every request, and the first one makes their account, so by the time the invite page accepts a link the account exists already: it gets the link's domain and level, raised and never lowered, and keeps the role `auth.oidc.default_role` gave it; the link's own role never applies here. The page offers no local account unless an admin made the link a local-account link, and accepting needs the forwarded identity and the CSRF token the first `/api/v1/auth/me` minted, like every other write. See [Invite links](#invite-links). `auth.trusted_header` behaves the same way.

**Create the admin account before turning this mode on.** The first proxied request provisions an account and so ends the first-run wizard, and if that account is a viewer the instance has no admin and the way back is `crystalline users add --role admin` on the host.

The rest follows the modes already documented above: a disabled account is refused, a request that carries no `Remote-User` falls through to the ordinary session cookie (turning the mode on escalates nobody), the first `/api/v1/auth/me` mints the session whose CSRF token this identity's writes echo, and a `Remote-User` that cannot be a login name is refused `403` naming why rather than provisioning something unusable.

**One header mode at a time.** `auth.trusted_header` names a single custom header and `auth.proxy_headers` trusts the standard set; an instance configured with both leaves the HTTP endpoint refusing to start (a warning naming both keys and saying to pick one), while the daemon itself keeps running - MCP over stdio, and every other background task, is unaffected. Note what switching between them costs: accounts the trusted-header mode created carry no identity link, so an instance that turns that mode off and this one on provisions a second account for every person, and the old accounts (with their roles and memberships) stay behind. Link them rather than re-granting: `crystalline users link <old-name> --issuer proxy --subject <the forwarded user>` makes the account they already have the one the proxy signs them into.

**Agents are governed separately.** `auth.mcp` is what decides whether an HTTP MCP connection has to authenticate, and it is answered with a personal MCP token and nothing else. No `Remote-*` header is a way past that gate, whatever this mode is set to: a proxy vouches for a browser, and an agent presents its own credential.

**This mode and `auth.oauth` coexist by design, and the two are unrelated except at one seam.** With OAuth on ([MCP clients over OAuth](#mcp-clients-over-oauth)), the consent screen a client's browser lands on is signed in the same way every other Fluid page is here, forward-auth included. But `/api/v1/oauth/token`, `/api/v1/oauth/register` and both well-known documents are machine-to-machine legs, public by path and never read through `Remote-*` headers - a proxy in front of an OAuth-enabled instance must pass those paths through unauthenticated. Getting that wrong has a specific failure shape worth knowing before it is met in production: the request guard checks CSRF before it checks whether a path is public, so a proxy that injects `Remote-User` on every request hands the token endpoint a trusted-header identity with no CSRF token yet, which the guard answers `403` - silently breaking every token exchange and refresh a connected client attempts. Exempt `/api/v1/oauth/*` from whatever forwards the identity header at the proxy, rather than routing around it here.

**The GitHub App's webhook has to pass through without authentication, too.** GitHub delivers the App's events to `POST /api/v1/github/webhook` with no session and no sign-in of any kind; the proof is the signature over the body under the App's webhook secret, which the daemon checks itself. A proxy that asks for a sign-in on that path answers GitHub with a login page or a 401, every delivery fails, and access changes on GitHub then wait for the five minute cache. Let `POST /api/v1/github/webhook` through unauthenticated, at an authenticating proxy, a forward-auth proxy or a single sign-on gate in front of the instance alike. A forwarded identity header on it does no harm (the daemon reads none on this route), but there is nothing for it to do either.

```mermaid
flowchart LR
    B[Browser] -->|1. request| P[Forward-auth proxy]
    P -->|2. authenticate, strip client headers| P
    P -->|3. request plus Remote-User, -Name, -Email, -Groups| D[Daemon]
    D -->|4. look up proxy plus user in the identity links| A[(Accounts)]
    A -->|5. the linked account, or a fresh one| D
    D -->|6. answer, and a session on the first probe| B
```

## The stdio and HTTP surfaces can differ

One daemon can serve a local agent over stdio and a remote one over HTTP at the same time, and with `skills.serve` at its `auto` default those two clients are deliberately not served the same skill surface. An operator who notices that is looking at a decision rather than a bug, so here is the whole of it.

A stdio session runs in a `crystalline mcp` process the harness itself started, so that process knows which harness it belongs to: `crystalline install` registers it as `crystalline mcp --harness <name>`, and at startup it asks the local install receipt whether that harness has session hooks wired. If it has, the harness already carries the six managed skills as files and delivers the routing block from its own hook, so the session is served neither the skill surface (the `skills` tool, the seven `skill://` resources, the two prompts) nor a second copy of the block. Nothing in that decision comes from the connecting client, and it is fixed before the session starts.

An HTTP client gets no such treatment and never will: one daemon serves every HTTP connection, and a remote client never ran `crystalline install` on this machine, so nothing here says what it already has. A remote client is exactly who the served surface exists for.

There is a second asymmetry, and it moves in the other direction: the routing block a stdio session gets on arrival names every registered domain, while the one an HTTP session gets on the legacy `initialize` handshake names none. That is not a setting - it is the handshake's shape. The instructions are built once per connection with no request in hand, so over HTTP there is no caller to resolve and no way to leave a private domain out of the block; the handshake therefore carries every behavior rule, a count of the domains that are not private and a pointer at `list_domains` with `include_routing: true`, which does resolve its caller and does filter. Every channel that carries a request scopes properly: `server/discover` (the 2026-07-28 era's own onboarding path), the `onboarding` prompt and `list_domains` itself each hand an agent the domains its account may see. A stdio session is the machine owner and keeps the whole block. An operator who wants domain lines in an HTTP client's instructions has one answer, and it is the one the block itself gives: have the client call `list_domains` at session start (the `connector` prompt and the shipped skills both teach exactly that).

Two things make the skills difference inspectable and overridable rather than mysterious:

- **See which answer a stdio session will get:** `claude mcp get crystalline` (and the Codex and Copilot equivalents) prints the registered command. If it reads `crystalline mcp --harness <name>` the session can be suppressed; if it reads plain `crystalline mcp` - which is what every registration written before that flag existed reads - it is served the full surface. Rerunning `crystalline install claude-code` repairs a flagless registration in place; it leaves a hand-edited one alone (a command that is not the one it writes, an entry in another scope, an environment block of your own) and prints the command you can run yourself. **It repairs Claude Code only.** Codex and Copilot registrations are read back through their own CLIs, whose `mcp get` output format has not been verified, and an install that cannot read what it is repairing must not touch it, so those are reported and left alone; replace one by hand with `codex mcp remove crystalline && codex mcp add crystalline -- crystalline mcp --harness codex` (the same shape for `copilot`), or set `skills.serve` explicitly and sidestep the whole question.
- **Turn the difference off:** set `skills.serve` explicitly to `true` or `false`. An explicit value always wins over the resolved answer, on both transports, so every client on the machine is served identically. Only the `auto` default produces the asymmetry.

Cursor, Kiro, Gemini CLI and Qwen Code keep the full skills surface until a live check confirms that they load the skills as files.

## Read-only deployments

Pass `--read-only` to `serve` (or to `mcp`), set `service.read_only: true` in the config, or set `CRYSTALLINE_SERVICE_READ_ONLY=true` (the container-native spelling, see [Configure through environment variables](#configure-through-environment-variables)) to serve the content API read-only. Thirteen tools leave the MCP tool list on a default install, and seventeen once `github.enabled` is on, since the four collaboration verbs that write (`share_changes`, `resolve_conflict`, `withdraw_proposal` and `discard_changes`) follow the same gate. The seven write-gated ones (`write_engram`, `edit_engram`, `split_engram`, `move_engram`, `delete_engram`, plus `add_domain` and `remove_domain`, which register and unregister domains) are also refused if a client calls one by name, and so is `configure`, which writes settings. `evolve_engrams` and `provision` leave the list for a different reason and keep answering: the sweep is a pure read, but every finding it returns prescribes a mutation, and a queue of work nobody can work is noise where mutation is impossible; `provision` follows the write gate because every action but `status` writes. Of the Reflection tools, `write_reflection` and `discuss` leave because they write and `reflect` for the reason `evolve_engrams` does; `read_reflection` stays. Meanwhile `search_engrams`, `read_engram`, `list_domains` and the rest of the read tools stay. Sync, the file watcher and embedding keep running, so the index still follows external edits such as a git pull. On PostgreSQL a read-only instance does not reparse virtual domains after a parser change. A writable instance does, and so does a `crystalline sync` run on a machine where no read-only daemon serves that database; where one does, the command goes to that daemon and skips the reparse too. A read-only instance refuses a collaborative editing session too, along with every other write to the knowledge: the collab WebSocket upgrade is refused, so a Fluid page opens an engram to read but never to co-edit. The one exception is the MCP token surface (`/api/v1/me/mcp-tokens` in the API, the Agent access card in Fluid), which keeps working: what `read_only` protects is the knowledge, and a token is account state in the accounts database rather than knowledge - a read-only server with `auth.mcp` on is exactly where an agent cannot connect at all until somebody issues it one. `crystalline prompt system` and the routing block the server hands each connecting agent follow the same mode: both drop the write guidance and state that the knowledge is curated externally, and `prompt system --read-only` forces that variant on demand. The block reaches an agent by whichever channel its protocol revision uses - `initialize` for every revision before 2026-07-28, `server/discover` from then on, where the handshake no longer exists - and carries the read-only variant either way. This is the natural pairing for the git-sync setup in `compose.git-sync.yaml`, where knowledge arrives by reviewed git commits and agents only consume it. The mode is fixed for the daemon's lifetime, so an agent attaching to a running daemon gets that daemon's mode. Most operator tooling on the host (`verify`, `import`, `domain init`/`add` and `model download`) is unaffected: the boundary is that the served API is read-only, not the machine. `crystalline domain remove` is the exception and follows the mode like `crystalline config set` does, because it goes through the same engine entry point every other surface removes a domain through, and a read-only instance's registry is frozen along with its knowledge. That entry point also clears the domain's index rows, so the command needs the index open: on a Postgres deployment a removal while the database is unreachable fails rather than editing the config file alone, which is the right answer on a database - the rows are the owner's, and a config-only removal here would leave the domain live for the next owner. The error says as much and names the config file to edit by hand if the database is gone for good. The web UI is served in full, because reading it is all GETs: the daemon hands out the shell and the app renders itself read-only, so a read-only instance is browsable as well as searchable, and with `auth.anonymous: true` it is browsable logged out (see [Web UI from the daemon](#web-ui-from-the-daemon)).

Agents connect to the containerized daemon over its HTTP MCP endpoint, `http://localhost:7411` from the host (the image sets `CRYSTALLINE_SERVICE_HTTP=0.0.0.0:7411` by default, since a container has to bind every interface to be reachable at all - binding `127.0.0.1` inside a container is only reachable from inside that same container). The stdio `crystalline mcp` transport (see [Get started](../README.md#get-started) in the README) is for local, non-containerized processes; point a harness at the HTTP endpoint instead when Crystalline runs in a container. A browser reaches the web UI at that same address, since the image serves it built in ([Web UI from the daemon](#web-ui-from-the-daemon)). Every HTTP endpoint also answers `GET /health` with a JSON body carrying `status`, `version`, `started_by` (`serve`, `autostart` or `unknown`) and `http` (the bound address, `off`, or `unrecorded`), so a load balancer or uptime monitor can probe the daemon without an MCP handshake, and can tell a managed daemon from one a connecting agent started on its own. A script reading both surfaces should not read that pair as disagreeing: `/health` spells a closed HTTP endpoint as the string `"off"`, while the same state comes back as `null` in a `crystalline status --json`/ctl reply's own `http` field.

The HTTP transport is Streamable HTTP: every exchange is a POST whose response arrives as a minimal SSE stream carrying exactly the JSON-RPC message, with no optional SSE fields (no retry hints, no priming frames), so strict intermediary parsers - AWS Bedrock AgentCore Gateway among them - consume it cleanly. Streamable HTTP is the transport MCP revision 2025-03-26 introduced, and it carries every protocol revision this server serves: `2024-11-05`, `2025-03-26`, `2025-06-18`, `2025-11-25` and `2026-07-28`. What is not served is the older HTTP+SSE transport that 2025-03-26 replaced: a client opening the old-style GET stream is answered with an immediate `400 Bad Request` naming the missing session id rather than a silent hang. A client declaring a version string this server does not serve is refused at the handshake with the protocol's own `-32022 Unsupported protocol version`, which names the revisions it can retry with, rather than being half-served.

**The session model differs by revision, and an operator meets that at the load balancer.** A client on any revision before `2026-07-28` opens with an `initialize` handshake and is handed an `Mcp-Session-Id` it presents on every later request, so those requests have to reach the same instance. From `2026-07-28` there is no handshake and no session at all: each POST carries its own protocol metadata and is answered on its own, which is what SEP-2575 exists for, so **a modern client needs no session affinity** and any instance can answer any of its requests. The client-opened GET stream is gone in that revision too; a modern client that wants notifications opens a `subscriptions/listen` POST stream instead, and receives on it only the categories it asked for. The daemon's `http_sessions` figure in `crystalline status --json` counts the legacy sessions alone, by construction: a modern client creates none. Results a modern client gets also carry the revision's caching hints, and they authorize nothing: the scope is `public`, but `ttlMs` is `0` on every one, so a caching proxy or CDN in front of the port may share what it holds but may not treat any response as fresh, which means it may not reuse one, and a legacy client is sent no hints at all because the fields do not exist below that revision.

The HTTP transport and the JSON API validate the request `Host` header to block DNS-rebinding attacks, where a malicious web page tries to drive a reachable server from inside the victim's browser. They answer only requests whose `Host` is on the allow-list, which is loopback by default (`localhost`, `127.0.0.1`, `::1`) plus the host of `service.public_url` when it is set. The MCP transport also checks the `Origin` header a browser sends against the same hosts; a client that sends no `Origin`, which is every client that is not a browser, is not affected. That default already covers the `http://localhost:7411` access above with no extra configuration, and the bind address is independent of it: binding `0.0.0.0` changes nothing about which `Host` values are accepted. Reaching the daemon by any other name needs that name added - a compose service-name (`http://crystalline:7411`), a LAN hostname or IP, or a public hostname forwarded by a reverse proxy. Add it with `CRYSTALLINE_SERVICE_ALLOWED_HOSTS` (comma-separated) or the repeatable `serve --allowed-host <host>` flag; loopback stays allowed either way. A single `*` accepts any `Host` and turns the guard off, which is only safe behind a trusted reverse proxy or firewall that validates `Host` itself. The guard is not access control: it stops a web page in somebody's browser, but any other program can send `Host: localhost`. What keeps agents out is `auth.mcp` (see [Authenticated agents](#authenticated-agents)). A blocked request gets `403 Forbidden`; `GET /health` and the GitHub App's webhook are never guarded, so probes and deliveries keep working regardless. With OAuth served, the same list decides which `Host` the two well-known documents will name as this instance's origin - see [MCP clients over OAuth](#mcp-clients-over-oauth). A reverse proxy that rewrites the upstream `Host` to `localhost` needs no allow-list entry; one that forwards the original public `Host` (the common default) needs that hostname listed.
