17  Configuration

This chapter lists everything you can set on a Crystalline instance: where the configuration is kept, which value wins when two places disagree, how to change a setting and every key and environment variable there is. Reach for it when a prose chapter names a setting in passing and you want its values, or when you set up a server and want the whole list in one place. The why stays in the prose chapters (chapter 5 for a laptop, Chapter 12 for a server, Chapter 13 and Chapter 14 for a team). This one keeps the complete list and links back to them.

17.1 Where configuration lives

Crystalline keeps three folders per user and uses the XDG layout on Linux and macOS alike, so on a Mac the file is under ~/.config too, never under ~/Library.

~/.config/crystalline/config.yaml
The configuration file, or $XDG_CONFIG_HOME/crystalline/config.yaml when that variable is set. It doesn’t have to exist: a missing file reads as all defaults, and a fresh install runs without one.
~/.local/state/crystalline
The state folder ($XDG_STATE_HOME), with the index in index.db, the accounts in web-auth.db, the daemon’s daemon.log and each team domain’s origin state. Back up the whole folder with the knowledge, because three things in it exist nowhere else: the accounts, sessions, agent tokens and memberships in web-auth.db, a virtual domain’s engrams in index.db and the unshared drafts of a domain in review mode.
~/.cache/crystalline
The cache ($XDG_CACHE_HOME). The embedding model sits under models/ there, unless CRYSTALLINE_MODELS_DIR moves it somewhere else.

On Windows the configuration and the state live under %APPDATA%\crystalline and the cache under %LOCALAPPDATA%\crystalline. The container image points all three at its /data volume, so there the file is /data/config/crystalline/config.yaml. serve, mcp, config and most other commands take --config <file> to read another file instead (verify --config is a different file, Chapter 20), and CRYSTALLINE_CONFIG does the same for every command in that environment; the flag wins over the variable.

Two more files share the name .crystalline.yaml, and neither is the configuration. One at a domain’s root tunes the checks for that domain (Chapter 20), and one in a workspace orders the domains the session-start briefing names there (Chapter 19).

17.2 Which value wins

The order is the same for every setting in the registry below: an environment variable beats the file and the file beats the built-in default (an empty variable counts as unset). A known variable with a value that can’t work stops the daemon at startup with a message naming the variable. The one exception is CRYSTALLINE_SERVICE_PUBLIC_URL, which only warns and falls back to deriving the address. An unknown CRYSTALLINE_* variable gets a warning in the log and is otherwise ignored.

Only five command-line flags override outright. serve --http and serve --allowed-host (repeatable) win over the variable and the file for that one run, and a serve whose flag disagrees with the saved value says so at startup. --config picks the file. The global --db picks the index file, ahead of database.url and the default index.db. --read-only on serve and mcp can only switch read-only on, never off, and on mcp it applies only when that process starts the daemon or runs the stack in-process.

Nothing from the environment is ever written back to the file. Crystalline ignores unknown keys in the file without a word, so watch the spelling: a misspelled key has no effect.

17.3 Changing a setting

crystalline config show prints every registry key with a one-line description and its effective value, marked (default) or (env) when it doesn’t come from the file. There’s no config get: show is the read, and the global --json makes it machine-readable. crystalline config set <key> <value> sets one key and crystalline config unset <key> puts it back to its default, removing a block that ends up empty. An unknown key is refused with the list of every known one, and a bad value is refused before anything is written.

With a daemon running, set and unset go to the daemon, which saves the file and takes the new value; with none, or with --config, the command edits the file directly. Either way the whole file is written out again, so comments, your own formatting and unknown keys are lost on the first set (a domain add rewrites it the same way). The result tells you when a key only applies at the next daemon start, and also when an environment variable overrides the key, in which case the saved value waits until the variable is removed. A read-only instance refuses set and unset, and show still works there.

Two keys are secrets, database.url and auth.oidc.client_secret, so config show, the configure tool and crystalline doctor render them as (set) whatever they hold.

For an agent the same registry is the configure tool, and called with no arguments it returns the settings page, which any caller may read. set takes a map of keys to values and unset a list of keys; the keys are applied in ascending order, and the first bad one stops the rest while the ones before it stay applied. A change needs a stdio session, an anonymous HTTP session on an instance with auth.mcp off or an admin account. On a read-only instance the tool refuses even the bare call, although config show in a terminal works. Its other arguments, connect, token, host and restart, run the GitHub sign-in Chapter 13 walks through; host names a GitHub Enterprise Server for that one sign-in, and github.api_url is the lasting setting.

The registry has 41 keys, and those are the only ones config set, configure and the environment reach. The embeddings block, prompt.rules and the domain registrations are edited in the file by hand or, for domains, with their own commands.

17.4 Serving

These keys shape the HTTP endpoint the daemon opens. All of them apply at the next daemon start except service.response_format, which a running daemon picks up at once. To restart, run crystalline ctl shutdown and let the next client start the daemon again, or restart the container or the systemd unit.

service.http
The endpoint that carries MCP, the JSON API and Fluid, on at 127.0.0.1:7411 by default. false turns it off, true spells the default out and a host:port binds that address instead. serve --http understands on and off too, besides the true and false that config set takes here.
service.allowed_hosts
A comma-separated list of extra Host header values the endpoint accepts, the guard against DNS rebinding from Chapter 12. Loopback is always allowed and a single * allows any host; empty by default. With OAuth served, a request whose Host isn’t on the list is refused rather than handed a document naming that host.
service.public_url
The address people open Fluid at, for example https://knowledge.example.com: an absolute http or https origin with no path, query or fragment (0.0.0.0 and :: are refused). Every web_url a tool hands back starts there, and it’s the OAuth resource identifier. Unset, the address is derived per caller, so set it behind a proxy that rewrites Host, in a container whose outside port differs from its inside one, for a separate Fluid deployment or for plain http off loopback.
service.ui
Whether the endpoint serves Fluid, true by default. With false only the API and MCP remain, the shape a separately deployed Fluid sits in front of.
service.api
Whether the endpoint serves the JSON API under /api/v1, true by default. false also switches Fluid off and leaves MCP and /health.
service.read_only
Serves knowledge read-only, false by default. The tools that change content are hidden and refused while sync, watching and embedding keep running, and config set is refused; serve --read-only forces it on for one run.
service.response_format
Decides how list-shaped MCP results are encoded. toon (the default) is compact for a model to read and json is plain JSON.
skills.serve
Whether the shipped skills are served over MCP (the skills tool, skill:// resources and the prompts). auto, the default, serves them to every client except a stdio session from a harness this machine already onboarded with hooks, which has them as files; true always serves them and false never does.

17.5 Signing in

Every key in this group applies at the next daemon start. Chapter 12 explains accounts, single sign-on and the header modes, and Chapter 14 what an agent is once it has signed in.

auth.anonymous
Serves API requests that carry no identity at all, at viewer level. It’s false by default, and then such a request is answered 401.
auth.mcp
Makes every MCP connection over HTTP present a personal token or sign in, false by default, while local stdio sessions are never asked.
auth.oauth
Serves OAuth for MCP clients, so a hosted client connects without a pasted token. Unset, it follows auth.mcp wherever Fluid is served, and false turns it off. With true it insists, and the daemon won’t start while auth.mcp, service.api or service.ui is off.
auth.max_users
How many accounts the trusted header, the forward-auth headers and single sign-on may create in total, 100 by default and at least 1. Past the cap only a new account is refused, and crystalline users is never capped.
auth.login.free_attempts
How many failed sign-ins in a row one name may make before each further attempt is delayed, 3 by default. The count is kept per submitted name, whether or not that account exists, and a successful sign-in clears it.
auth.login.max_delay
The longest delay in seconds, 8 by default: the delay doubles from one second up to this, and after that the answer is 429 with a Retry-After. Set it to 0 and the whole throttle is off.
auth.trusted_header
The one header a trusted proxy sets to name the signed-in user, for example remote-user. Unset by default, when no header is believed; an account it names is created at viewer role the first time it’s seen.
auth.proxy_headers
Trusts the forward-auth set Remote-User, Remote-Name, Remote-Email and Remote-Groups, false by default, and new accounts land at auth.oidc.default_role. Setting it together with auth.trusted_header keeps the HTTP endpoint from starting, so pick one.
auth.oidc.issuer
The single sign-on provider’s issuer URL, the one discovery appends /.well-known/openid-configuration to; while it’s unset, single sign-on is off. Entra’s {tenantid} template and the common, organizations and consumers endpoints are refused.
auth.oidc.client_id
The client id the provider issued when you registered this instance with it.
auth.oidc.client_secret
The secret that goes with the client id, best kept in CRYSTALLINE_AUTH_OIDC_CLIENT_SECRET rather than set with config set: that keeps it out of the file and out of your shell history.
auth.oidc.name
The label on the sign-in button, which uses generic wording while this is unset.
auth.oidc.scopes
The scopes requested, separated by spaces. Leave it unset and you get profile email; openid is always added.
auth.oidc.default_role
Decides the role a first sign-in creates an account at. It takes viewer, the default, editor or admin, and it also applies to accounts that arrive through auth.proxy_headers.
auth.oidc.redirect_uri
The callback the provider sends the browser back to, used verbatim instead of the address derived from each request. It’s an absolute https URL (http only on loopback) ending in /api/v1/auth/oidc/callback, spelled exactly as the provider has it registered. A value in the file that can’t work leaves single sign-on off with a warning at startup.

17.6 Team sync

Changes to the github.* keys take effect at once, without a restart. Chapter 13 tells the story of team domains, and a domain’s own origin (repository, branch and poll interval) is part of its registration in Chapter 19.

github.enabled
Turns team collaboration on, false by default. It lists the six collaboration tools and starts the background poll, and connecting GitHub from Fluid turns it on as well.
github.poll_secs
Sets how often the daemon checks each team domain’s repository for changes, in seconds: 300 by default and at least 60.
github.stacks
Whether sharing again while a proposal is open stacks a new proposal on top of it where the forge supports stacked pull requests, true by default. With false there’s one proposal per domain, updated in place.
github.share_identity
Whose GitHub identity a share runs under. instance, the default, uses the one connected token for everything; personal makes each person connect their own identity for sharing, while pulling stays on the instance token. config set refuses any other value, and a hand-edited one reads as instance.
github.agent_identity
In personal mode, the account whose connected GitHub identity an agent’s share over HTTP runs under when agents don’t sign in (auth.mcp off). While it’s unset, such shares are refused. The account name takes lowercase letters, digits, ., _ and -.
github.api_url
The GitHub API address, https://api.github.com by default; point it at your GitHub Enterprise Server’s API to use one.
github.oauth_client_id
The client id of an OAuth App you registered yourself, which replaces the one built in. Set it together with github.api_url when the sign-in should use an app on your own server.

17.7 Search, capture and recall

These keys take effect at once, and Chapter 9 explains how a search ranks.

search.salience_weight
The largest lift a fully salient engram gets in the ranking, 0.0 to 1.0, 0.15 by default. It reorders results within a band of relevance and never filters.
search.retired_weight
The factor applied to an engram whose status is deprecated, superseded, archived or legacy, 0.0 to 1.0, 0.6 by default; 1.0 turns the fade off.
capture.similar
Whether a write, or an edit that changes content, answers with the nearest existing engrams and the advice to merge, supersede or link them, true by default. false turns the hint off for agents and in Fluid alike.
recall.enabled
Whether the prompt hook crystalline install wires puts the engrams that may apply in front of the agent with each prompt, true by default. It works in Claude Code and Codex; Copilot gets the hook too, but there it stays quiet. false keeps the hook installed and silent.
recall.limit
How many engrams one prompt may bring along, 1 to 5, 3 by default; the rest wait for a later prompt on the same topic.
recall.min_score
The search score an engram must reach before the hook names it, 0.0 to 1.0, 0.69 by default. Raise it for a quieter hook and lower it to hear about weaker matches.

17.8 Embeddings

The embedding model turns text into the vectors semantic search compares. It’s configured in an embeddings block that isn’t in the registry: you edit it in the file by hand, it has no environment twin and config set doesn’t know it. The daemon reads it when it starts, so restart after a change. A block needs both provider and model, and a block missing either stops the whole file from loading.

embeddings.provider
local (the default) runs the model inside the daemon, and openai-compatible (also spelled openai or remote) sends the text to an endpoint that speaks the OpenAI embeddings API.
embeddings.model
For local, granite-embedding-97m-multilingual-r2 by default, a multilingual model of about 220 MB, or bge-small-en-v1.5, the English model used before 0.19.0, about 130 MB. Either the short name or the full repository name works. For a remote provider it’s whatever name the endpoint gives its model.
embeddings.endpoint
The base address of a remote provider, which won’t start without it; the daemon posts the text to <endpoint>/embeddings.
embeddings.api_key_env
The name of the environment variable that holds the remote provider’s key, never the key itself; if that variable isn’t set, the provider fails to start.

An install without the block downloads the multilingual model on first start. Write the block yourself to keep an index on the English model or to use a remote endpoint:

embeddings:
  provider: local
  model: bge-small-en-v1.5
embeddings:
  provider: openai-compatible
  model: my-embedding-model
  endpoint: https://embeddings.example.com/v1
  api_key_env: EMBEDDINGS_API_KEY

Switching the model re-embeds every engram in the background. If the provider can’t be built (a missing key, an unknown model), the daemon logs why and carries on with full-text search only. crystalline model download fetches the configured local model ahead of time, for a host that won’t have network access later.

17.9 Storage

These keys decide where the index lives. For a file domain the index is derived from the files and can always be rebuilt, while a virtual domain’s engrams live in the index itself. The two database keys wait for the next daemon start, while index.files and domains_root take effect at once.

database.backend
The store behind the index: turso, the embedded default, or postgres. Several instances can share one PostgreSQL database with pgvector, each file domain hosted by one of them, as docs/deployment.md describes under shared database collaboration.
database.url
For postgres, the connection URL, starting postgres:// or postgresql://. For turso, an optional path for the index file, below --db and above the default.
index.files
Whether Crystalline keeps a generated index.md in every folder of a file domain, true by default. Set it to false and Crystalline stops generating them, leaving the ones already there where they are and out of the index. Either way they stay on your machine unless the domain’s MANIFEST shares them (Chapter 18).
domains_root
The folder a new file domain lands under when you give no path, ~/Documents/Crystalline by default. In a container, point it at a persistent path so domains created in Fluid survive.

Accounts don’t move to Postgres. web-auth.db stays a local file in each node’s state folder whatever the backend, and crystalline reindex --wipe refuses on Postgres. Each domain’s own entry in the file (domains.<name>, with its path, origin, review mode and provisioning decision) is written by the domain commands, and Chapter 19 lists its keys.

17.10 Identity and prompt rules

identity.actor and prompt.rules decide whose name a write carries and which domains a session hears about. The first is a registry key like the ones above, the second a hand edit in the file.

identity.actor
Who is recorded as the writer in generated.by on every write, for example team-bot/1.0 or human:dallas, with no spaces. A change takes effect at once, and while it’s unset the connected client names itself.
prompt.rules
Which domains the session-start briefing names, depending on the folder a session starts in. It’s a hand edit with no environment twin, and it applies from the next session on. Each key is a path pattern, with ~ expanded, and each value an include list, an exclude list or both.

Every rule whose pattern matches the workspace counts. The included domains of all matching rules add up and the excluded ones are taken away; a match with no include starts from every domain. When no rule matches, or there are no rules, the briefing names every domain. A pattern ending in /** matches the folder itself as well as everything under it, so a session started right in ~/work names engineering and payments. In ~/work/website or any folder below it both rules match: the first includes the two domains, the second takes payments away, and the briefing names engineering only.

prompt:
  rules:
    "~/work/**":
      include: [engineering, payments]
    "~/work/website/**":
      exclude: [payments]

17.11 Environment variables

Every one of the 41 registry keys has an environment twin: CRYSTALLINE_ followed by the key in capitals, with dots turned into underscores. github.enabled becomes CRYSTALLINE_GITHUB_ENABLED, domains_root becomes CRYSTALLINE_DOMAINS_ROOT and the login throttle is CRYSTALLINE_AUTH_LOGIN_FREE_ATTEMPTS and CRYSTALLINE_AUTH_LOGIN_MAX_DELAY. A twin takes the same values config set does and is checked the same way, which is how a container gets configured without a file. A domain registers from the environment too, through CRYSTALLINE_DOMAIN_<NAME> and its _ORIGIN and _REVIEW suffixes, for this process only (Chapter 19). A handful of other variables cover what the registry doesn’t:

CRYSTALLINE_CONFIG
Another configuration file for every command in that environment, with ~ expanded; --config wins over it.
CRYSTALLINE_GITHUB_TOKEN
A GitHub token for a machine that can’t sign in interactively. While it’s set, a saved sign-in is ignored and crystalline connect github refuses.
CRYSTALLINE_MODELS_DIR
Where the embedding model lives instead of the cache folder, for a host without network access or an image with the model built in (the with-model image sets it). Give two daemons with different models a folder each, or each deletes the other’s model on every start.
CRYSTALLINE_UPSTREAM
Tells the separate Fluid image where its web server forwards /api/, as host:port, crystalline:7411 by default. Crystalline itself never reads it.

XDG_CONFIG_HOME, XDG_STATE_HOME and XDG_CACHE_HOME move the three folders from the top of this chapter, and on Windows APPDATA and LOCALAPPDATA do the same. COPILOT_HOME tells crystalline install where the Copilot CLI keeps its files, ~/.copilot by default.

RUST_LOG
Sets how much the daemon and every command log, as a filter like RUST_LOG=debug or RUST_LOG=crystalline_service=debug,warn. Without it serve logs at info and everything else at warn. The log goes to stderr only, so the routing block, hook output and the MCP stream stay clean, and a hook logs only when the variable is set.
NoteIn brief

The configuration is one YAML file per user under ~/.config/crystalline, beside a state folder that holds the index and the accounts and a cache that holds the model. For the 41 registry keys an environment variable beats the file and the file beats the default, only five flags override outright, and config set or the configure tool change a key while rewriting the whole file. Keys under auth, database and most of service apply at the next daemon start, as do skills.serve and the embeddings block; prompt.rules applies from the next session and the other keys take effect at once. The embeddings block, prompt.rules and the domain registrations are edited by hand or with their own commands and have no environment twin, while every registry key does.
