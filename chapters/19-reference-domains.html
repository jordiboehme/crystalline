19  Domains

This chapter is the lookup for everything you can set on a domain and every rule you run into while doing it: reach for it when a prompt to the agent isn’t enough (a script, a container or the question of why a command refused). The prose chapters keep the why (domains in Section 4.1, private domains in Chapter 12, team domains and review mode in Chapter 13, membership in Chapter 14, provisioning in Chapter 15). The MANIFEST’s own keys are in Chapter 18 and every other setting is in Chapter 17.

19.1 Kinds of domain

Every domain is one of three kinds, and the same tools read and write all of them. Whether a domain lives in files or in the database is fixed when you register it, and a file domain turns into a team domain once you connect an origin to it.

file domain
A folder of markdown files with a MANIFEST.md at its root, the default kind. The files are the source of truth and the index is derived from them, so a rebuild of the index loses nothing.
virtual domain
A domain that lives in the database with no folder on disk, for a container without a writable volume or a Postgres backend shared by several machines. Its engrams live only in the index, so removing it deletes them and crystalline reindex --wipe refuses while one is registered.
team domain
A file domain with an origin: a GitHub repository, an optional subfolder in it and a branch. It needs github.enabled and a GitHub connection, and it can’t be virtual, because a proposal needs files to carry.

19.2 The registration block

Each registered domain is one entry under domains: in the global config.yaml, keyed by its name, and the commands in this chapter write these entries for you. crystalline config set doesn’t reach them, so a key without a command is a hand edit.

domains:
  books:
    path: ~/Documents/Crystalline/books
    provision: true
  club:
    path: ~/Documents/Crystalline/club
    origin:
      repo: dallas/book-club
      path: knowledge
      branch: main
      poll_secs: 600
    review: overlay
  reading:
    kind: virtual
kind
Either file or virtual, and it only appears on a virtual domain, since a file domain leaves the key out.
path
The domain’s root folder, with a leading ~ expanded; a file domain registered without one lands at <domains_root>/<name>, and a virtual domain has none.
origin.repo
The GitHub repository of a team domain, as owner/name; its presence is what makes a file domain a team domain.
origin.path
The subfolder of the repository that is the domain root, for a repository that holds more than knowledge (absent means the repository root).
origin.branch
The branch the domain tracks. Adding a team domain without a branch writes the repository’s default branch here, asked from GitHub; an entry without the key, from before that or written by hand, tracks main.
origin.poll_secs
How often the daemon checks this origin for merged work, in seconds. Absent defers to the global github.poll_secs (300 unless set), and any value below 60 is raised to 60. No command sets it, so it’s a hand edit.
provision
This machine’s decision on the artifacts the domain ships: true installs them into every onboarded harness, false keeps them out and removes what was installed. Absent means undecided, and nothing installs.
review
overlay puts the domain in review mode; absent means the domain takes changes directly, which is how every domain starts.

19.3 Names

The name is the key in the config, the folder under the domains root, the first segment of every crystalline:// address and the word the agent routes by, so choose it once: no command renames a domain.

What a name may be
Letters and digits in any script, plus -, _ and ., up to 64 characters, with no dot at the start or the end. The Windows device names (CON, PRN, AUX, NUL, COM1 to COM9, LPT1 to LPT9) are refused on every platform. The command line, add_domain, Fluid and the API all run this check, and so does domain init --name, with the same message everywhere. A name registered before the check existed keeps working.
Names taken already
Adding a name that is already registered at the same folder, or as the same virtual domain, changes nothing and indexes it again, so every way of adding a domain is safe to repeat. The same name at another folder or as the other kind of domain is refused, and the message names what holds it. Every surface also refuses a name that an environment variable already defines, and the refusal names the variable, because that domain belongs to it.
Names given for you
add_domain without a name takes the folder’s name, with a suffix when that one is taken, and a team domain takes the repository’s name; a name made this way is always turned into a valid one (a folder called CON becomes con-2). Fluid does the same for a team domain whose name field is left empty.

19.4 Registering a domain

There are five ways in: the agent’s tool, the command line, Fluid, the JSON API behind it and environment variables. Each registers the domain, and all but --no-sync index it at once.

add_domain
The MCP tool, with domain, folder, virtual, repo, path and branch. The arguments pick the kind: repo makes a team domain, virtual: true a virtual one (it needs domain), anything else a file domain, and repo and virtual can’t be combined.
add_domain on a folder
A folder without a MANIFEST.md gets a starter one, and the files already there are kept and adopted in place. Without folder the domain lands at <domains_root>/<domain>.
Who may call add_domain
Any local session may. Over HTTP, on an instance where agents sign in, it takes the instance admin role, and a read-only instance refuses it.
crystalline domain add <name> [path]
Registers a domain and indexes it at once, in <domains_root>/<name> when no path is given. A file domain needs a MANIFEST.md in its folder already and refuses with the domain init line otherwise.
--virtual
Registers a virtual domain and scaffolds its MANIFEST into the index; it takes no path and can’t be combined with --origin.
--origin owner/repo[/subfolder]
Connects a team domain and downloads the repository, or the subfolder given after its name, into the domain’s folder; it needs github.enabled and a prior crystalline connect github. A folder that already holds knowledge, or a registered domain with no origin yet, is connected in place: nothing local is overwritten, and files that differ from the repository become local changes to share.
--branch
The branch to track, and it only works with --origin. Left out, Crystalline asks GitHub for the repository’s default branch and records it; when GitHub can’t answer, the add refuses and asks for --branch.
--no-sync
Registers a file domain without indexing it, for a script that runs crystalline sync later; a team domain is always indexed as it connects, so the flag refuses with --origin.
--private and --owner <account>
Registers the domain private from its first minute, owned by the named account. --private needs --owner, and before anything is registered the account has to exist and be enabled. A domain that is already registered is refused here; crystalline domain visibility makes that one private.
crystalline domain init <path>
Creates the folder if needed and writes a starter MANIFEST.md with the Scope, When to Use and Notes for Agents sections, then prints the domain add line to run, or says a MANIFEST is already there and leaves it alone. --name sets the name in the manifest, the folder’s name otherwise. It never touches the config.
crystalline domain list
Lists the registered domains, with engram counts when the index is there.
Fluid’s New domain dialog
Only admins get the dialog. Its Kind is Local folder, Virtual or GitHub team, and the fields follow it: a Name for the first two; a Repository, Branch, Folder in the repository and an optional Name for a team domain. A local domain always lands under the server’s domains root, since a browser can’t name a folder on the server, and the Private box makes the domain private with you as its owner.
POST /api/v1/domains
The request behind the dialog, for a script, with mode (local, virtual or github), name, repo, branch, path and private as its fields. A field that doesn’t belong to the mode is refused rather than ignored, and a team domain on an instance with no GitHub connection is refused with where to make one.
CRYSTALLINE_DOMAIN_<NAME>=<path>
Registers a file domain for as long as the variable is set, for a container that shouldn’t carry a config file. The domain’s name is <NAME> in lower case with _ turned into -, and the variable replaces a config.yaml entry of that name, with a warning at startup, without ever being written into the file.
CRYSTALLINE_DOMAIN_<NAME>_ORIGIN
Attaches an origin to that domain, as owner/repo[/subfolder][@branch], so a new node downloads the team domain on its first start; with CRYSTALLINE_GITHUB_ENABLED off the domain waits and says so, and without the matching CRYSTALLINE_DOMAIN_<NAME> the daemon refuses to start. Because the suffix is read first, no variable can define a domain whose name ends in -origin or -review, so register such a domain in the file, and look in Chapter 17 for the GitHub token variable that goes with the origin.

19.5 Moving knowledge in and out

These commands copy engrams between a domain and a folder or an archive, and none of them changes the domain’s registration.

crystalline domain import <path> --domain <name>
Loads engram files that are already well formed into a registered virtual domain, verbatim. A file domain is refused: for a folder of notes that still needs converting, crystalline import writes into the domain’s folder and crystalline sync indexes it.
--overwrite and --dry-run on domain import
An engram whose path or permalink already exists is skipped unless --overwrite says otherwise, and --dry-run reports what would land and writes nothing.
crystalline domain export <path> --domain <name>
Writes any domain’s engrams out as an ordinary markdown folder, which is how a virtual domain’s content gets checked with crystalline verify or turned back into files. --force writes into a folder that isn’t empty, and --dry-run only reports.
Fluid’s Backup card
The card sits above the Danger zone at the foot of the domain’s page and is drawn for admins. Download archive saves a zip of the whole domain, MANIFEST and attachments included, and works on a read-only instance too. An archive from a file domain restores into a virtual one and the other way round.
Import archive
Uploads such a zip into the domain, shows a preview of every entry first and imports only after you confirm. Skip existing, the default, leaves a path that’s already there alone, and Overwrite existing replaces it. A MANIFEST in the archive is never imported, and a broken or oversized archive is refused as a whole.

19.6 Removing a domain

Removing a domain unregisters it and clears its rows from the index. A file or team domain’s files stay on disk and the team’s repository is never touched: the only knowledge a removal can delete is a virtual domain’s, and that takes an explicit confirmation.

crystalline domain remove <name>
Unregisters the domain. Registering the same folder again adopts the files as they are, and a team domain is connected again with its repository, which keeps its origin. The visibility and membership records go too, so a later domain under the same name starts out shared.
--purge
Confirms that a virtual domain’s engrams are deleted with it, and nothing brings them back afterwards; a virtual domain that holds any refuses without it, so export first when you want a copy.
--end-drafts <actor>
Names one other person whose private drafts in a review-mode domain end with the removal; repeat it for each. The refusal says who is drafting and how many drafts each holds, and your own drafts need no naming.
remove_domain
The MCP tool, with domain, purge and end_drafts working as the flags do. On a harness that can ask, the first call removes nothing and puts a confirmation question to you naming the domain, its kind, its engram count and the drafts at stake.
Who may remove a domain
The machine operator, an instance admin or, for a private domain, its owner. An agent on an instance that leaves agent authentication off is refused. A domain defined by an environment variable can’t be removed at all: unset the variable instead.
Unregister domain
The button in the Danger zone at the foot of the domain’s page, drawn for admins and for a private domain’s owner. It asks you to type the domain’s name and says whether the files stay on disk or, for a virtual domain, are deleted.

19.7 Visibility and membership

Every domain starts shared, visible to every account on the instance. A private domain is visible only to its owner, the instance’s admins and the accounts invited into it, and to everyone else it answers as if it had never been registered (Chapter 12).

crystalline domain visibility <domain> private --owner <account>
Makes the domain private and hands it to that account, which has to exist and be enabled. Making a domain that is already private private again changes nothing, its owner included.
crystalline domain visibility <domain> default
Shares the domain with every account again and forgets its list of members, so making it private later starts from the owner alone.
Make private and Share with everyone
The same switch in Fluid’s Danger zone, confirmed by typing the domain’s name. Making a domain private is for admins, and the admin who does it becomes the owner; sharing it again is for the owner or an admin.
viewer
The membership level that reads and searches the domain and nothing more. It’s the level an invitation takes unless you name another.
editor
A viewer who also writes and edits engrams in the domain, as far as the account’s instance role allows.
manager
An editor who also runs the membership: inviting, removing and changing levels up to manager. A manager can’t change visibility, transfer the domain or remove it.
crystalline domain members <domain> list
Prints the owner and every member with their level, though a shared domain has no owner and no members, because membership only decides anything while a domain is private.
crystalline domain members <domain> add <user>
Invites an account, or moves a member to another level, with --level viewer, editor or manager; the owner can’t be added, because the owner already holds every level.
crystalline domain members <domain> remove <user>
Ends a membership, though the owner can’t be removed this way; hand the domain on first.
The Members card
The same list in Fluid, on the domain’s page: invite by username and level, change a level, remove, and a Leave button for a member’s own membership, which needs nobody’s permission.
crystalline domain transfer <domain> <new_owner>
Hands a private domain to another existing, enabled account, which becomes the owner at once. The old owner keeps nothing and is a stranger to the domain unless invited back. It’s for the owner or an admin, and Fluid offers it on the Members card.
A deleted owner
Deleting the owner’s account leaves the domain with no owner and only an admin can administer it after that, so transfer it before the account goes.
Instance role and membership level
On a shared domain an account does what its instance role allows: a viewer reads, an editor writes, an admin does everything. On a private domain the membership decides what the account may reach, and a write takes the lower of level and role. So an instance viewer invited as an editor writes nothing, and neither does an owner whose instance role is viewer.
Action on a domain Who may
Read and search viewer or better
Write editor or better, capped by role
Invite, re-level, remove manager, owner, admin
Leave the member
Make private admin
Share again, transfer owner, admin
Review mode on or off owner, admin
Unregister owner, admin
Register, provision admin
Backup and archive import admin

The command line and a local stdio session are the machine operator and pass every gate in this table. An agent over HTTP on an instance where agents sign in is its user and gets exactly that user’s row, with no tool for membership at all. Where agent authentication is off, an agent is nobody in particular: it reads and writes the shared domains, registers and provisions without a role and is refused when it unregisters one.

19.8 Review mode

Review mode gives every writer a private overlay of drafts over a team domain’s folder, and the folder changes only with what lands on the team’s branch (Chapter 13). It lives in the registration as review: overlay, never in the MANIFEST, and no MCP tool turns it on.

crystalline domain review <domain> overlay
Turns review mode on. It needs a GitHub origin and a folder, so a virtual domain is refused, and it refuses while the folder holds unshared changes, listing their paths to share or revert first.
crystalline domain review <domain> direct
Turns review mode off, which ends every private draft in the domain. Run without answers it prints the plan (who holds drafts, how many and where two people drafted the same path), and then it needs one --fold or --discard per person the plan names.
--fold <actor>
Writes that person’s drafts into the domain’s folder as they are (your own drafts from the command line or a local session belong to the actor owner).
--discard <actor>
Ends that person’s drafts without touching the folder. Both flags repeat, one per person, and both refuse with overlay.
The Review mode card
The same switch near the foot of the domain’s page in Fluid. Turning it off shows the plan with a fold or discard choice per person, set to fold until you change it.
Who may switch review mode
The machine operator, an instance admin or a private domain’s owner; a domain an environment variable defines is refused, because its variable holds the setting.
CRYSTALLINE_DOMAIN_<NAME>_REVIEW=overlay
Puts a domain defined by CRYSTALLINE_DOMAIN_<NAME> in review mode, and any other value stops the daemon at startup, while an empty one counts as unset. The variable and a hand-edited review: key are taken as written, without the origin check the command makes, so pair them with an origin.
One proposal at a time
A domain in review mode keeps one open proposal, even with github.stacks on. A second share while one is open is refused: somebody else’s proposal is named with the choice to wait for the merge or ask for a withdrawal, and your own is withdrawn and shared again.

19.9 Sharing and sync

Whether a team domain shares through proposals or straight onto the branch is the MANIFEST’s sharing switch. That key and generated_indexes, which decides whether the folder listings travel with a share, are in Chapter 18. The per-domain part of sync is the origin block above.

github.enabled
The switch every team domain needs before it can be added or kept current, and Chapter 17 has it with the other github.* settings.
The background poll
The daemon checks each team domain’s origin on the interval above and brings merged work into the folder, and a read-only instance keeps polling, so it follows the team’s repository on its own.

19.10 The provisioning decision

A domain whose MANIFEST declares a Provisioning section ships skills, commands, subagent definitions and MCP server configs, and each machine decides per domain whether to take them (Chapter 15). The decision is the registration’s provision key.

crystalline provision allow <domain>
Sets provision: true and reconciles, installing the domain’s artifacts into every harness this machine onboarded.
crystalline provision deny <domain>
Sets provision: false and reconciles, which removes whatever the domain shipped before.
crystalline provision status
Prints every domain’s decision, the domains still waiting for one and each harness’s installed state.
provision
The MCP tool, with action set to status, allow, deny or apply and domain for the two decisions. On an instance where agents sign in, everything but status takes the admin role.

19.11 Where domains live and which ones an agent hears about

Four more settings touch domains without belonging to one. Two sit in the global config and two are files named .crystalline.yaml, one in a workspace and one at a domain’s root.

domains_root
The folder a new file domain lands in when nobody names one; the setting is in Chapter 17.
prompt.rules
Narrows which domains the session-start briefing names for a workspace, by path pattern. The rule syntax and an example are in Chapter 17.
preferred_domains
A list in a .crystalline.yaml at a workspace’s root that puts those domains first in the briefing, in that order. It only reorders and never hides a domain.
Where the two routing hints apply
Both need a workspace path, so they shape the briefing the session-start hook prints with crystalline prompt system, while an agent connecting over MCP gets the server’s briefing, which covers every domain it may see and ignores both.
The domain’s own .crystalline.yaml
A file at a file domain’s root whose verify: block tunes the checker for that domain, with its keys and the codes they touch in Chapter 20; a virtual domain has no root, so it always takes the defaults.
NoteIn brief

A domain is a folder, a database-only virtual domain or a team domain with a GitHub origin, and each is one entry under domains: in config.yaml with path, origin, provision and review. You register one with add_domain, crystalline domain add, Fluid’s New domain dialog or an environment variable, and removing it leaves files on disk but deletes a virtual domain’s engrams, which is what --purge confirms. Every domain starts shared, and a private one belongs to one owner and admits members as viewer, editor or manager; a write there takes the lower of level and instance role. Review mode is switched with crystalline domain review or the Review mode card and needs a GitHub origin and a clean folder, and turning it off folds or discards each person’s drafts. prompt.rules and preferred_domains steer the hook’s briefing, and a domain’s own .crystalline.yaml tunes the checker of chapter 20.
