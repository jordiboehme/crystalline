Questions and answers

The questions people ask in the first week, and a few that come up in the second, once somebody is onboarding agents for other people. Each answer points at the chapter that goes deeper.

Why not just a folder of markdown files?

It is one. Every engram is a markdown file in a folder you chose, readable in any editor, diffable in any repository and backed up with whatever you already use. What a folder cannot do on its own is what Crystalline adds on top: routing, so an agent knows which domain owns a task without reading every file; search that blends the exact phrase with the meaning; a graph of relations and backlinks; and a temporal model, so a fact that stopped being true in March still carries its dates and is no longer mistaken for the present. Chapter 1 walks the ladder from one file of instructions to real indexes.

Why not a vector database or a retrieval pipeline?

Retrieval is the easy half. A vector index finds text that resembles a question. It does not know which domain owns the task, that a fact was superseded, who verified a claim or that something worth writing down just happened in this session. Crystalline treats similarity as one ranking signal inside a larger system of routing, provenance and time, on files you own, with no pipeline to operate. A pipeline also swallows whatever it is fed. Here knowledge is taught, and in a team it is reviewed before it reaches anyone else’s agent, so what comes back is meant to make sense rather than merely to resemble the question. Chapters 4 and 11 cover the ranking, and chapter 13 the review.

Where does the name come from?

From psychology. Crystallized intelligence is what learning deposits in a person; fluid intelligence is the reasoning applied to a problem never seen before. A model arrives with fluid intelligence in abundance and none of your crystallized kind, so every session starts as a brilliant stranger. Crystalline is the crystallized half, the store of what an agent has learned, and Fluid, the web UI, is named for the seam where fluid minds meet it. An engram is neuroscience’s word for the trace an experience leaves. Chapter 2 is the whole story.

Is Crystalline a hosted service?

No. It is a binary that runs on a machine of yours, your laptop by default or a server your team operates, and the knowledge is a folder on that machine’s disk. Nothing runs on anyone else’s servers. GitHub, where a team uses it, holds a reviewed copy of a domain’s files, the way it holds code; it serves nothing and sees no index. Chapter 1 has the two shapes and chapter 7 the shared one.

Do I have to run a server?

No. The first agent that connects starts a background daemon on your machine, and every later agent, terminal and browser tab attaches to it. crystalline serve runs the same daemon in the foreground and crystalline serve --daemon in the background. It stops only when told to, with crystalline ctl shutdown, Ctrl-C in a foreground serve or the signal a container sends; it keeps running after the last agent disconnects, so the index stays warm for the next session. If a crash ever leaves a stale lock or socket behind, crystalline doctor --fix clears it and a daemon that is alive but no longer answering is replaced by the next client that connects.

Do I need a terminal at all?

Only for the local install and the occasional maintenance command. Claude Desktop users install an extension from the releases page and never open one: the agent creates its first domain itself, and Fluid, in the browser, is where a person reads, edits and corrects. Chapter 6 has both paths.

Is the MCP endpoint over HTTP protected?

On a laptop it listens on loopback, 127.0.0.1:7411, and any process on that machine can reach it, which is the right trade for one person; crystalline config set service.http false turns the endpoint off. The daemon also checks the request’s Host header against a loopback allow-list to block DNS rebinding, so a hostname or a proxy name has to be added first. Fluid and its API on the same port have accounts of their own, and nothing there is readable without a session.

On a shared instance turn on auth.mcp, and from then on every agent that connects over HTTP identifies itself with a token that belongs to one person, with no anonymous tier beside it. Chapter 7 sets it up and chapter 14 says what the token means.

Where does my knowledge actually live?

In your domain folders, as plain markdown. By default those folders sit under ~/Documents/Crystalline, one per domain, which is where an agent creates a domain when nobody names a path. A folder you registered yourself lives where you put it, like chapter 6’s ~/knowledge/engineering, and the domains_root setting moves the default. Everything Crystalline derives from it is disposable: the search index lives in the state directory and crystalline reindex --full rebuilds it from the files at any time. The config file, the index and the embedding model live in the platform’s config, state and cache directories, ~/.config/crystalline, ~/.local/state/crystalline and ~/.cache/crystalline on Linux and macOS.

Is my knowledge locked in?

No. An engram extends Google’s Open Knowledge Format, OKF 0.2: markdown with YAML frontmatter, readable by any OKF tooling and by any text editor. Frontmatter keys Crystalline does not know are preserved through every write, an index.md at each domain’s root lets a folder navigate itself on a git forge with nothing running, and crystalline import brings an existing tree of frontmatter markdown in as a pure file transformation. If you stopped using Crystalline tomorrow, the folder would still be a readable knowledge base. Chapter 5 has the format.

What happens to wrong knowledge?

It depends on how it was wrong. A fact that was never quite true, a cutoff measured from the wrong event, is corrected where it stands. A fact that was true and stopped being is superseded: the replacement is written as its own engram with supersedes pointing back, the old one gets status: superseded and a real valid_to, and any lesson worth keeping moves forward. The past stays in every search, dated and gently below the present. The sweep finds the retirements nobody finished, the links that dangle and the tags spelled two ways, and hands each to the agent as a mechanical fix or to you as a judgment. Deleting is for mistakes, never for history. Chapters 3 and 12.

What is GitHub, and what does Crystalline use it for?

GitHub is a website where teams keep files and every change ever made to them, above all source code. Its habit worth borrowing is the review: a change to something shared is proposed first, a colleague who knows the subject reads it, and only then does it land for everyone. Crystalline uses GitHub for exactly that, with knowledge in place of code. A team domain’s markdown lives in a GitHub repository, a change goes out as a proposal, a pull request in GitHub’s own words. It reaches everyone’s agent once somebody has merged it. You do not need to learn GitHub’s tools to take part: a one-time sign-in through a code in the browser connects your machine. After that the agent, Fluid or the command line does the talking. Chapter 13 walks through it. A team that does not use GitHub loses nothing else in this book; only sharing a domain between machines needs it.

Do I need git to share knowledge with a team?

No. A team domain talks to GitHub directly over its API: each person connects once with a browser code, and proposals open as pull requests that a person reviews and merges there. No local clone, no SSH key and nobody types git. Chapter 13.

Can the agent see my private domain?

Only if its user can. On a shared instance an agent authenticates with a token that belongs to one person and acts as that person for the length of the session: it sees what they see, writes where they may write and captures under their name. A private domain shows to its owner, to the instance’s admins and to the members the owner invited, and to everyone else it reads as absent, on every surface. There is no tool for changing a membership, so an agent cannot talk itself in. Before you rely on it, know the limits: admins see every domain, and a private domain protects from the instance’s other users, never from whoever operates the machine. Chapters 7 and 14.

What does the onboarding cost in tokens?

Little, and the same on the tenth session as on the thousandth. The routing block is one line per domain and a handful of rules; the reminder at the end of a session costs about a hundred and twenty tokens and fires once; and recall loads only the engrams that matter, routed by domain and narrowed by the indexes, instead of a folder read whole every session. Chapters 8 and 11.

What should I teach first?

Whatever you would tell a new hire in the first week, and the test is that sentence. The rule behind the strange number, the nickname, the word the wiki gets wrong, the day nobody deploys. Teach where information lives rather than the information itself: which repository holds what, how access is granted, the architecture, so the agent can reach the territory with the tools its harness already gives it. Chapter 9 has the list, and chapter 10 says what to do when the first week meets the wiki.
